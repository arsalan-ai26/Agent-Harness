Software factory I: stations

One session with one context fills up (fact 3), and a model checking its own work shares its own blind spots (fact 5). A software factory follows from taking those facts seriously at scale: it is the harness scaled from one session to the whole delivery loop: an issue goes in, a reviewed draft pull request comes out, and people make the judgement calls. This chapter reads the real code of eve's Foreman template and compares it with Stripe's Minions, Ramp, Coinbase and StrongDM. You build a four-station factory that works on your own book repository.

  2. Why might a factory use different model vendors for different stations?
  3. What is the difference between a light factory and a dark factory?
Answers
  1. So it judges the real diff against the criteria instead of being persuaded by the author's explanation.
  2. Cost (cheap models for triage and planning) and independence: a reviewer from another vendor is less likely to share the implementer's blind spots.
  3. In a light factory humans review every pull request (Stripe). In a dark factory humans write specs and scenarios but review outcomes, not code (StrongDM).

1. What a factory adds to a harness

Why split one job into stations instead of giving one agent the whole issue? Derive it. A single session that triages, plans, codes and reviews accumulates everything in one window, so by the review it is reasoning through a crowded context (fact 3). Worse, it reviews its own work with the same weights, the same prompt and the same history that produced the mistake (fact 5); its errors are correlated with themselves. Splitting gives each station a fresh window holding only what that job needs, and lets the reviewer be a different model that sees only the diff and the criteria. Independence is the point: two samples with different blind spots catch more than one sample checked twice.

The other parts follow too. Acceptance criteria must be written before the code, because a check written after it is shaped by it. The revision loop must be bounded, because a model that failed twice on the same feedback is unlikely to succeed on the tenth try, while the bill keeps growing (fact 4). Memory across runs must be small and curated, because it is loaded into every station's window.

Everything in Stages 1 to 4 still applies inside each station. The factory adds structure around them: intake from where work is filed, triage, a plan with checkable acceptance criteria, isolated implementation, independent review, a bounded revision loop, safe delivery and memory across runs.

2. Code tour: Foreman

apps/templates/eve-software-factory-template/ is a complete, deployable factory. Read it in this order.

  • agent/agent.ts: the orchestrator. Compaction at 75% of the window, and a session usage limit: stop when output passes 100,000 tokens or uncached input passes 40 million. "Crossing a limit asks an attended caller to continue; unattended work cannot wait."
  • agent/lib/models.ts: one model per station, across vendors. Orchestrator and Implementer: Anthropic; Analyst and Classifier: a fast OpenAI model; Reviewer: a different OpenAI model; Researcher: Anthropic Opus; the triage decision: a Google model. Cheap models where judgement is narrow, strong ones where it is wide, and a reviewer that does not share the implementer's vendor.
  • agent/subagents/: classifier, analyst, implementer, reviewer, researcher, each started by a run_* tool in agent/tools/.
  • agent/channels/: github.ts, linear.ts, intake.ts (authenticated HTTP tickets), eve.ts. A factory label or an @mention starts work, but only from users GitHub verifies as having triage, write, maintain or admin rights.
  • agent/lib/factory-brain.ts: the brain is "a short, curated set of durable notes about the target repository, not a transcript of every run", size-bounded, under a reserved storage prefix that only trusted callers may write.
  • agent/tools/diagnose_ci_failure.ts: when CI goes red on a factory PR, Foreman classifies the failure first. Only code failures get a revision; missing logs, infrastructure, configuration and flaky failures stop for a person.
  • evals/: pipeline, routing and safety suites. The factory is tested like the harness.

The README's security details are worth copying: authenticated git runs in separate disposable transfer sandboxes, never in stations that execute repository code; only bounded git bundles cross that boundary; pushes target one branch prefix, refuse the default and protected branches and never force-push; label intake is at-most-once through a write-once claim; station sandboxes start with egress limited to GitHub and package registries, and install scripts are disabled by default.

Factory pieces inside the reference harnesses

None of the five reference harnesses is a factory, but each ships the parts one is built from, and which parts they chose says a lot.

  • Codex has the unattended pieces: codex exec with --json and --output-schema for CI, codex review against a base branch or commit, and cloud tasks (codex-rs/cloud-tasks/) that run in OpenAI's environments. Its flag for running without approvals or sandbox is named --dangerously-bypass-approvals-and-sandbox and documented as "intended solely for running in environments that are externally sandboxed": the factory, not the agent, must provide the boundary.
  • Claude Code runs headless with claude -p, and Anthropic's GitHub Actions integration starts it from issue and PR comments. The paper's custom-agent frontmatter (tools, model, permission mode, isolation, max turns) is effectively a station definition.
  • Qwen Code has the most factory-shaped code: an autofix_pr tool (tools/autofix-pr.ts) that runs a watch on a pull request and lets the fix agent run its commands unattended only after the user confirmed that watch; teams with a plan-approval step (team_create, team_plan_approval); git worktrees per agent; and GitHub and GitLab channels for intake.
  • Kimi Code has goals with deadlines (features/goal/), cron, and a swarm mode, which are the long-running, scheduled parts of a factory.
  • Trae Agent is a factory of attempts rather than of stations: generate many candidate patches, prune them, and let a selector agent choose (Chapter 14).

6. Build: four stations on your own repo

"""A small software factory: triage -> analyst -> implementer -> reviewer -> draft PR.
Each station is your harness with its own prompt, tools, model and working copy."""
import json, re, subprocess
from pathlib import Path

BRANCH_PREFIX = "factory/"
BRAIN = Path("factory-brain.md")         # short, curated notes about the repo; every run starts from it
BRAIN_MAX_CHARS = 6_000
MAX_REVISIONS = 2

STATIONS = {
    "triage": {"model": "cheap", "tools": ["read", "bash"],
               "system": "Classify the issue. Reply JSON only: {\"lane\": \"ready\"|\"clarify\"|\"reject\", "
                         "\"questions\": [...], \"reason\": \"...\"}. Use 'clarify' if acceptance is unclear."},
    "analyst": {"model": "strong", "tools": ["read", "bash"],
                "system": "Write an implementation plan for the issue. Reply JSON only: {\"plan\": [steps], "
                          "\"acceptance\": [checkable criteria], \"files\": [paths]}. Do not edit files."},
    "implementer": {"model": "strong", "tools": ["read", "write", "edit", "bash"],
                    "system": "Implement the plan in this working copy. Run the repository's own tests and linters "
                              "until they pass. Commit your work. Reply with a short summary."},
    "reviewer": {"model": "other-vendor", "tools": ["read", "bash"],
                 "system": "You review a diff against acceptance criteria. You did not write it and you cannot see "
                           "how it was written. Reply JSON only: {\"verdicts\": [{\"criterion\": ..., \"met\": true|false, "
                           "\"evidence\": \"file:line or command output\"}], \"approve\": true|false}"},
}

def sh(cmd, cwd):
    p = subprocess.run(cmd, shell=True, cwd=cwd, capture_output=True, text=True)
    return p.returncode, (p.stdout + p.stderr).strip()

def parse_json(text):
    m = re.search(r"\{.*\}", text, re.S)
    return json.loads(m.group(0)) if m else {}

def brain():
    return BRAIN.read_text()[:BRAIN_MAX_CHARS] if BRAIN.exists() else ""

def run_factory(issue: dict, repo: str, run_station, log=print):
    """run_station(name, cfg, prompt, workdir) -> final text. Returns a dict describing the outcome."""
    context = f"Repository notes:\n{brain()}\n\nIssue #{issue['number']}: {issue['title']}\n{issue['body']}"

    triage = parse_json(run_station("triage", STATIONS["triage"], context, repo))
    log(f"triage: {triage.get('lane')}")
    if triage.get("lane") != "ready":
        return {"status": triage.get("lane", "clarify"), "questions": triage.get("questions", []),
                "reason": triage.get("reason", "")}

    plan = parse_json(run_station("analyst", STATIONS["analyst"], context, repo))
    criteria = plan.get("acceptance", [])
    log(f"analyst: {len(plan.get('plan', []))} steps, {len(criteria)} criteria")

    branch = f"{BRANCH_PREFIX}{issue['number']}"
    work = str(Path(repo).resolve().parent / f".factory-{issue['number']}")
    _, base = sh("git rev-parse HEAD", repo)                  # review the whole change, not just the last commit
    sh(f"git worktree add -B {branch} {work}", repo)          # the implementer gets its own working copy
    feedback = ""
    for attempt in range(1 + MAX_REVISIONS):
        prompt = f"{context}\n\nPlan:\n{json.dumps(plan, indent=1)}{feedback}"
        run_station("implementer", STATIONS["implementer"], prompt, work)
        _, diff = sh(f"git diff {base} --stat && git diff {base}", work)
        review = parse_json(run_station("reviewer", STATIONS["reviewer"],
                                        f"Acceptance criteria:\n{json.dumps(criteria)}\n\nDiff:\n{diff[:60_000]}", work))
        failed = [v for v in review.get("verdicts", []) if not v.get("met")]
        log(f"review {attempt + 1}: approve={review.get('approve')} failed={len(failed)}")
        if review.get("approve") and not failed:
            return {"status": "ready_for_pr", "branch": branch, "worktree": work, "review": review}
        feedback = "\n\nThe reviewer rejected the last attempt:\n" + json.dumps(failed, indent=1)
    return {"status": "needs_human", "branch": branch, "worktree": work, "review": review}

def open_draft_pr(result, issue, repo):
    """Push only the factory branch, never force, never the default branch; open a draft PR."""
    assert result["branch"].startswith(BRANCH_PREFIX)
    sh(f"git push origin {result['branch']}", result["worktree"])
    body = "Closes #%d\n\nReviewer verdicts:\n%s" % (issue["number"], "\n".join(
        f"- [{'x' if v['met'] else ' '}] {v['criterion']} ({v.get('evidence', '')})" for v in result["review"]["verdicts"]))
    return sh(f"gh pr create --draft --head {result['branch']} --title {json.dumps(issue['title'])} --body {json.dumps(body)}", repo)

Wiring:

  • run_station(name, cfg, prompt, workdir) runs your harness with cfg["system"], cfg["tools"], a model chosen from cfg["model"] and its own session. Use a different provider for the reviewer than for the implementer.
  • Trigger it from the Chapter 12 GitHub channel when an issue gets a factory label from you. Post triage questions back to the issue; on success call open_draft_pr.
  • Point it at this book's repository. Good first issues: fix a typo, add a missing reference, add a test for a build script.

Measure

File 10 small issues. Record for each: lane chosen, revisions used, review verdicts, whether you merged the PR unchanged, and cost. Your merge-unchanged rate is the factory's real score.
