Software factory I: stations

A software factory takes work from where it is filed (an issue, a ticket, a Slack thread) and returns a draft pull request, with no one at the keyboard. It is built from everything in Stages 1 to 4, plus structure: stations that each do one job in a fresh context, acceptance criteria written before code, a reviewer independent of the implementer, a bounded revision loop, safe delivery, and a small memory across runs. This chapter derives why stations beat one long session, walks through ten design decisions using Vercel's open-source Foreman as the worked example, compares what industry built, shows which factory parts each of the nine harnesses ships, and keeps the four-station factory you build.

Before you start: skip check
  1. Why should the reviewer station not be the same session (or even the same vendor's model) as the implementer?
  2. Why must acceptance criteria be written before the code?
  3. CI fails on a factory pull request. Why does Foreman classify the failure before asking for a revision?
  4. Why does Foreman run authenticated git in a separate sandbox from the one that runs the repository's code?
Answers
  1. A model reviewing its own work shares the blind spots that produced the mistake (fact 5). A different model that sees only the diff and the criteria makes independent errors, so together they catch more.
  2. A check written after the code is shaped by the code. Criteria written first are a fixed target the reviewer can hold the work to.
  3. Only code failures can be fixed by revising code. Missing logs, infrastructure, configuration and flaky tests need a person; revising for them burns money and can make things worse.
  4. Repository code (tests, install scripts) is untrusted and can read anything in its sandbox. Keeping credentials in a separate disposable sandbox means the code that runs never sees them.

1. Why stations, from first principles

Why split one job into stations instead of giving one agent the whole issue? A single session that triages, plans, codes and reviews accumulates everything in one window, so by the review it reasons through a crowded context (fact 3). Worse, it reviews its own work with the same weights, prompt and history that produced the mistake; its errors are correlated with themselves (fact 5). Splitting gives each station a fresh window with only what its job needs, and lets the reviewer be a different model that sees only the diff and the criteria. Two samples with different blind spots catch more than one sample checked twice.

2. The decisions, one at a time

Decision 1. Fork a harness, compose on one, or build one?

Decision 2. Who may start work?

A factory triggered by any comment is a remote-control interface for anyone who can comment (Chapter 12). Foreman starts work from a factory label or a mention, but only from users GitHub verifies as having triage, write, maintain or admin rights, and label intake is at-most-once through a write-once claim, so a label applied twice does not start two runs. Public pull request content cannot start a privileged session. Its intake channels are GitHub, Linear and an authenticated HTTP ticket endpoint.

Decision 3. What does the plan contain?

The analyst station turns an issue into a plan with acceptance criteria that can be checked: commands to run, behaviours to observe, files that must not change. Criteria come before code because a check written after the code is shaped by it. If the issue is too vague to write criteria, the right output is a question back to the issue, not a guess.

Decision 4. Which model at which station?

Foreman assigns one model per station, across vendors: Anthropic models for the orchestrator and implementer, a fast OpenAI model for the analyst and classifier, a different OpenAI model for the reviewer, a stronger Anthropic model for research, and a Google model for the triage decision.

Decision 5. How is the implementer isolated?

The implementer runs the repository's code: tests, builds, install scripts. That code is untrusted input (Chapter 7). Foreman's security design is worth copying in full.

Decision 6. How independent is the review?

Foreman's reviewer is a different model from a different vendor, sees only the diff and the criteria (never the implementer's reasoning, on purpose), and must give evidence for each verdict. A human still marks the pull request ready and merges. StrongDM went further, with a rule that code is neither written nor reviewed by humans; people write specifications and scenarios instead. Chapter 14 covers the verification gates in depth.

Decision 7. How many revisions, and for which failures?

A model that failed twice on the same feedback is unlikely to succeed on the tenth try, while the bill keeps growing (fact 4). So the loop is bounded. Foreman adds a second filter: when CI goes red on a factory pull request, it classifies the failure first.

Decision 8. What stops a runaway run?

Foreman's orchestrator compacts at 75% of the window and has a session usage limit: stop when output passes 100,000 tokens or uncached input passes 40 million. In its own words, crossing a limit asks an attended caller to continue; unattended work cannot wait. Open SWE, LangChain's packaging of the Stripe, Ramp and Coinbase pattern, lists budget limits as a core piece alongside isolated sandboxes and resumable sessions.

Decision 9. What does the factory remember?

Memory across runs is loaded into every station's window, so it must be small. Foreman's factory brain is, in its own description, a short, curated set of durable notes about the target repository, not a transcript of every run. It is size-bounded and kept under a reserved storage prefix that only trusted callers may write, so a malicious issue cannot plant a permanent instruction (Chapter 6, decision 9).

Decision 10. How is the factory itself tested?

Foreman ships eval suites for its pipeline, its routing and its safety: does the right issue reach the right lane, does a stranger's label start nothing, does a red CI on infrastructure stop for a person. The factory is tested like the harness (Chapter 10), because it is one.

4. Factory parts in each harness

Only eve ships a complete factory (Foreman). Each of the others ships parts, and which parts they chose says a lot.

  • Codex has the unattended pieces: exec with JSON and an output schema for CI, a review command against a base branch or commit, and cloud tasks that run in OpenAI's environments. Its flag for running without approvals or sandbox is named to warn and documented as intended solely for environments that are externally sandboxed: the factory, not the agent, must provide the boundary.
  • Claude Code runs headless, and Anthropic's GitHub Actions integration starts it from issue and pull request comments. Its custom agent definitions (tools, model, permission mode, isolation, turn limit) are effectively station definitions.
  • Qwen Code has the most factory-shaped code among the CLIs: an autofix tool that watches a pull request and lets the fix agent run unattended only after the user confirmed that watch; teams with a plan-approval step; worktrees per agent; and GitHub and GitLab channels for intake.
  • Kimi Code has goals with deadlines, cron and a swarm mode: the long-running, scheduled parts of a factory.
  • Trae Agent is a factory of attempts rather than of stations: generate many candidate patches, prune them, and let a selector choose (Chapter 14).
  • Pi, fx and nanocode supply foundations: durable sessions, one-shot JSON modes, embeddable cores and cost accounting.

7. The Chinese view

  • An Aliyun article on the "second half" of coding agents frames Stripe, Ramp and Coinbase converging on one architecture as the move from personal productivity to organisation-level engineering systems, and lists the forcing problems: sandboxes, resumable sessions, many entry points (including Feishu) and budget limits.

8. Build: four stations on your own repo

"""A small software factory: triage -> analyst -> implementer -> reviewer -> draft PR.
Each station is your harness with its own prompt, tools, model and working copy."""
import json, re, subprocess
from pathlib import Path

BRANCH_PREFIX = "factory/"
BRAIN = Path("factory-brain.md")         # short, curated notes about the repo; every run starts from it
BRAIN_MAX_CHARS = 6_000
MAX_REVISIONS = 2

STATIONS = {
    "triage": {"model": "cheap", "tools": ["read", "bash"],
               "system": "Classify the issue. Reply JSON only: {\"lane\": \"ready\"|\"clarify\"|\"reject\", "
                         "\"questions\": [...], \"reason\": \"...\"}. Use 'clarify' if acceptance is unclear."},
    "analyst": {"model": "strong", "tools": ["read", "bash"],
                "system": "Write an implementation plan for the issue. Reply JSON only: {\"plan\": [steps], "
                          "\"acceptance\": [checkable criteria], \"files\": [paths]}. Do not edit files."},
    "implementer": {"model": "strong", "tools": ["read", "write", "edit", "bash"],
                    "system": "Implement the plan in this working copy. Run the repository's own tests and linters "
                              "until they pass. Commit your work. Reply with a short summary."},
    "reviewer": {"model": "other-vendor", "tools": ["read", "bash"],
                 "system": "You review a diff against acceptance criteria. You did not write it and you cannot see "
                           "how it was written. Reply JSON only: {\"verdicts\": [{\"criterion\": ..., \"met\": true|false, "
                           "\"evidence\": \"file:line or command output\"}], \"approve\": true|false}"},
}

def sh(cmd, cwd):
    p = subprocess.run(cmd, shell=True, cwd=cwd, capture_output=True, text=True)
    return p.returncode, (p.stdout + p.stderr).strip()

def parse_json(text):
    m = re.search(r"\{.*\}", text, re.S)
    return json.loads(m.group(0)) if m else {}

def brain():
    return BRAIN.read_text()[:BRAIN_MAX_CHARS] if BRAIN.exists() else ""

def run_factory(issue: dict, repo: str, run_station, log=print):
    """run_station(name, cfg, prompt, workdir) -> final text. Returns a dict describing the outcome."""
    context = f"Repository notes:\n{brain()}\n\nIssue #{issue['number']}: {issue['title']}\n{issue['body']}"

    triage = parse_json(run_station("triage", STATIONS["triage"], context, repo))
    log(f"triage: {triage.get('lane')}")
    if triage.get("lane") != "ready":
        return {"status": triage.get("lane", "clarify"), "questions": triage.get("questions", []),
                "reason": triage.get("reason", "")}

    plan = parse_json(run_station("analyst", STATIONS["analyst"], context, repo))
    criteria = plan.get("acceptance", [])
    log(f"analyst: {len(plan.get('plan', []))} steps, {len(criteria)} criteria")

    branch = f"{BRANCH_PREFIX}{issue['number']}"
    work = str(Path(repo).resolve().parent / f".factory-{issue['number']}")
    _, base = sh("git rev-parse HEAD", repo)                  # review the whole change, not just the last commit
    sh(f"git worktree add -B {branch} {work}", repo)          # the implementer gets its own working copy
    feedback = ""
    for attempt in range(1 + MAX_REVISIONS):
        prompt = f"{context}\n\nPlan:\n{json.dumps(plan, indent=1)}{feedback}"
        run_station("implementer", STATIONS["implementer"], prompt, work)
        _, diff = sh(f"git diff {base} --stat && git diff {base}", work)
        review = parse_json(run_station("reviewer", STATIONS["reviewer"],
                                        f"Acceptance criteria:\n{json.dumps(criteria)}\n\nDiff:\n{diff[:60_000]}", work))
        failed = [v for v in review.get("verdicts", []) if not v.get("met")]
        log(f"review {attempt + 1}: approve={review.get('approve')} failed={len(failed)}")
        if review.get("approve") and not failed:
            return {"status": "ready_for_pr", "branch": branch, "worktree": work, "review": review}
        feedback = "\n\nThe reviewer rejected the last attempt:\n" + json.dumps(failed, indent=1)
    return {"status": "needs_human", "branch": branch, "worktree": work, "review": review}

def open_draft_pr(result, issue, repo):
    """Push only the factory branch, never force, never the default branch; open a draft PR."""
    assert result["branch"].startswith(BRANCH_PREFIX)
    sh(f"git push origin {result['branch']}", result["worktree"])
    body = "Closes #%d\n\nReviewer verdicts:\n%s" % (issue["number"], "\n".join(
        f"- [{'x' if v['met'] else ' '}] {v['criterion']} ({v.get('evidence', '')})" for v in result["review"]["verdicts"]))
    return sh(f"gh pr create --draft --head {result['branch']} --title {json.dumps(issue['title'])} --body {json.dumps(body)}", repo)

Wiring:

  • run_station(name, cfg, prompt, workdir) runs your harness with cfg["system"], cfg["tools"], a model chosen from cfg["model"] and its own session. Use a different provider for the reviewer than for the implementer.
  • Trigger it from the Chapter 12 GitHub channel when an issue gets a factory label from you. Post triage questions back to the issue; on success call open_draft_pr.
  • Point it at this book's repository. Good first issues: fix a typo, add a missing reference, add a test for a build script.

Measure

File 10 small issues. Record for each: lane chosen, revisions used, review verdicts, whether you merged the PR unchanged, and cost. Your merge-unchanged rate is the factory's real score.

9. Exercises

  1. Criteria first. For five real issues, have the analyst write acceptance criteria, then implement. How many pull requests would a reviewer reject against the criteria?
  2. Independent review. Review the same ten diffs with the implementer's model and with a different vendor's model. Count real bugs each finds.
  3. CI classification. Collect 20 red CI runs and label them code, infrastructure, configuration or flaky. Build a classifier and measure how many wasted revisions it would have prevented.
  4. Split sandboxes. Move git credentials into a separate container that only receives bundles. Prove a test that prints the environment finds no token.
  5. Intake policy. Apply the factory label from a non-collaborator account and twice from a collaborator. Exactly one run should start.
