Stage 1 · Foundations · Chapter 0

What an agent harness is

A language model only writes text. Everything that turns that text into work, such as reading files, running commands, remembering, asking permission and checking results, is the harness. This chapter starts from six plain facts about models and the world, derives the harness from them, splits it into eleven components, shows why it matters as much as the model, and introduces the four open-source harnesses we read through the whole book.

Level: beginner to intermediate Time: 4 to 5 hours with the reading lab Needs: basic Python, git Facts checked: 22 Nov 2026
Before you start: skip check

  1. An agent is running a test suite. Which part decides that the test output goes back to the model: the model or the harness?
  2. Name three harness components that exist only because the context window is finite.
  3. Why can the same model get very different scores on the same benchmark?
Answers
  1. The harness. The model only asks for a tool call. The harness runs it, decides how much output to keep, and appends the result to the next request.
  2. Any three of: compaction, tool-output truncation, subagents (isolated context), skills loaded on demand, file-based memory, prompt caching discipline.
  3. Because the score measures model plus harness. Tools, prompts, context management and verification change the result even when the weights do not change.

1. Why a model is not an agent

Forget products and frameworks for a moment and look at what a model call actually is. You send a sequence of tokens. The model computes a probability for every possible next token, samples one, appends it and repeats until it emits a stop token. That is all. Everything else in this book follows from a few plain facts about that process and about the world the agent works in.

Six facts the rest of the book stands on

Fact 1. The model only produces text. It can write rm -rf build/; it cannot run it. Any effect on the world needs code outside the model that reads the text and acts.

Fact 2. The model keeps nothing between calls. The weights are fixed during use. If the model should know something on this call, it must be in this call's input. "Memory" is always the harness resending text.

Fact 3. The input has a hard limit, and quality falls before the limit. The context window caps how much fits. Long before it fills, attention spreads thin and the model starts missing things in the middle.

Fact 4. Every token costs money and time. Input is paid for on every call, again and again. A prefix the provider has already seen can be served from cache far cheaper, but only if it is byte-for-byte the same.

Fact 5. The output is a sample, not a proof. It varies between runs, is sometimes wrong while sounding certain, and is shaped by everything in the input, including text written by an attacker. The model has no built-in way to tell your instructions from a web page's.

Fact 6. The world is stateful, slow and fallible. Commands take minutes, networks fail, processes crash, laptops sleep, and some actions (a sent email, a force-push) cannot be undone.

Put facts 1 and 2 together and you get the first consequence. If the model cannot act and cannot remember, then something must sit between the model and the world: it sends the model a prompt, reads the reply, runs the actions the reply asks for, writes down what happened, and sends the updated record back on the next call. Add facts 3 to 6 and that something must also choose what to show, keep costs down, decide what the model may do, survive crashes and check results. That something is the harness.

A useful way to read every design in this book: ask which fact forced it. A feature that answers none of them is decoration.

The word comes from horse tack: the straps that connect a strong animal to the cart and let a driver steer it. The model provides the power. The harness turns that power into controlled, useful work. Chinese writers use exactly this picture: 马具, horse tack, and translate harness engineering as 驾驭工程, the engineering of driving and controlling.

In 2026 this layer got its own name and its own discipline. Mitchell Hashimoto described the habit that defines it: every time an agent makes a mistake, engineer a permanent fix into its environment so that mistake cannot happen again. OpenAI, Anthropic, LangChain, Cursor and GitHub then published how their own harnesses work. This book builds one.

2. From one call to a loop

Start with the smallest possible agent. It has one tool, bash, and one rule: keep going while the model asks for tools.

def run(task):
    messages = [{"role": "user", "content": task}]
    while True:
        reply = model(messages, tools=[BASH])        # 1. ask the model
        messages.append(reply)
        if not reply.tool_calls:                       # 2. no tool call: done
            return reply.text
        for call in reply.tool_calls:                    # 3. run each tool
            output = run_bash(call.args["command"])
            messages.append(tool_result(call.id, output))  # 4. feed the result back

Why a loop and not a single call? Because of facts 1 and 2. The model needs to see the result of an action before it can choose the next one, and it can only see what the harness sends. So the harness must alternate: ask, act, append, ask again. The message list is the agent's whole working memory, and it grows by one action and one observation per step.

This is the agent loop. It is the ReAct pattern from 2022: reason, act, observe, repeat. Every harness in this book runs a version of it. Thorsten Ball built a working coding agent in 315 lines of Go on this idea, and Chinese analyses note that the innermost loop can be about 200 lines.

The loop is easy. The hard questions start the moment you use it on real work, and each one is a fact pushing back:

  • The test suite prints 40,000 lines. How much goes back to the model? (Facts 3 and 4: every line costs money on every later call and dilutes attention.)
  • After two hours the conversation no longer fits the context window. What do you drop? (Fact 3, and fact 2: whatever you drop, the model has truly forgotten.)
  • The model asks to run rm -rf build/. Do you run it? Who decides? (Facts 5 and 6: the request may be wrong or injected, and the effect may be permanent.)
  • Your laptop sleeps in the middle of a task. Can the agent continue? (Fact 6, and fact 2: the model holds no state, so if the harness did not write it down, it is gone.)
  • The model says "done". How do you know it is true? (Fact 5: a claim is a sample, so only an outside check settles it.)

Every answer is harness code. Community analysis of Claude Code's leaked source estimated that only about 1.6% of it is AI decision logic and 98.4% is operational infrastructure around the loop (Dive into Claude Code). The rest of this book is about that 98%.

3. Definitions we use in every chapter

Definitions

Model: the language model behind an API. Input: a list of messages and tool definitions. Output: text, tool calls, or both.

Harness: all the code, configuration and execution logic that is not the model. LangChain's short version: Agent = Model + Harness, and if you are not the model, you are the harness.

Environment: the world the agent acts on: a file system, a shell, a browser, APIs, a sandbox.

Tool: a named action the harness offers the model, with a description and an input schema, for example read_file(path).

Turn: one user message and all the work it triggers until the agent replies. Step: one model call and the tool calls that follow it. Session: the whole conversation, possibly many turns over days.

Context window: the maximum number of tokens the model can read in one request. Every token in it costs money and attention.

Two neighbouring terms. Prompt engineering asks how to phrase one request. Context engineering asks what the model should see in one window. Harness engineering asks what the whole system should allow, measure and correct across many windows over time. Each layer contains the one before it.

6. Why the harness matters as much as the model

From the facts you can predict this before looking at data. The model only ever sees what the harness chose to send (fact 2), inside a limited window (fact 3), and only acts through the tools the harness offers (fact 1). So the harness controls the model's entire view of the problem and its entire reach. Two harnesses around the same weights are two different agents. The evidence agrees:

  • Same model, better harness. LangChain moved its coding agent from about Top 30 to Top 5 on Terminal Bench 2.0 by changing only the harness; self-verification and tracing helped most (LangChain).
  • Interfaces matter. SWE-agent's custom interface reached 12.5% on SWE-bench at a time when non-interactive approaches were far lower, with the same kind of model (SWE-agent).
  • Harnesses can be searched. Meta-Harness (Stanford, MIT, KRAFTON, 2026) let a coding agent rewrite harness code from raw execution traces, and the discovered harnesses beat hand-built ones while the model weights stayed frozen.
  • Coupling cuts both ways. Claude Code and Codex models are post-trained with their own harness in the loop. A model can underperform in a harness it was not trained with, and changing a tool format such as apply_patch can hurt.
  • Industry scale. Stripe merges over 1,300 pull requests a week written entirely by its unattended agents, with humans reviewing (Stripe). The model is the same one anyone can buy; the harness and environment are Stripe's.
Careful reading

A benchmark score is a property of model, harness, environment and grader together. When you read "model X scores Y", ask which harness produced it. Several 2026 papers make this point directly, for example "Same model, different harness: different coding-agent results" and "What does a harness buy? Tokens, mostly".

7. The four harnesses we read

We read real source code, not marketing pages. The four projects below sit at four corners of the design space. Claude Code and Codex appear as comparison points, because almost every design decision is made in reaction to them.

eve · Vercel · TypeScript

An agent is a directory of files: instructions.md, tools/, skills/, hooks/, channels/, subagents/. The harness kernel does one step and returns { session, next }, and a workflow engine checkpoints every step, so sessions survive crashes and redeploys. Vercel builds its own agents on it. It ships a full software-factory template.

Read: packages/eve/src/harness/kernel.ts

fx · Vercel Labs · Zig

A tiny native coding agent (one binary of about 6 MB) that you script with fx ask, connect to editors over ACP, or embed in apps through libfx. CI fails a change if a benchmarked command takes over 2 ms. Its compaction verifies its own summaries and its safety classifier must quote evidence.

Read: src/core/agent/runtime/orchestrator.zig

Pi and Pi Durable · Earendil · TypeScript

Pi is the minimalist: four core tools, a short system prompt, everything else as extensions, sessions stored as trees. Pi Durable, released with Pi 1.0 in Oct 2026, is a separate library that commits every turn and tool call to storage before anything is shown, so an agent resumes after a crash.

Read: packages/agent/src/agent-loop.ts, packages/durable/docs/spec.md

nanocode · gakonst · Rust

An SDK for embedded agents: one durable runtime that runs the Codex and Claude harnesses with their own pinned prompts and tools. Every model and tool call is journaled. In Code Mode the model writes one program that calls the tools, and only the result enters the context.

Read: crates/README.md, docs/memory-invariant.md

Commits read for this edition: eve 5c52fbf (21 Nov 2026), fx cbe7daf, Pi fb248c7, nanocode 015cbfa (all 22 Nov 2026). All four change weekly; each chapter states the commit it quotes.

8. The design space

Two questions separate most harnesses. How much is built into the core? And does the agent live inside one process, or as a durable service that outlives any process?

The two axes are two facts. Core size is a bet about fact 3: everything built in costs tokens on every call, so a small core keeps the window clear but leaves you to build what is missing. Durability is a bet about fact 6: if crashes and long waits are rare for your users, memory is enough; if they are normal, state must live outside the process. Neither corner is correct. A small core is easy to read, cheap in tokens and easy to bend, but you build safety and planning yourself. Batteries included is safer for most users but hides context you cannot see. A durable service survives crashes and waits days for a human, but every step must be serializable and replay-safe. You will feel each trade-off when you build it.

9. How Chinese teams see the harness

In China the harness became a strategy topic, not just an engineering one. Tencent Cloud's CEO Tang Daosheng wrote that AI has entered "the Harness era", and Alibaba, ByteDance and Tencent each paired a coding tool (Qoder, Trae, CodeBuddy) with a desktop agent and a skills marketplace (36Kr). Three ideas from Chinese writing are worth keeping:

  • Coding builds tools, skills store experience, the harness runs the whole. The harness governs workflow, context, memory, permissions and cost (same source).
  • No model covers every agent scenario. As open Chinese models close the gap with closed ones, harness design becomes the differentiator (Beijing News).
  • Zero-tolerance AGENTS.md. Every rule in your agent instructions must trace back to a real failure; if you cannot name the failure, delete the rule (CSDN). We adopt this rule for our own harness.

Chinese labs also tie model releases to their own harnesses: Alibaba's Qwen Code is a fork of Gemini CLI, Moonshot ships Kimi CLI, and ByteDance ships Trae Agent. Chinese research includes Tsinghua's Natural-Language Agent Harnesses, which writes harness logic as editable natural-language contracts run by a shared runtime. Chapters 4 and 10 return to it.

10. What we build, and how

We build one harness in Python and grow it through five stages. Each stage ends with a gate the harness must pass.

1. Foundations0 to 3: loop, models, toolsA working terminal coding agent
2. Context4 to 6: instructions, compaction, sessionsSessions that last hours and resume
3. Control7 to 10: safety, extensions, subagents, evalsA governable agent
4. Durability and surfaces11 to 12Survives kill -9 mid-task
5. Software factory13 to 15Issue in, draft pull request out

Every chapter has the same five parts: the concept, derived from the six facts above; a code tour of eve, fx, Pi and nanocode; a design-decision table with reasons and trade-offs; what research and Chinese teams say; and the build. Three rules guide the build:

  1. Shape the loop for durability from day one. In Chapter 1 the loop body becomes a function step(state) → (state, next), the shape eve uses, so Chapter 11 can make it durable without a rewrite.
  2. Measure every change. From Chapter 1, a small set of test tasks runs every week. A change that does not move a number is a guess.
  3. Every rule traces to a failure. We add harness features when the agent fails without them, not because another product has them.

Step 4. Answer three questions

  1. Which of the four loops would lose the current turn if the process crashed? Why?
  2. In Pi, what are the two reasons the inner loop continues?
  3. In eve, what does the kernel return instead of looping?
Answers
  1. Pi's CLI loop and fx keep the turn in memory, so a crash loses it (Pi Durable and nanocode exist to fix exactly this). eve checkpoints each step in a workflow; nanocode journals every call.
  2. More tool calls to run, or pending steering messages that the user typed while the agent worked.
  3. { session, next }: the updated session and the next step function, or next: null when the turn ends. The workflow engine calls next, which is what makes each step a checkpoint.
