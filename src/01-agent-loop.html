The agent loop

The loop exists because the model can neither act nor remember (facts 1 and 2 from Chapter 0), so something has to alternate between asking it and acting for it. It is the smallest part of a harness and the one every other part plugs into. This chapter shows how four harnesses shape it, why eve does not loop at all, and how the shape you choose today decides whether your agent can become durable later. You end the chapter with a working 120-line agent and a baseline score.

Before you start: skip check
  1. What is the difference between a turn and a step?
  2. A user types a correction while the agent is running tools. When should the model see it?
  3. Why would you write the loop body as a function that returns the next state instead of a while loop?
Answers
  1. A turn is one user message and all the work until the agent replies. A step is one model call plus the tool calls it asked for. A turn has one or more steps.
  2. Before the next model call: queue it, and deliver it at the next step boundary (this is "steering").
  3. Each return is a natural checkpoint. You can save the state, crash, and continue from the last step. That is how eve becomes durable.

1. Turn, step, run, session

Start from fact 2: the model is stateless, so the only state an agent has is the message list the harness keeps. That list changes at exactly one kind of moment: after the model replies and its tool calls have run. Between those moments nothing new exists. So the natural unit of an agent is that change, and every other unit is a group of them. This is why harnesses save, resume and accept new input at these boundaries and nowhere else, and why the words need to be exact.

Definitions

Step: one model call plus the tool calls it asks for. The smallest unit that changes the conversation.

Turn: one user input and every step it triggers until the model answers without a tool call.

Run: Pi Durable's word for the steps from one admitted input to the final answer, possibly including follow-up input that arrived meanwhile.

Session: all turns of one conversation. It can span days.

Steering message: user input that arrives while a turn is running. Follow-up message: input that arrives just as the agent was about to stop.

2. What the loop must decide

The toy loop from Chapter 0 hides six decisions. You can derive each one, and the reasonable answers, from the facts.

  1. When to stop. The only signal the model can give is text, so "I am done" is a reply with no tool call. But that signal is a sample (fact 5): the model can stop too early or never stop. So the harness needs its own limits it does not delegate to the model: step limits, token budgets, cancellation, and stop hooks that check the world (for example "tests still fail") before accepting the stop.
  2. How to run several tool calls. A model can ask for five reads at once. Tools act on a stateful world (fact 6). Reads do not change it, so their order does not matter and running them in parallel only saves time. Writes do change it, so two writes to one file must run in order. The rule follows: parallel by default, sequential when tools share state.
  3. When new user input is seen. The model reads its input once, at the start of a call (fact 2). A message that arrives mid-call cannot reach it until the next call. So the only real choice is between cancelling the current step or queueing the message for the next step boundary.
  4. What happens between steps. The step boundary is the only moment the message list is complete and consistent, so it is the only safe moment to rewrite it. Compaction, model switches, context updates and checkpoints all happen here for that reason.
  5. Where state lives. All state is the message list plus side effects in the world. Processes crash (fact 6). If the list is only in memory, a crash erases the agent's entire mind, while the world keeps the half-finished changes. Writing it down after every step costs a little; not writing it down costs the whole turn.
  6. Who calls whom. If the loop owns the while, the process must stay alive until the turn ends. If an outside engine calls one step at a time and saves between calls, no single process has to live that long. This choice decides whether durability is easy later.

3. Three loop shapes

4. Code tour

Pi: two nested loops with queues

Open packages/agent/src/agent-loop.ts (952 lines) and find runLoop(). The outer while (true) exists only for follow-up messages: when the agent would stop, it asks getFollowUpMessages() and continues if any arrived. The inner loop runs while (hasMoreToolCalls || pendingMessages.length > 0). Steering messages are polled at the start and after each turn preparation, and injected before the next model call, never in the middle of one.

Between turns, two hooks run: prepareNextTurn (can return a new context, new model or thinking level, which is how compaction and model switching plug in) and prepareRequest (last change before the call). Tool calls run in parallel by default; executeToolCalls() switches to sequential if the config says so or if any tool in the batch declares executionMode: "sequential". That per-tool flag is a nice detail: a file-mutation tool can force order without slowing down a batch of reads.

eve: no loop, a kernel

Open packages/eve/src/harness/kernel.ts. createKernel() returns runStep(session, input). One call runs a fixed sequence of stages in runStages(): settle runtime results (finished tasks, subagents), admit human answers (approvals), prepare turn input, run hook effects, apply human decisions, then either park (wait for a human), settle the turn, or call runModelStep. It returns { session, next }. The Workflow SDK calls next in a new durable step. A step is by default one model call plus its inline tool calls; the experimental workflow.modelCallsPerStep groups several cycles to cut checkpoint overhead, at the cost of a bigger replay unit.

Look at how many stages are about humans and background work: approvals, parked work, queued input, running tasks. A durable loop spends most of its code on waiting correctly.

fx: a native orchestrator with a step limit

fx's loop lives in src/core/agent/runtime/orchestrator.zig, with parallel_execution.zig and tool_batch.zig for tool batches and interruption.zig for cancel. config.zig defines an agent_step_limit and the message the model receives when it is hit: "Agent step limit reached; continue with a follow-up prompt if needed." Subagents get their own, smaller limit (src/core/subagent/agent_adapter.zig). The loop also warms the provider cache (cache_warmer.zig), because a native binary that starts in microseconds should not then wait on a cold prompt cache.

nanocode: a runtime with an inbox and a log

In crates/runtime/agent/src, turn_inbox.rs receives prompts and steering, turn_log.rs and session_log.rs record every event, and runtime.rs drives turns. Steering has a receipt status, so the caller knows whether a message was accepted into the running turn. The design goal is stated in the README: every model call and tool call is journaled, so a turn finishes after its process dies.

Codex: one turn loop, steering drained at the step boundary

Codex's loop is run_turn() in codex-rs/core/src/session/turn.rs (about 4,000 lines). Its doc comment states the contract: each sampling request returns function calls or an assistant message; a call is executed and its output sent back on the next request; a message with no calls ends the turn. At the top of every iteration the loop drains sess.input_queue, so text the user typed while the model was working is recorded before the next request, never pushed into one already in flight (fact 2 in action). It then captures a step context once, with the comment "Capture once so context, advertised tools, and tool calls share one request view": the tools the model was offered and the tools that run cannot drift apart inside a step. After sampling it measures the context window and may start background compaction, tagged MidTurn if the model still needs a follow-up and PostTurn if not. Stop hooks run in completion_hooks.finish() before the turn returns.

Claude Code: an async generator shared by every surface

Claude Code's source is not public; the description here comes from the source-level study Dive into Claude Code (arXiv 2604.14228), which analysed v2.1.88. The loop, queryLoop(), is an AsyncGenerator that yields streaming events, and the CLI, the SDK and the IDE extensions all consume that one generator. The paper describes a nine-step pipeline per iteration (settings, state, context assembly, context management, model call, tool dispatch, permission gate, tool execution, stop check) and five stop conditions: no tool use, max turns, context overflow, hook intervention and explicit abort. A StreamingToolExecutor starts running tools while the reply is still streaming, a latency optimisation that only works because tool calls arrive as complete blocks before the reply ends.

Kimi Code: an event-sourced loop actor

Moonshot's Kimi Code CLI keeps its loop in packages/core/src/loop/. The loop is an actor (loop-actor.ts, about 1,750 lines) whose state is a projection of recorded events. record.ts lists what is persisted: turn.started, step.started, message.appended, tool.started, tool.ended, llm.retry and others, and a reducer rebuilds state from them. This is fact 2 taken literally: since the model holds nothing, the harness treats its own log as the agent's memory and derives everything else. state.ts decides whether an interrupted turn can continue: isResumable() finds the last assistant message and checks for tool calls with no result. Step limits are not built into the loop; createMaxStepsHook() is a blocking hook on the step.continuing point.

Qwen Code: named stop reasons and loop detection

Alibaba's Qwen Code keeps its loop in packages/core/src/core/agent-loop.ts. Its AgentLoopStopReason type names every way a loop can end, including completed, cancelled, loop_detected, duplicate_provider_call, tool_ended_turn, max_session_turns, session_token_limit and user_prompt_blocked. client.ts caps a turn at MAX_TURNS = 100. services/loopDetectionService.ts watches for a model stuck repeating itself: 5 identical tool calls in a row, a content chunk repeated 10 times, the same file read 8 times. The comment above the first threshold is first-principles reasoning in one line: repeating an identical call yields an identical result, so it is never productive.

Trae Agent: the research baseline

ByteDance's Trae Agent has the simplest loop in this book. trae_agent/agent/base_agent.py runs while step_number <= self._max_steps (200 in the example config). A turn ends only when the model calls the task_done tool, whose description says it cannot be called before verification. With must_patch set, trae_agent.py also takes the git diff, removes changes to tests, and if nothing is left it rejects the stop with "ERROR! Your Patch is empty." That is fact 5 handled in the loop: the model's claim that it is finished is checked against the world before it is accepted.

Why this matters later

From fact 2, the agent's true state is small: the message list and a few counters. Any state the loop holds outside that object (an open file handle, a half-streamed reply, a background process) is state the model never sees and a crash will lose. Making an in-memory loop durable after the fact is hard because you have to discover all of that hidden state one bug at a time. Writing the loop body as step(state) → state from the start forces all state into one object you can save. We do that now, and Chapter 11 adds the journal.

6. Research and how Chinese teams see the loop

  • ReAct (2022) introduced interleaving reasoning, action and observation. Every loop here is ReAct plus engineering.
  • The Ralph loop: when the model tries to stop, a hook re-injects the original goal into a fresh context window; files carry state between iterations. LangChain describes it as a harness pattern for long goals.
  • Loop engineering is the 2026 name for designing the outer loops that re-drive agents, one layer above harness engineering.
  • Chinese view. Chinese analyses stress that the innermost loop can be about 200 lines and that the hard part is everything around it (36Kr). Practitioner write-ups describe the loop's job as mediating observation, action, feedback and completion (Jimmy Song).

7. Build: a 120-line agent with a step function

We use the openai Python SDK because almost every provider (OpenAI, OpenRouter, Ollama, vLLM, most Chinese labs) offers an OpenAI-compatible endpoint. Chapter 2 replaces it with our own provider layer.

pip install openai
export BASE_URL=...   # any OpenAI-compatible endpoint; leave unset for OpenAI
export API_KEY=...
export MODEL=...
import json, os, subprocess
from dataclasses import dataclass, field
from openai import OpenAI

client = OpenAI(base_url=os.getenv("BASE_URL"), api_key=os.getenv("API_KEY"))
MODEL = os.getenv("MODEL", "gpt-5-mini")
SYSTEM = "You are a coding agent. Use the tools to inspect and change files. Be brief."

def tool(name, desc, props, required):
    return {"type": "function", "function": {"name": name, "description": desc,
            "parameters": {"type": "object", "properties": props, "required": required}}}

TOOLS = [
    tool("read", "Read a text file.", {"path": {"type": "string"}}, ["path"]),
    tool("write", "Create or overwrite a file.", {"path": {"type": "string"}, "content": {"type": "string"}}, ["path", "content"]),
    tool("edit", "Replace exact text in a file. old must appear exactly once.",
         {"path": {"type": "string"}, "old": {"type": "string"}, "new": {"type": "string"}}, ["path", "old", "new"]),
    tool("bash", "Run a shell command and return its output.", {"command": {"type": "string"}}, ["command"]),
]

def run_tool(name, args):
    try:
        if name == "read":
            return open(args["path"]).read()[:20_000]
        if name == "write":
            os.makedirs(os.path.dirname(args["path"]) or ".", exist_ok=True)
            open(args["path"], "w").write(args["content"])
            return f"wrote {len(args['content'])} chars"
        if name == "edit":
            text = open(args["path"]).read()
            if text.count(args["old"]) != 1:
                return f"error: old text found {text.count(args['old'])} times, need exactly 1"
            open(args["path"], "w").write(text.replace(args["old"], args["new"]))
            return "edited"
        if name == "bash":
            p = subprocess.run(args["command"], shell=True, capture_output=True, text=True, timeout=120)
            out = (p.stdout + p.stderr)[-20_000:]
            return f"{out}\n[exit code: {p.returncode}]"
        return f"error: unknown tool {name}"
    except Exception as e:
        return f"error: {e}"

@dataclass
class State:
    messages: list
    steps: int = 0
    done: bool = False
    steering: list = field(default_factory=list)  # messages typed while the agent works

def step(state: State, max_steps: int = 50) -> State:
    """One unit of work: one model call plus the tool calls it asks for."""
    if state.steering:                       # deliver queued user messages first
        state.messages += [{"role": "user", "content": m} for m in state.steering]
        state.steering.clear()
    reply = client.chat.completions.create(model=MODEL, messages=state.messages, tools=TOOLS).choices[0].message
    state.messages.append(reply.model_dump(exclude_none=True))
    state.steps += 1
    if not reply.tool_calls:                 # no tool call: the turn is over
        state.done = True
        return state
    for call in reply.tool_calls:
        output = run_tool(call.function.name, json.loads(call.function.arguments or "{}"))
        state.messages.append({"role": "tool", "tool_call_id": call.id, "content": output})
    if state.steps >= max_steps:             # the harness, not the model, enforces limits
        state.messages.append({"role": "user", "content": "Step limit reached. Summarize and stop."})
    return state

def run(task: str) -> str:
    state = State(messages=[{"role": "system", "content": SYSTEM}, {"role": "user", "content": task}])
    while not state.done:
        state = step(state)
    return state.messages[-1].get("content", "")

if __name__ == "__main__":
    import sys
    print(run(" ".join(sys.argv[1:])))

Four design choices in this code, each taken from the code tour:

  • step() is the unit. It does one model call and its tools, and returns the state. run() is a thin driver, the role eve gives its workflow engine.
  • Steering waits for a step boundary, as in Pi. Never inject input in the middle of a tool batch.
  • Errors are results, not exceptions. A failed tool returns text that starts with error:, so the model can recover. Manus keeps failed actions in context for the same reason.
  • The harness enforces the step limit and tells the model, as fx does. The model never decides its own budget.
Safety for this week

This agent runs any shell command with your permissions. Run it inside a container or a throwaway VM (docker run -it -v $PWD:/work python:3.12 bash). Chapter 7 adds real permissions and a sandbox.

Your first test tasks

Make a small scratch repository and write 10 tasks the agent must do in it. Each task needs an automatic check, usually a test that passes only when the task is done. Examples:

  1. A function has an off-by-one bug; a failing test shows it. Fix it.
  2. Rename get_user to fetch_user everywhere.
  3. Add a --verbose flag to the CLI.
  4. Add type hints to one module without changing behaviour.
  5. Write a test for an untested function.
  6. Fix an import error after a file was moved.
  7. Make a slow function 10x faster (a timing test checks it).
  8. Update a README section to match the code.
  9. Add input validation that raises ValueError.
  10. Find and remove dead code that a test proves is unused.

Run all 10, reset the repo with git checkout . between tasks, and record: tasks passed, total steps, total tokens. That is your baseline. Every later chapter reports against it.
