Capstone: benchmark and retrospective

Sixteen weeks ago the loop was a page of code. Now it has a provider layer, typed tools, cache-stable context, compaction, session trees, a safety gate, skills and hooks, subagents and Code Mode, evals, durability, a server, channels and a factory. This chapter does three things. It measures your harness honestly against the reference harnesses on the same tasks. It pulls the whole book together: one profile per harness, one map of every decision, and a guide to choosing which kind of harness to build. And it closes with a retrospective and a release checklist for version 1.0.

Level: advanced Time: about 20 hours Needs: all earlier chapters Facts checked: 24 Nov 2026

1. Why compare against real harnesses

Your weekly eval tells you whether your harness improved. It does not tell you whether it is good. A pass rate is produced jointly by the model, the harness and the tasks, and the model's output varies from run to run (fact 5). To learn what the harness contributes, hold the other two fixed and repeat enough to see through the noise.

Safety

Pi has no permission gate, fx can run with full access, and the flags in the runner below switch off the gates of Codex, Claude Code, Kimi Code and Qwen Code. Run every harness in this chapter inside a container with only the task's copy of the repository mounted (Chapter 7).

2. Method

Use the same model for every harness where possible (Pi supports most providers; fx talks to one provider at a time through a gateway, a subscription or any OpenAI-compatible endpoint), then repeat with each harness's preferred model. The second run matters: Chapter 2 showed that models trained inside a harness behave best with its prompts and tool names, so a "same model" comparison can understate a vendor harness.

3. The nine harnesses at a glance

Each profile names the harness's central idea and its signature answer in each part of the book. Together they are the holistic view: nine coherent sets of trade-offs, not a ranking.

5. Choosing what kind of harness to build

Whichever you choose, five decisions are hard to change later and should be settled first: the log format (Chapter 6), whether effects are journaled (Chapter 11), where the safety boundary is (Chapter 7), how context changes are delivered (Chapter 4), and whether the core sits behind a session API (Chapter 12). Everything else can be added when its absence costs you.

6. The Chinese view, across the book

  • Kimi Code is the purest event-sourced design read for this book, with the best compaction prompt and the clearest tool descriptions about the cost of delegation.
  • Qwen Code shows that borrowing a proven design is a strategy: Claude Code's thresholds and hook names, Gemini CLI's context files, then real investment where its users differ (CJK token counts, Chinese workplace channels, a DashScope search backend, other harnesses as subagents).
  • Trae Agent shows that a small harness is the right instrument for research, and that breadth can come from many attempts plus a selector.
  • Practice. Zero-tolerance AGENTS.md, "harness is the new dataset", semantic gradient descent, and skills marketplaces from Alibaba, ByteDance and Tencent: Chinese teams treat the harness, not the model, as where most competition now happens.

7. Build: the comparison runner

"""Capstone: run three harnesses headless on the same tasks, same model where possible, and compare."""
import json, shutil, subprocess, sys, tempfile, time
from pathlib import Path

# Each harness is a command that takes the prompt as its last argument and works in the current directory.
# Run every one of them inside a container (Chapter 7): fx in full-access mode and Pi have no gate.
HARNESSES = {
    "mine": ["harness", "ask", "--json"],          # your CLI from Chapter 12
    "pi":   ["pi", "--print"],                     # Pi's non-interactive mode
    "fx":   ["fx", "ask", "--json"],               # fx's scripting mode; final answer in .final_output
    # reference harnesses: run them only inside a container, since these flags remove their gates
    "codex": ["codex", "exec", "--json", "--dangerously-bypass-approvals-and-sandbox"],
    "claude": ["claude", "-p", "--output-format", "json", "--dangerously-skip-permissions"],
    "kimi":  ["kimi", "-p"],                     # non-interactive runs use auto permission
    "qwen":  ["qwen", "--approval-mode", "yolo", "-p"],
    "trae":  ["trae-cli", "run", "--working-dir", "."],
}

def run(harness, cmd, task, repo, timeout=1800):
    work = Path(tempfile.mkdtemp(prefix=f"cap-{harness}-{task['id']}-"))
    shutil.copytree(repo, work, dirs_exist_ok=True)
    t0 = time.time()
    try:
        p = subprocess.run(cmd + [task["prompt"]], cwd=work, capture_output=True, text=True, timeout=timeout)
        out, err = p.stdout[-4000:], p.returncode
    except subprocess.TimeoutExpired:
        out, err = "timeout", -1
    passed = subprocess.run(["bash", str(task["check"])], cwd=work, capture_output=True).returncode == 0
    shutil.rmtree(work, ignore_errors=True)
    return {"harness": harness, "task": task["id"], "pass": passed, "secs": round(time.time() - t0, 1),
            "exit": err, "output_tail": out[-300:]}

def main(tasks_dir, repo, repeats=3, out="capstone.json"):
    tasks = [{"id": d.name, "prompt": (d / "prompt.md").read_text(), "check": d / "check.sh"}
             for d in sorted(Path(tasks_dir).resolve().iterdir()) if (d / "prompt.md").exists()]
    rows = [run(h, cmd, t, repo) for t in tasks for h, cmd in HARNESSES.items() for _ in range(repeats)]
    Path(out).write_text(json.dumps(rows, indent=1))
    print(f"{'harness':8} {'pass rate':>9} {'mean secs':>9}")
    for h in HARNESSES:
        r = [x for x in rows if x["harness"] == h]
        print(f"{h:8} {sum(x['pass'] for x in r) / len(r):9.0%} {sum(x['secs'] for x in r) / len(r):9.1f}")

if __name__ == "__main__":
    main(*sys.argv[1:3])

Run it as python capstone.py tasks/ scratch-repo/. Add token and cost columns where a harness reports them (your own harness and fx's JSON output; Pi's session files record usage).

10. Lessons the harnesses teach

  • Pi: a small core you can read in an afternoon beats a large one you cannot. Add a feature when its absence costs you, not before.
  • Pi Durable: write the specification before the code when correctness is hard. The effect sandwich fits on a napkin and prevents a class of bugs.
  • eve: shape the loop for durability from day one, and keep secrets out of the place where the model's commands run.
  • fx: treat your own outputs as untrusted. Check summaries against the record and make the safety reviewer prove its claims.
  • nanocode: respect each model's native harness, and state your invariants as numbers you can test.
  • Codex: separate what is possible from when to ask, enforce the first in the operating system, and test your rules like code.
  • Claude Code: order your defences from cheapest to most lossy, and never rewrite the record; patch the view when it is read.
  • Kimi Code: make the log the truth and everything else a projection, then tell the model where the log is.
  • Qwen Code: converge on what works and spend your effort where your users differ.
  • Trae Agent: a stable harness is the right instrument for experiments, and breadth can come from many attempts plus a good selector.

11. Release checklist for v1.0

  • README with a 60-second quick start, the results table and a link to this book.
  • A container image that runs the harness safely by default.
  • The eval suite and holdout in the repo, with instructions to reproduce your numbers.
  • An AGENTS.md where every rule names the failure that created it.
  • A tagged release and a final post: what you built, what it scores, what you would do differently.

12. Where to go next

  • Contribute one fix upstream to Pi, fx, eve, nanocode, Codex, Kimi Code, Qwen Code or Trae Agent, in a component you now understand deeply.
