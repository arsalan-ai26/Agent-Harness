Context management and compaction

The window is finite (fact 3) and every step appends to it, so every long session eventually fills it. Compaction replaces old turns with a summary so the agent can keep working. It is also where harnesses quietly lose information. This chapter reads four real compactors with their exact thresholds, shows why fx verifies its own summaries and why Pi Durable compacts in the background, then builds a compactor with turn handles, a lint pass and recallable raw history.

Level: intermediate to advanced Time: about 20 hours with the build Needs: Chapters 2 and 4 Code read at: Pi fb248c7, eve 5c52fbf, fx cbe7daf, nanocode 015cbfa
Before you start: skip check
  1. Why not simply drop the oldest messages when the window is full?
  2. A summary says "tests passed in step 14", but they never did. How could the harness catch that?
  3. Why must compaction never split a tool call from its tool result?
Answers
  1. The oldest messages usually hold the goal and the user's constraints. Dropping them loses the task; summarizing keeps the meaning.
  2. Give every turn and tool call a handle, ask the summary to cite handles, and check that each cited handle exists and supports the claim (fx's lint pass).
  3. Providers reject histories with a tool result whose call is missing, or a call with no result. The kept tail must start at a clean boundary.

1. The problem

Do the arithmetic first. Each step appends a model reply and a tool result, and the next step resends everything (fact 2). If a session has n steps of roughly equal size, the total tokens sent are about 1 + 2 + ... + n, which grows with n². Manus measured about 50 tool calls per task and about 100 input tokens for every output token, which is exactly what that arithmetic predicts. Long before the hard limit, a second effect hits: attention is spread over every token in the window, so the more irrelevant tokens there are, the less weight the relevant ones get (often called context rot).

So the window is a budget, and there are only two ways to stay inside a budget: spend less, or throw some away. Throwing away is dangerous because of fact 2: whatever leaves the window, the model has truly forgotten, and it does not know that it has forgotten. That gives the order of preference. The harness has four tools, in rising order of what is lost:

  1. Bound tool output at the source (Chapter 3: 2,000 lines or 50 KB, full output saved to a file).
  2. Offload: keep large content in files and keep only the path in context (Manus calls this restorable compression).
  3. Isolate: do exploration in a subagent and bring back only its conclusion (Chapter 9).
  4. Compact: summarize old turns into a checkpoint and keep a recent tail word for word.

eve: compaction with a size contract

eve measures size against the provider's last reported input tokens plus an estimate for new messages, and scales its character estimate by the ratio between the two (DEFAULT_ESTIMATE_RATIO = 1.6 until calibrated). The summary prompt separates completed progress and decisions from remaining work and keeps constraints, preferences, data and references. A later compaction passes the previous summary in full and replaces it. Memory stays outside history, so the summarizer never sees it. If instructions, tools and memory alone do not fit, eve does not call the provider at all; the turn fails with COMPACTION_FAILED.

fx: compaction you can check

The header of src/core/compactor/compactor.zig lists the pipeline: window.zig chooses what to compact; summarize.zig keeps user messages and final replies exact and gives every turn and tool call a handle; ledger.zig asks the model for notes; lint.zig checks every note against the saved turns and marks what it cannot confirm; model.zig calls the conversation's model at its lowest reasoning with a fallback; records.zig saves the records and searches them. Manual /compact, automatic compaction and provider-overflow recovery all use the same path.

Pi Durable: compaction that does not block

Spec section 8.7 defines three starts: a manual Conversation.compact(), a background start above one threshold, and a blocking start above a higher threshold or on overflow. Only the blocking one makes the run wait. Background summaries are placed like any passive write at a turn boundary, and several compactions may run at once. Raw history always stays in storage; the summary entry just marks the first kept entry as its head.

Codex: 90% by default, a handoff prompt, and compaction in the background

Codex compacts when the context passes auto_compact_token_limit(), which in protocol/src/openai_models.rs is 90% of the model's window unless configured lower. The local compactor's prompt (prompts/templates/compact/prompt.md) asks for a "handoff summary for another LLM that will resume the task": progress and decisions, constraints and preferences, what remains, and the data needed to continue. The summary is then introduced to the next call with a prefix that frames it as another model's work, so the model builds on it instead of repeating it. Recent user messages are kept up to 20,000 tokens. For providers that support it, Codex can ask the server to compact (compact_remote_v2.rs), with a 64,000-token budget for retained messages. An experimental async mode starts a speculative compaction in the background at 65% of the window, so the summary is ready when the limit arrives instead of blocking the user.

Claude Code: five stages, cheapest first

The paper's best single lesson on compaction: Claude Code does not have one compactor but five stages, applied in order before a model call, each under its own conditions. Budget reduction caps the size of individual tool results; snip trims older history; microcompact clears old tool results; context collapse is a non-destructive projection applied when the context is read, not written; auto-compact asks the model for a summary. The order follows the cost of being wrong: each stage loses more than the one before. Compact boundaries are recorded in the transcript, and the loader patches the message chain at read time, so nothing on disk is rewritten.

Kimi Code: compaction that tells the model where the raw log is

Kimi Code's defaults are in agent/fullCompaction/strategy.ts: compact at 85% of the window, or earlier if the remaining space would drop under a 50,000-token reserve; keep the last 4 messages, up to 20% of the window; try at most 3 times on overflow. The instruction (compaction-instruction.md) is one of the best in any harness. It asks for the summary in the conversation's language, exact commands, paths and results rather than descriptions of them, decisions kept separate from open questions, an explicit list of what is still unknown, and a careful forward plan, because "right now you hold more context on this task than you ever will again". Then context-recovery-footer.md tells the model that everything compacted is still on disk in an append-only wire.jsonl, and how to grep it. That turns lossy compaction into lossless compaction plus a cache, which is the design our build uses.

Kimi's archived Python CLI tried something more radical, still worth knowing: a SendDMail tool (named after Steins;Gate) let the model revert its own context to an earlier checkpoint and leave itself a note with only the useful result. The model, not the harness, decided what to forget.

Qwen Code: Claude Code's numbers, plus CJK

services/chatCompressionService.ts compacts at 85% (DEFAULT_PCT) and reserves 20,000 tokens for the summary. Its buffers (13,000 tokens before the window for auto-compaction, 20,000 for a warning, 3,000 hard) are documented in the comments as matching Claude Code's. After 3 consecutive failures a circuit breaker stops trying. The summary is an XML <state_snapshot> written after an <analysis> block, a format inherited from Gemini CLI. One detail no Western harness has: the token estimator counts CJK characters as 1.5 tokens, because Chinese text tokenizes differently and a count based on characters per token would underestimate it.

Trae Agent: none

Trae Agent does not compact. It clips tool output at 16,000 characters and relies on the 200-step cap and a large window. For short benchmark tasks that is enough, and it keeps experiments free of a lossy step.

4. Research and the Chinese view

  • Externalize memory. Anthropic's long-running harness has each session read a progress file and git log instead of relying on a summary. Chinese readings of that post put it bluntly: the context window is not reliable memory; reliable memory must be externalized (CSDN).
  • Restorable compression. Manus drops a page's content but keeps its URL, or a file's content but keeps its path, so nothing is truly lost (Manus).
  • Long-horizon harness work. Alibaba's DreamX team's LongHorizon-Harness asks how much long-task performance changes when only the harness changes; compaction policy is a major lever.

5. Build: a compactor with handles, lint and recall

"""Compaction: summarize old turns into a checkpoint, keep a verbatim tail, keep raw history recallable."""
import json, re

THRESHOLD = 0.85          # compact at 85% of the window (fx: 80%, eve: 90%)
TARGET = 0.5              # after compaction, the request must fit in half the window (eve)
KEEP_TAIL_TOKENS = 20_000 # recent messages kept word for word (eve, Pi)
TAIL_TOOL_CHARS = 2_000   # tool results inside the kept tail are shortened (eve)

class TokenEstimator:
    """chars / 4, corrected by the provider's reported input tokens (eve's ratio trick)."""
    def __init__(self):
        self.ratio = 1.0
    def raw(self, messages):
        return sum(len(json.dumps(m, default=str)) for m in messages) / 4
    def calibrate(self, messages, reported_input_tokens):
        est = self.raw(messages)
        if est > 0 and reported_input_tokens:
            self.ratio = reported_input_tokens / est
    def __call__(self, messages):
        return int(self.raw(messages) * self.ratio)

SUMMARY_PROMPT = """You are writing a checkpoint so another engineer can continue this task with no other context.
Every message has a handle M<n>; every tool call has a handle T<n>. Write these sections:
## Goal - the user's request, in their words where possible.
## Done - completed steps and decisions, each citing the handles it rests on, e.g. (M3, T7).
## Remaining - what is left, in order.
## Facts - file paths, commands, constraints and preferences needed to continue, each with a handle.
Cite only handles that appear in the transcript. Do not invent results."""

def with_handles(messages):
    """Give every message and tool call a stable handle, as fx does (M1, T1, ...)."""
    lines, t = [], 0
    for i, m in enumerate(messages, 1):
        body = m.get("content") or ""
        for c in m.get("tool_calls", []) or []:
            t += 1
            body += f"\n[T{t}] {c.name}({json.dumps(c.args)[:300]})"
        lines.append(f"[M{i}] {m['role']}: {str(body)[:4000]}")
    return "\n".join(lines), len(messages), t

def lint(summary, n_messages, n_tools):
    """Flag summary lines that cite handles which do not exist (fx's lint pass)."""
    bad = [h for h in re.findall(r"\b([MT])(\d+)\b", summary)
           if int(h[1]) < 1 or int(h[1]) > (n_messages if h[0] == "M" else n_tools)]
    cited = len(re.findall(r"\b[MT]\d+\b", summary))
    return {"bad_handles": [f"{a}{b}" for a, b in bad], "cited": cited}

def split_tail(messages, estimate):
    """Keep the newest messages up to KEEP_TAIL_TOKENS. Never split a tool call from its results."""
    kept, total = [], 0
    for m in reversed(messages):
        total += estimate([m])
        if total > KEEP_TAIL_TOKENS and kept:
            break
        kept.insert(0, m)
    while kept and kept[0]["role"] == "tool":          # a tail may not start with orphaned tool results
        kept.pop(0)
    old = messages[: len(messages) - len(kept)]
    tail = [dict(m, content=m["content"][:TAIL_TOOL_CHARS] + "\n[shortened]")
            if m["role"] == "tool" and len(m.get("content", "")) > TAIL_TOOL_CHARS else m for m in kept]
    return old, tail

def maybe_compact(state, window, estimate, summarize, archive):
    """summarize(prompt, transcript) -> str uses a cheap model. archive(messages) stores raw history.
    Returns True if the history was compacted."""
    if estimate(state.messages) < THRESHOLD * window:
        return False
    old, tail = split_tail(state.messages, estimate)
    if not old:
        return False
    archive(old)                                       # raw history stays recoverable (Pi Durable, fx)
    transcript, n_m, n_t = with_handles(old)
    previous = state.checkpoint or ""
    summary = summarize(SUMMARY_PROMPT, (f"Previous checkpoint:\n{previous}\n\n" if previous else "") + transcript)
    report = lint(summary, n_m, n_t)
    if report["bad_handles"]:
        summary += f"\n\n[warning: these cited handles do not exist and may be wrong: {', '.join(report['bad_handles'])}]"
    state.checkpoint = summary
    state.messages = [{"role": "user", "content": f"<checkpoint>\n{summary}\n</checkpoint>\n"
                       "Older turns were summarized above; the raw history is available with the recall tool."}] + tail
    if estimate(state.messages) > TARGET * window:     # tail too big: keep only its text
        state.messages = state.messages[:1] + [m for m in tail if m["role"] != "tool"][-4:]
    return True

Wiring:

  • After every model call, call estimator.calibrate(messages, reply.input_tokens).
  • Before every model call, call maybe_compact(state, window, estimator, summarize, archive). summarize calls a cheap model with the prompt and transcript. archive appends the raw messages to session-archive.jsonl.
  • Add a recall(handle_or_query) tool that searches the archive, so the agent can read what the checkpoint left out.

Measure

  1. Create one long task (for example a 3-hour refactor across 15 files) that needs at least two compactions. Record whether it finishes, how many lint warnings appear, and whether the agent used recall.
  2. Run it with the threshold at 0.8 and at 0.9. Compare completion and total tokens.
  3. Read one checkpoint and mark every claim as true or false against the transcript. That number is your summary accuracy.
