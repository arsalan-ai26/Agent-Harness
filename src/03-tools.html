Tools and the action interface

The model only writes text (fact 1). A tool is a contract that says which text the harness will turn into which action, so their design decides what the agent can do, how often it fails, and how many tokens it burns. This chapter compares Pi's four tools, fx's toolbox with capability search, eve's sandboxed built-ins and nanocode's Code Mode, then builds a typed tool registry with validation, truncation, safe multi-edits and background jobs. It closes Stage 1: your harness is now a real coding agent.

Before you start: skip check
  1. Why does Pi's edit tool require each old text to be unique in the file?
  2. A test command prints 80,000 lines. What should the model see?
  3. What is the difference between listing all tools and tool search?
Answers
  1. If the text appears twice, the edit is ambiguous and may change the wrong place. Rejecting it with a clear error makes the model add surrounding lines.
  2. A bounded slice (for example the last 2,000 lines or 50 KB, plus the head) and a path to the full output, so it can read more only if needed.
  3. Listing puts every tool schema in every request. Tool search puts a small search tool in the request and loads a tool's schema only when the model asks for it.

1. The agent-computer interface

Ask what the model actually perceives when it uses a tool. It sees a name, a description and a schema, all as text in its input. It writes a call as text. It then sees the result as text. It never sees the screen, the file system or the process; it sees only what the tool chose to print. So a tool is two things at once: an action in the world and the model's only sense organ for that action.

That explains SWE-agent's 2024 finding that the interface you give a model matters as much as the model. A raw Linux shell was designed for humans who can scroll, glance and remember: it prints too much, fails silently and hides state. A model can do none of those things. A good agent-computer interface (ACI) has simple actions, informative error messages and outputs sized for a context window.

Every tool decision is a trade between three costs, and each one comes straight from a fact:

  • Context cost (facts 3 and 4). The model cannot use a tool it has not been told about, so every tool schema is in every request, paid for every time. Playwright's MCP server alone is about 13.7k tokens of definitions.
  • Error cost (fact 5). The model picks a tool and writes arguments by sampling, so it will sometimes pick wrong. A vague tool gets misused more. An edit tool that silently changes the wrong line is worse than one that refuses, because a refusal is information the model can act on and a silent mistake is not.
  • Round-trip cost (facts 2 and 4). The model only learns a result on its next call, and each call resends the whole history. Ten reads in ten steps cost ten times the prefix.

2. Code tour

Pi: few tools, carefully bounded

packages/coding-agent/src/core/tools/ contains read.ts, write.ts, edit.ts, bash.ts, plus grep.ts, find.ts and ls.ts, which are off by default. The core prompt and tools stay under 1,000 tokens. Three details are worth copying:

  • Truncation (truncate.ts): DEFAULT_MAX_LINES = 2000 and DEFAULT_MAX_BYTES = 50 * 1024. The bash tool description tells the model this up front, and when output is cut the result names the line range kept and a file with the full output.
  • Multi-edit (edit.ts): one call carries several edits[]; each oldText must match a unique, non-overlapping region. Line endings are normalized to LF for matching and the original endings and BOM are restored when writing.
  • File mutation queue (file-mutation-queue.ts): writes to the same real path are serialized, writes to different files run in parallel. This is how Pi keeps parallel tool batches safe.

fx: a toolbox with search

src/tools/ groups tools by kind: filesystem/ (read, write, edit, glob, grep), shell/, web/ (search and fetch with an HTML-to-Markdown converter and a URL policy), agent/ (subagent, vision, ask the user), skills/ and capabilities/. capability_search.zig searches skills and MCP tools on request and loads the matching schemas only for the next step. Tool results are capped at 64 KB by default (src/core/tooling/tool_result_limits.zig) with a visible cut marker.

eve: tools that proxy into a sandbox

eve's built-in bash, read_file, write_file and edit_file run in the trusted app runtime and proxy into the sandbox (docs/concepts/built-in-tools.md). bash waits 60 seconds by default and at most 120 (to leave time for the model call inside a serverless function). A command still running after that keeps going as its own process group and returns status: "running", a pid and an output directory under /tmp/.eve/jobs/; the model checks it later with tail and cat .../exit. Each stream keeps its last 2,000 lines or 50 KB. Any tool can be replaced by a file of the same name in agent/tools/, or removed with disableTool().

nanocode: Code Mode

nanocode's answer to round-trip cost is to change the interface itself. In Code Mode only two tools are top level, exec and wait (crates/backends/claude/prompts/code_mode.md). The model writes JavaScript that calls every other tool through a tools object, for example await tools.Bash({ command: "ls" }), uses Promise.all for independent calls, and returns only what the next decision needs. Cells run in a QuickJS worker with a fresh context each time (crates/runtime/code-mode-engine). Pi has the same idea in packages/codemode. Chapter 9 builds it.

4. Research and the Chinese view

  • SWE-agent (arXiv 2405.15793): simple actions, informative errors and history processors beat a raw shell.
  • Minimal works too. Terminus 2, a reference agent that sends raw keystrokes to tmux, ranks competitively on Terminal-Bench 2.0; Mario Zechner cites it as evidence for Pi's minimalism.
  • Tool masking. Manus does not add or remove tools mid-task because tool definitions sit near the front of the context and any change breaks the KV cache; it masks tools instead.
  • Chinese practice. Chinese write-ups summarize Claude Code's architecture as one loop plus a short list of tools (bash, read, write, edit, glob, grep, browser) plus on-demand skills and compression (Learn Claude Code mirror), the same minimal-core-plus-extensions shape as Pi.

5. Build: a typed tool registry

Replace Chapter 1's tools with a registry. Each tool is a Python function plus a pydantic model for its arguments; the schema comes from the model, so code and schema never drift.

"""A typed tool registry: schemas from type hints, validation, truncation, safe edits, background jobs."""
import os, subprocess, tempfile, threading, time, uuid
from typing import Callable
from pydantic import BaseModel, ValidationError

MAX_LINES, MAX_BYTES = 2000, 50 * 1024        # same limits as Pi and eve
JOBS = os.path.join(tempfile.gettempdir(), "harness-jobs")

class Tool:
    def __init__(self, fn: Callable, args: type[BaseModel], sequential: bool):
        self.fn, self.args, self.sequential = fn, args, sequential
        self.name, self.description = fn.__name__, (fn.__doc__ or "").strip()

    def spec(self):
        return {"name": self.name, "description": self.description, "parameters": self.args.model_json_schema()}

REGISTRY: dict[str, Tool] = {}

def tool(args: type[BaseModel], sequential=False):
    """Register a function as a tool. sequential=True forces calls to run in order (Pi's executionMode)."""
    def wrap(fn):
        REGISTRY[fn.__name__] = Tool(fn, args, sequential)
        return fn
    return wrap

def truncate(text: str, label: str) -> str:
    """Keep the head and the tail; save the full text to a file the agent can read in parts."""
    lines, size = text.splitlines(), len(text.encode())
    if len(lines) <= MAX_LINES and size <= MAX_BYTES:
        return text
    path = os.path.join(tempfile.gettempdir(), f"{label}-{uuid.uuid4().hex[:8]}.txt")
    open(path, "w").write(text)
    head, tail = lines[:200], lines[-(MAX_LINES - 200):]
    kept = "\n".join(head) + f"\n[... {len(lines) - len(head) - len(tail)} lines cut; full output: {path} ...]\n" + "\n".join(tail)
    return kept.encode()[-MAX_BYTES:].decode(errors="ignore")

def call(name: str, raw_args: dict) -> str:
    """Validate, run, truncate. Every failure comes back as text the model can read."""
    t = REGISTRY.get(name)
    if t is None:
        return f"error: unknown tool '{name}'. Available: {', '.join(REGISTRY)}"
    try:
        args = t.args.model_validate(raw_args)
    except ValidationError as e:
        return f"error: invalid arguments for {name}: {e.errors(include_url=False)}"
    try:
        return truncate(str(t.fn(args)), name)
    except Exception as e:
        return f"error: {type(e).__name__}: {e}"

# ---- file tools -------------------------------------------------------------
class ReadArgs(BaseModel):
    path: str
    offset: int = 1        # first line, 1-based
    limit: int = MAX_LINES

@tool(ReadArgs)
def read(a: ReadArgs):
    """Read a text file. Use offset and limit for large files."""
    lines = open(a.path, encoding="utf-8", errors="replace").read().splitlines()
    chunk = lines[a.offset - 1 : a.offset - 1 + a.limit]
    more = f"\n[lines {a.offset}-{a.offset + len(chunk) - 1} of {len(lines)}]" if len(lines) > len(chunk) else ""
    return "\n".join(f"{a.offset + i:>6}  {l}" for i, l in enumerate(chunk)) + more

_locks: dict[str, threading.Lock] = {}
def _lock(path):                                   # one lock per real file path (Pi's file mutation queue)
    return _locks.setdefault(os.path.realpath(path), threading.Lock())

class WriteArgs(BaseModel):
    path: str
    content: str

@tool(WriteArgs, sequential=True)
def write(a: WriteArgs):
    """Create or overwrite a file. Prefer edit for changes to existing files."""
    with _lock(a.path):
        os.makedirs(os.path.dirname(os.path.abspath(a.path)), exist_ok=True)
        open(a.path, "w", encoding="utf-8").write(a.content)
    return f"wrote {a.path} ({len(a.content)} chars)"

class Edit(BaseModel):
    old: str
    new: str

class EditArgs(BaseModel):
    path: str
    edits: list[Edit]

@tool(EditArgs, sequential=True)
def edit(a: EditArgs):
    """Replace exact text. Each edits[].old must match exactly one place in the file; edits must not overlap."""
    with _lock(a.path):
        raw = open(a.path, encoding="utf-8", newline="").read()
        crlf = "\r\n" in raw
        text = raw.replace("\r\n", "\n")                      # match on LF, write back the original line endings
        spans = []
        for e in a.edits:
            old, new = e.old.replace("\r\n", "\n"), e.new.replace("\r\n", "\n")
            n = text.count(old)
            if n != 1:
                return f"error: edit.old found {n} times in {a.path}; include more surrounding lines so it is unique"
            i = text.index(old)
            spans.append((i, i + len(old), new))
        spans.sort()
        if any(spans[k][1] > spans[k + 1][0] for k in range(len(spans) - 1)):
            return "error: edits overlap; merge them into one edit"
        for start, end, new in reversed(spans):
            text = text[:start] + new + text[end:]
        open(a.path, "w", encoding="utf-8", newline="").write(text.replace("\n", "\r\n") if crlf else text)
    return f"applied {len(spans)} edit(s) to {a.path}"

# ---- shell with background jobs --------------------------------------------
class BashArgs(BaseModel):
    command: str
    timeout: int = 60       # seconds to wait before the command moves to the background

@tool(BashArgs, sequential=True)
def bash(a: BashArgs):
    """Run a shell command. If it runs longer than timeout, it keeps running in the background and you get
    a job directory: read its stdout file and its exit file later with bash."""
    job = os.path.join(JOBS, uuid.uuid4().hex[:8])
    os.makedirs(job)
    cmd = f"({a.command}) > {job}/stdout 2>&1; echo $? > {job}/exit"
    proc = subprocess.Popen(cmd, shell=True, start_new_session=True)
    deadline = time.time() + max(1, min(a.timeout, 600))
    while time.time() < deadline and proc.poll() is None:
        time.sleep(0.1)
    out = open(f"{job}/stdout", errors="replace").read()
    if proc.poll() is None:
        return f"{out}\n[still running as pid {proc.pid}; output in {job}/stdout, exit code will be in {job}/exit]"
    proc.wait()
    return f"{out}\n[exit code: {open(f'{job}/exit').read().strip()}]"

What each piece borrows:

  • Errors as text, everywhere. Unknown tool, invalid arguments and exceptions all return readable strings, including the list of valid tool names.
  • Truncation keeps 200 head lines and the tail up to 2,000 lines or 50 KB, and saves the full output to a file the agent can read with read(offset, limit). Pi's limits.
  • Multi-edit with uniqueness, overlap checks and preserved line endings: Pi's edit.ts.
  • Per-file locks: Pi's file mutation queue. sequential=True: Pi's per-tool execution mode.
  • Background bash with a job directory: eve's design.
  • Read with line numbers: the model can cite and target exact lines.

Wire it in

In step(), send [t.spec() for t in REGISTRY.values()] as the tools. Run tool calls with a thread pool when none of them is sequential, otherwise in order; each result comes from call(name, args).
