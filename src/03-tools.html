Tools and the action interface

The model only writes text (fact 1). A tool is a contract that says which text the harness will turn into which action, and what text comes back. That makes a tool two things at once: the model's hands and the model's only eyes on what its hands did. This chapter derives what a good tool looks like from that double role, then takes the design decisions one at a time: shell or dedicated tools, how the shell behaves, the edit format, read-before-write, how big a result may be, how many tools the model sees, and how descriptions are written. It shows how nine harnesses answered each, and ends with a typed tool registry you build.

Level: intermediate Time: about 20 hours with the build Needs: Chapters 1 and 2, Python 3.11+ Harnesses read: Pi, eve, fx, nanocode, Codex, Claude Code, Kimi Code, Qwen Code, Trae Agent
Before you start: skip check

  2. A command is still running when its time limit arrives. Name three things a harness could do, and one harness that does each.
  3. Why do Pi and eve accept an edit whose search text differs from the file only in smart quotes or trailing spaces, while Claude Code's Edit tool refuses it?
  4. A tool printed 2 MB. What are the two ways to keep that from reaching the model while still letting the model see any part of it later?
Answers
  1. Through the shell (cat, rg, sed -n). Models are heavily trained on shell use, one general tool costs less context than several, and the harness can still bound the output.
  2. Kill it (Trae Agent's shell must then be restarted), keep it running and hand back a handle to poll (Codex, fx, eve), or move it to the background automatically and report where its output goes (Claude Code).
  3. A tolerant match recovers from the model's typing habits (it often normalises quotes and whitespace), at the small risk of matching something unintended. An exact match never surprises, at the cost of more failed edits. Both are defensible; each harness chose one.
  4. Save the full output to a file and tell the model its path (Pi, Claude Code, Kimi Code, Qwen Code), or keep it in the session behind a handle that a dedicated tool can read in ranges or search (fx).

1. What a tool is, from the model's side

Ask what the model actually perceives. It sees each tool as a name, a description and a schema, all text in its input. It writes a call as text. It sees the result as text (or an image). It never sees the screen, the file system or the process; it sees only what the tool chose to return. So every tool has two jobs: do the action safely, and report it in a form the model can use. Most tool bugs are failures of the second job.

SWE-agent's 2024 finding still frames the subject: the interface you give a model matters as much as the model, and a shell designed for humans (prints too much, fails silently, hides state) is a poor interface for a model that cannot scroll, glance or remember. Anthropic's guidance on writing tools for agents makes the same point in practice: use pagination, range selection, filtering, or truncation with sensible defaults, and describe each tool as you would to a new team member, making implicit context explicit.

2. The decisions, one at a time

Decision 1. The shell, or dedicated tools?

A coding agent can do almost everything through one tool, the shell: read with cat, search with rg, edit with sed or a heredoc. Or the harness can provide a dedicated tool for each action: Read, Grep, Glob, Edit, Write. This is the most visible split between harnesses, and it is moving.

Derive the trade-off. For the shell: models have seen enormous amounts of shell use in training, so they use it fluently; one general tool costs less context than five specific ones; and any new command-line program is usable with no harness change. Against the shell: its output is unbounded and unstructured; permission rules on raw command text are hard (Chapter 7); and the harness loses track of what the model has read, which matters for read-before-write (decision 4).

The harnesses that lean on the shell recover the lost properties another way. Claude Code's documentation says that on macOS, Linux and WSL it leaves Glob and Grep out of the default tool set, and in its shell find and grep run embedded versions of bfs and ugrep, so searches still reach permission rules and hooks as shell calls. It also counts a small set of single-file shell views (cat, head, tail, sed -n, grep, rg and a few more, with no pipes) as reads for the purpose of read-before-edit. Codex bounds shell output and offers a patch tool for edits, so the one thing it does not leave to the shell is writing. The harnesses that lean on dedicated tools say so in the shell's own description: Kimi Code's tells the model to translate cat, find and grep into Read, Glob and Grep, and fx's says to use its file tools rather than ls, find, grep or cat.

Decision 2. What is the shell, exactly?

Once there is a shell tool, three questions remain: does state (working directory, variables) carry from one call to the next, what happens to a command that outlives its time limit, and how big may a command's output be. The answers form three models.

The long-running case is where the models differ most, and where the details matter.

The reasoning behind process sessions is worth spelling out. A time limit exists to keep the loop responsive, not because the command is wrong. Killing a test suite at 120 seconds throws away the work and teaches the model to retry the same slow command. Returning a handle keeps the work and turns "wait" into an ordinary action the model can choose. eve adds one more reason: its harness runs inside serverless functions with their own time limit, so a shell call must return in time for the model call that follows.

Claude Code adds a detail that shows how much a description must say: exit code 1 counts as success only for commands where it is a normal answer (grep, rg, find, diff, test and a few others); for everything else it is a failure and gets the shorter, head-and-tail output. A model told "the command failed" behaves differently from one told "no matches".

Decision 3. What does an edit look like?

Writing whole files is simple and wasteful: a one-line change to a 2,000-line file resends 2,000 lines and risks silently dropping some. So every harness offers a partial edit. Three formats exist, and the choice is a bet about how models fail.

  • Exact replacement is the most common because it is the easiest to explain and verify: the search text must appear exactly once, or the model must add context or ask to replace every occurrence. Claude Code's documentation states it plainly: no regex, no fuzzy matching, and a single character of whitespace difference is enough to miss. The cost is failed edits, which cost a round trip each.
  • Multi-edit with tolerance (Pi, and eve's edit tool with the same rules) batches several replacements into one call, all matched against the file as it was before the call, so the model does not have to predict how earlier edits shift later ones. Overlaps are rejected with a message that names both edits. If no exact match exists, it normalises the text the way models tend to mangle it (Unicode normalisation, trailing spaces, smart quotes to straight quotes, Unicode dashes to hyphens, special spaces to plain spaces) and tries again. Line endings and a byte-order mark are preserved on write.
  • A patch grammar (Codex) lets one call add, delete, update and move several files, with context lines instead of line numbers. It suits models trained to produce it; Codex's parser is lenient about the envelope for at least one model that needs it, and finds hunks with decreasing strictness.

The error message is part of the format. Pi's says how many times the text occurred and asks for more context; its overlap error names the two edits and tells the model to merge them or target disjoint regions. An error that says exactly what to do next turns a failed edit into one extra step instead of a spiral.

Decision 4. Must the model read a file before it changes it?

Fact 2 again: the model only knows a file's contents if they are in its context. An edit to a file it never read is a guess about text it cannot see, and an edit based on a read from twenty minutes ago may overwrite changes made since (by the person, a formatter or another agent). Harnesses track what the model has seen to catch both.

The trend in Claude Code's documentation is instructive: the strict rule (always read first) applies to older models, while newer models may edit an unread file when reading it would not need a permission prompt, and a partial read never counts. The strict rule cost round trips that capable models did not need; the relaxation keeps the safety where it matters (unreadable files, partial reads, stale search text).

A related problem is two writes to one file at once. Pi serialises all changes to the same real path through a per-file queue while letting changes to different files run in parallel; Chapter 1 showed how Codex and Claude Code reach the same result with locks and concurrency classes.

Decision 5. How big may a result be, and where does the rest go?

Output is the largest single source of context growth. A test run can print 40,000 lines; left in history, it is resent on every later step and dilutes attention (facts 3 and 4). So every harness bounds results. The design question is what happens to the part that is cut.

Decision 6. How many tools does the model see?

Every tool definition is in every request. Connect a few MCP servers and the definitions alone can run to tens of thousands of tokens, most of which the model never uses. Worse, adding or removing a tool mid-session changes the start of the request and breaks the prompt cache (Chapter 2). Both problems have the same fix: keep a small, fixed list of tools in the request, and let the model find the rest.

The variations are in how a found tool is called. In eve and Qwen Code, the search returns a signature and the model calls the tool through a generic call-by-name tool, so the request's tool list stays fixed. Claude Code's documentation describes the cache consequence directly: with tools deferred, the tool list from the conversation's first request stays fixed, and a server that connects later supplies its tools as deferred definitions. Pi takes a different route: changes to the available tools are declared in the transcript as a system message, so replaying the transcript always reproduces the tools offered at each point.

Decision 7. What goes in a tool's description and result?

A description is a prompt the model reads on every call. It is the cheapest place to prevent a misuse, and the most often neglected.

  • Say the limits. Pi's shell description tells the model the output is cut to the last 2,000 lines or 50 KB and that the full output is saved, so the model is not surprised by a truncated log.
  • Say what not to do. fx's shell description: each call starts a new shell, so cd and export do not carry over; a command still running returns a session ID, never rerun it. Kimi Code's tells the model which shell commands to translate into dedicated tools and to issue independent read-only commands as parallel calls.
  • Keep it short, enforce it. fx checks at build time that the shell description fits the description length limit, because a longer one would be cut before it reaches the model.
  • Shape the result for the model, not the UI. eve separates what a tool returns from what the model sees: a channel may need rich data, the model only the gist. Codex's patch results and Claude Code's moved-to-background notices are written as instructions for the next step.
  • Make errors actionable. Every harness returns tool errors as results, never as crashes (Chapter 1). The good ones say what to do: provide more context, merge two edits, read the file first, use a longer timeout.

3. The nine tool sets, harness by harness

Each diagram shows the tools the model sees by default, grouped by job. Indigo marks tools that reach the outside world or other agents; amber marks tools that act on the local environment.

Pi: four tools and a strong opinion

Pi's default set is read, write, edit and bash; grep, find and ls exist but are off by default. The reasoning is Pi's general position: a small core costs little context and leaves the model to use the shell for everything else. The care goes into the four: bounded and saved output, multi-edit with tolerant matching and preserved line endings, image reading, and a per-file queue for concurrent changes.

eve: tools that run outside the sandbox and reach into it

eve's file and shell tools run in the trusted application runtime and act on a separate sandbox, so credentials and integration code never sit in model-controlled compute (Chapter 7). The default set adds web fetch and search and the agent tool; opt-ins include ask-the-user, glob, grep, a no-reply tool for scheduled checks that find nothing, and a sleep that survives restarts. Any tool can be marked deferred and found through its catalog tools.

fx: dedicated tools with lossless results

fx has file tools (glob with a count-only mode, literal-text grep, read with line ranges and images, write, edit), a process-session shell, web fetch and search with a URL policy and HTML-to-Markdown conversion, subagents, vision, ask-the-user, and a toolbox for skills and MCP servers. Results over 64 KB are cut with a marker and stay readable through a dedicated tool by handle, by search query or by byte range, which also finds earlier tool calls after compaction.

nanocode: the vendor's tools, or two tools and a program

nanocode's drivers reproduce each vendor's own tool set (Chapter 2). Its distinctive option is Code Mode: only exec and wait are top-level tools, and the model writes JavaScript that calls every other tool through a tools object, running independent calls together and returning only what the next decision needs. Chapter 9 covers it; here it is the extreme answer to round-trip cost.

Codex: a shell, a patch, and very little else

Codex gives the model a process-session shell (start a command, read more or send input with a second tool), the patch tool for every change, image viewing, a plan tool, a question tool, tool search for MCP tools, and a handful of session tools such as checking the remaining context. Reading and searching go through the shell. The bet is that a model trained in this harness is best served by the tools it was trained with.

Claude Code: a large, curated set that is shrinking where the shell suffices

Claude Code's tools reference lists dozens of tools: Bash and PowerShell, Read, Edit, Write and NotebookEdit, web fetch and search, Agent and messaging tools, task tools, plan mode, worktrees, LSP, Monitor for streaming a background command's output, scheduling tools, and ToolSearch for deferred tools. Glob and Grep are absent by default on macOS, Linux and WSL, where search runs through the shell; they return when the shell is removed, for example for a subagent that lists them without Bash.

Kimi Code: dedicated tools with explicit budgets

Kimi Code's core set is Read, Write, Edit, Bash, Glob and Grep, plus web fetch and search, media reading, the Agent tool, ask-the-user, task tools and a tool for loading more tools. Its descriptions are separate documents and read like instructions to a colleague: call Read directly on a known path without checking first, read several files in parallel, use Bash only for real shell semantics.

Qwen Code: everything, with deferral

Qwen Code has the broadest set in this book: file tools with read-before-write enforcement, ripgrep search, a shell with a background registry, LSP, web fetch and search (including a DashScope search backend), memory tools, cron, worktrees, teams, plan mode, image tools and more. It keeps the request small by deferring MCP tools and low-frequency built-ins behind a tool search that supports exact selection or keyword scoring.

Trae Agent: five tools for experiments

Trae Agent uses a persistent bash session (state carries over; a command past 120 seconds forces a restart), one editor tool with view, create and replace commands, a JSON editing tool, a sequential-thinking tool for planning, and task_done. An optional code knowledge graph tool queries functions and classes. A fixed, small set keeps experiments comparable.

5. Choosing a tool interface

For this book's harness: read, write, multi-edit and bash, with bounded output saved to a file, a per-file lock and background jobs. That is Pi's minimal set plus eve's job model, and it is what the build below implements. Exercises add a process-session shell, read tracking and a search tool for deferred tools.

6. Research and the Chinese view

  • SWE-agent (2024) named the agent-computer interface and showed that interface design moves results as much as the model: simple actions, informative errors, output sized for a context window.
  • Anthropic's guidance on writing tools for agents adds practice: consolidate multi-step operations into single tools, group related tools under shared prefixes by service and resource, and prioritize high-signal, human-readable information like names over low-level identifiers like UUIDs.
  • The shell turn. Across 2026 the production harnesses moved reading and searching into the shell (Codex from the start, Claude Code by removing Glob and Grep on Unix, nanocode's per-model guidance). The reason is the facts, not fashion: newer models use the shell well, and one tool costs less context than five.
  • Chinese practice. Kimi Code and Qwen Code both chose dedicated tools with explicit budgets and strict read-before-write, closer to Claude Code's earlier design. Qwen Code's tool results carry a hash of the full output so its loop detector stays correct after truncation, and it ships a DashScope web-search backend for users in China, where some Western search providers are not reachable.

7. Build: a typed tool registry

Replace Chapter 1's tools with a registry. Each tool is a Python function plus a pydantic model for its arguments; the schema comes from the model, so code and schema never drift.

"""A typed tool registry: schemas from type hints, validation, truncation, safe edits, background jobs."""
import os, subprocess, tempfile, threading, time, uuid
from typing import Callable
from pydantic import BaseModel, ValidationError

MAX_LINES, MAX_BYTES = 2000, 50 * 1024        # same limits as Pi and eve
JOBS = os.path.join(tempfile.gettempdir(), "harness-jobs")

class Tool:
    def __init__(self, fn: Callable, args: type[BaseModel], sequential: bool):
        self.fn, self.args, self.sequential = fn, args, sequential
        self.name, self.description = fn.__name__, (fn.__doc__ or "").strip()

    def spec(self):
        return {"name": self.name, "description": self.description, "parameters": self.args.model_json_schema()}

REGISTRY: dict[str, Tool] = {}

def tool(args: type[BaseModel], sequential=False):
    """Register a function as a tool. sequential=True forces calls to run in order (Pi's executionMode)."""
    def wrap(fn):
        REGISTRY[fn.__name__] = Tool(fn, args, sequential)
        return fn
    return wrap

def truncate(text: str, label: str) -> str:
    """Keep the head and the tail; save the full text to a file the agent can read in parts."""
    lines, size = text.splitlines(), len(text.encode())
    if len(lines) <= MAX_LINES and size <= MAX_BYTES:
        return text
    path = os.path.join(tempfile.gettempdir(), f"{label}-{uuid.uuid4().hex[:8]}.txt")
    open(path, "w").write(text)
    head, tail = lines[:200], lines[-(MAX_LINES - 200):]
    kept = "\n".join(head) + f"\n[... {len(lines) - len(head) - len(tail)} lines cut; full output: {path} ...]\n" + "\n".join(tail)
    return kept.encode()[-MAX_BYTES:].decode(errors="ignore")

def call(name: str, raw_args: dict) -> str:
    """Validate, run, truncate. Every failure comes back as text the model can read."""
    t = REGISTRY.get(name)
    if t is None:
        return f"error: unknown tool '{name}'. Available: {', '.join(REGISTRY)}"
    try:
        args = t.args.model_validate(raw_args)
    except ValidationError as e:
        return f"error: invalid arguments for {name}: {e.errors(include_url=False)}"
    try:
        return truncate(str(t.fn(args)), name)
    except Exception as e:
        return f"error: {type(e).__name__}: {e}"

# ---- file tools -------------------------------------------------------------
class ReadArgs(BaseModel):
    path: str
    offset: int = 1        # first line, 1-based
    limit: int = MAX_LINES

@tool(ReadArgs)
def read(a: ReadArgs):
    """Read a text file. Use offset and limit for large files."""
    lines = open(a.path, encoding="utf-8", errors="replace").read().splitlines()
    chunk = lines[a.offset - 1 : a.offset - 1 + a.limit]
    more = f"\n[lines {a.offset}-{a.offset + len(chunk) - 1} of {len(lines)}]" if len(lines) > len(chunk) else ""
    return "\n".join(f"{a.offset + i:>6}  {l}" for i, l in enumerate(chunk)) + more

_locks: dict[str, threading.Lock] = {}
def _lock(path):                                   # one lock per real file path (Pi's file mutation queue)
    return _locks.setdefault(os.path.realpath(path), threading.Lock())

class WriteArgs(BaseModel):
    path: str
    content: str

@tool(WriteArgs, sequential=True)
def write(a: WriteArgs):
    """Create or overwrite a file. Prefer edit for changes to existing files."""
    with _lock(a.path):
        os.makedirs(os.path.dirname(os.path.abspath(a.path)), exist_ok=True)
        open(a.path, "w", encoding="utf-8").write(a.content)
    return f"wrote {a.path} ({len(a.content)} chars)"

class Edit(BaseModel):
    old: str
    new: str

class EditArgs(BaseModel):
    path: str
    edits: list[Edit]

@tool(EditArgs, sequential=True)
def edit(a: EditArgs):
    """Replace exact text. Each edits[].old must match exactly one place in the file; edits must not overlap."""
    with _lock(a.path):
        raw = open(a.path, encoding="utf-8", newline="").read()
        crlf = "\r\n" in raw
        text = raw.replace("\r\n", "\n")                      # match on LF, write back the original line endings
        spans = []
        for e in a.edits:
            old, new = e.old.replace("\r\n", "\n"), e.new.replace("\r\n", "\n")
            n = text.count(old)
            if n != 1:
                return f"error: edit.old found {n} times in {a.path}; include more surrounding lines so it is unique"
            i = text.index(old)
            spans.append((i, i + len(old), new))
        spans.sort()
        if any(spans[k][1] > spans[k + 1][0] for k in range(len(spans) - 1)):
            return "error: edits overlap; merge them into one edit"
        for start, end, new in reversed(spans):
            text = text[:start] + new + text[end:]
        open(a.path, "w", encoding="utf-8", newline="").write(text.replace("\n", "\r\n") if crlf else text)
    return f"applied {len(spans)} edit(s) to {a.path}"

# ---- shell with background jobs --------------------------------------------
class BashArgs(BaseModel):
    command: str
    timeout: int = 60       # seconds to wait before the command moves to the background

@tool(BashArgs, sequential=True)
def bash(a: BashArgs):
    """Run a shell command. If it runs longer than timeout, it keeps running in the background and you get
    a job directory: read its stdout file and its exit file later with bash."""
    job = os.path.join(JOBS, uuid.uuid4().hex[:8])
    os.makedirs(job)
    cmd = f"({a.command}) > {job}/stdout 2>&1; echo $? > {job}/exit"
    proc = subprocess.Popen(cmd, shell=True, start_new_session=True)
    deadline = time.time() + max(1, min(a.timeout, 600))
    while time.time() < deadline and proc.poll() is None:
        time.sleep(0.1)
    out = open(f"{job}/stdout", errors="replace").read()
    if proc.poll() is None:
        return f"{out}\n[still running as pid {proc.pid}; output in {job}/stdout, exit code will be in {job}/exit]"
    proc.wait()
    return f"{out}\n[exit code: {open(f'{job}/exit').read().strip()}]"

What each piece borrows:

  • Errors as text, everywhere. Unknown tool, invalid arguments and exceptions all return readable strings, including the list of valid tool names.
  • Truncation keeps 200 head lines and the tail up to 2,000 lines or 50 KB, and saves the full output to a file the agent can read with read(offset, limit). Pi's limits.
  • Multi-edit with uniqueness, overlap checks and preserved line endings: Pi's edit tool.
  • Per-file locks: Pi's file mutation queue. sequential=True: Pi's per-tool execution mode.
  • Background bash with a job directory: eve's design.
  • Read with line numbers: the model can cite and target exact lines.

Wire it in

In step(), send [t.spec() for t in REGISTRY.values()] as the tools. Run tool calls with a thread pool when none of them is sequential, otherwise in order; each result comes from call(name, args).

Stage 1 gate

Rerun your 10 test tasks with both models and compare with the Chapter 1 baseline. Record pass rate, steps per task and tokens per task. Stage 1 is done when the agent passes most tasks and you can explain every failure by reading its transcript.

8. Exercises

  1. Process sessions. Change bash so that a command still running after 10 seconds returns a job ID instead of blocking. Add a tool that reads new output from a job or stops it. Run a 2-minute test suite through it.
  2. Read tracking. Record a hash of each file when the model reads it. Refuse an edit to a file that was never read, or whose hash changed since, with an error that says to read it again. Measure how often your tasks trip it.
  3. Tolerant edits. Add Pi's normalisation (trailing spaces, smart quotes, dashes, special spaces) as a fallback when the exact match fails. Log every fallback match for a week of tasks. Did any match the wrong place?
  4. Lossless truncation by handle. Instead of a temp-file path, store each long result under a handle and add a tool that searches it or reads a byte range, as fx does. Compare step counts with the file approach.
  5. Shell-first. Disable your read tool and tell the model to use cat, sed -n and rg. Compare pass rate, steps and tokens on your 10 tasks with both of your models.
