Stage 2 · Context · Chapter 6

Sessions, state and memory

The model keeps nothing between calls (fact 2), so everything an agent "remembers" is something the harness wrote down. The question is what to write, in what shape, for how long, and who reads it. This chapter separates three records that are easy to confuse (history, state and memory), derives the shape each should take, and walks through ten design decisions: append-only logs, trees and branches, what a session records besides messages, rewinding files as well as words, storage, typed state, and how cross-session memory is captured, recalled and kept safe. It ends with the session tree and memory slot you build.

Level: intermediate Time: about 12 hours with the build Needs: Chapters 1 to 5 Harnesses read: Pi, eve, fx, nanocode, Codex, Claude Code, Kimi Code, Qwen Code, Trae Agent
Before you start: skip check
  1. Why should the remaining budget or the list of running background jobs not live only in the message history?
  2. Kimi Code undoes the last three messages without deleting anything. How?
  3. Claude Code's rewind can restore code, conversation or both. Why can it not always restore a file that only a shell command changed?
  4. Codex's memory folder is itself a git repository. What does that buy?
Answers
  1. Compaction summarises history, and a summary is a sample (fact 5): it can round a number or drop a job. Values the harness must get exactly right belong in typed state outside the messages.
  2. It appends an undo record with a count. The conversation the model sees is computed from the log, and the record retracts the previous messages in that computation.
  3. Checkpoints snapshot files the file-editing tools touched. A file changed only by a shell command was never snapshotted, so the documentation sends you to git for that case.
  4. Every change the background pipeline makes to memory can be inspected and reverted, so a bad consolidation is not permanent.

1. Three different records

Ask what the harness needs to write down and who will read it. Three different answers come out, and mixing them causes predictable failures.

2. The decisions, one at a time

Decision 1. Is history ever rewritten?

No harness in this book rewrites history. Compaction, undo and branching are all new records, and the conversation the model sees is computed from the log when it is needed. This is the event-sourcing pattern: the log is the truth, the request is a projection.

Why insist on this? Three reasons fall out of the facts. A resumed session must reproduce exactly what the model was shown, or the model's next step is based on a context it never saw. An audit or an eval (Chapter 10) needs the real sequence, not a cleaned-up one. And a crash mid-write (Chapter 11) can only corrupt the last line of an append-only file, never the history before it.

Decision 2. A line or a tree?

A linear log is enough until the user wants to go back and try another approach. Then there are two choices: throw away the later part, or keep it and start a branch.

Decision 3. What does a session record besides messages?

To replay a session exactly, the log must hold everything that changed what the model saw or how it was called. Pi's entry types are a good checklist.

Codex goes further on the same idea: each piece of model-visible state is saved with a snapshot of what the model was last told (Chapter 4), so a resumed session knows which updates the model already has. Claude Code keeps three records per the paper: an append-only transcript, a global prompt history, and separate "sidechain" transcripts for subagents. Kimi Code gives every agent its own log; a parent's log holds only the subagent call and its result.

Decision 4. Can you rewind the files, not just the words?

Fact 6: the world is stateful. Rewinding the conversation does not un-write a file. A harness that offers undo must snapshot files separately.

Decision 5. Where are sessions stored?

Two details deserve copying. Qwen Code stores titles, branches, goals and artifact summaries in small sidecar files next to the transcript, so changing a title does not rewrite a large file, and a writer lease ensures only one process writes a session at a time. nanocode stores large payloads as content-addressed blobs, so a 5 MB tool result is written once and referenced by its hash.

Decision 6. Where does exact state live?

A plan, a budget, a task table, the working directory, the permission mode: values the harness must not get wrong. They live as typed values outside the message list, and the model sees a rendering of them.

  • eve stores typed session values declared by the agent author, alongside its session, turn and step nesting.
  • Codex keeps each model-visible section's snapshot with the session, as Chapter 4 described.
  • Todo and plan tools (Codex's plan tool, Claude Code's task tools, Kimi Code's and Qwen Code's todo tools) keep the plan as data the harness can show in the UI and re-inject after compaction, instead of trusting a summary to carry it.

Decision 7. How is memory captured?

Memory is selection: out of everything that happened, what is still true and useful next week? Three answers exist.

Decision 8. How is memory recalled?

Recall has the same problem as tools (Chapter 3): everything loaded costs context on every step. So harnesses load an index and fetch details on demand.

  • Claude Code loads the first 200 lines or 25 KB of its MEMORY.md index at the start of a session; topic files are read on demand. Per the paper, a model scans memory file headers and picks up to five, with no embeddings.
  • eve uses memory slots: each slot names a provider (built-in file memory, or third-party services) and a scope (for example per signed-in caller). Each turn it resolves the scope, asks the provider to recall, gives the model the provider's tools, and asks it to capture after the turn.
  • Qwen Code gives the model memory tools to manage and search memory, and marks a memory catalog snapshot in the turn so it can be recognised as injected context (Chapter 4).
  • Kimi Code relies on AGENTS.md; we found no separate memory store. Trae Agent has none, by design.

Decision 9. How is memory kept safe?

Memory is text the model will read in future sessions. Anything wrong or malicious in it becomes a standing instruction.

Decision 10. Chat history or artifacts?

For work that spans many sessions, a growing chat log is the wrong carrier. Anthropic's harness for long-running agents has each new session read a progress file, a feature list and the git log, and leave them updated for the next one. The model reads a few short, current documents instead of a long, stale conversation. This is memory as artifacts, and it composes with everything above: the session log is still kept for audit, but the next session starts from the artifacts.

5. Choosing a session and memory design

This book's design: an append-only tree in one JSONL file with Pi-style entry types, a projection that walks root to leaf, file snapshots before each turn, and one memory slot that recalls as labelled user content and is never shown to the compactor.

6. Research and the Chinese view

  • Persistence is open research. The Dive into Claude Code paper lists memory and long-term human-agent relationships among its open directions.
  • Artifacts beat chat history for multi-session work, per Anthropic's long-running harness: a progress file, a feature list and git commits.
  • Chinese framing. OpenHarness's walkthrough splits a harness into Brain (model calls), Hands (tools) and Session (memory) layers; the Code as Agent Harness survey counts repository state and commit history as part of the harness's memory. Kimi Code's per-agent logs with retraction records are the clearest event-sourcing design read for this book.

7. Build: a session tree and a memory slot

"""Sessions as append-only JSONL trees (Pi's design), plus a memory slot that lives outside history (eve's design)."""
import json, os, time, uuid
from pathlib import Path

SESSIONS = Path.home() / ".harness" / "sessions"

class Session:
    """Every entry has id and parent_id. The leaf is the current position; appending adds a child of the leaf.
    Branching moves the leaf back. History is never rewritten."""
    def __init__(self, path: Path):
        self.path, self.entries, self.leaf = path, {}, None
        if path.exists():
            for line in path.read_text().splitlines():
                e = json.loads(line)
                if e["type"] == "leaf":                 # leaf moves are entries too, so a reload restores the position
                    self.leaf = e["to"]
                else:
                    self.entries[e["id"]] = e
                    self.leaf = e["id"]

    @classmethod
    def new(cls, cwd: str):
        SESSIONS.mkdir(parents=True, exist_ok=True)
        s = cls(SESSIONS / f"{time.strftime('%Y%m%d-%H%M%S')}-{uuid.uuid4().hex[:6]}.jsonl")
        s._write({"type": "session", "cwd": cwd, "id": uuid.uuid4().hex[:12], "parent_id": None})
        return s

    @classmethod
    def latest(cls, cwd: str):
        """Resume the newest session started in this directory (fx -c, pi --continue)."""
        for p in sorted(SESSIONS.glob("*.jsonl"), reverse=True):
            first = json.loads(p.open().readline())
            if first.get("cwd") == cwd:
                return cls(p)
        return None

    def _write(self, entry):
        with self.path.open("a") as f:                  # append only; one line per entry
            f.write(json.dumps(entry, default=str) + "\n")
            f.flush(); os.fsync(f.fileno())
        if entry["type"] == "leaf":
            self.leaf = entry["to"]
        else:
            self.entries[entry["id"]] = entry
            self.leaf = entry["id"]

    def append(self, kind: str, **data) -> str:
        """kind: 'message', 'checkpoint' (from compaction), 'model_change', 'label' ..."""
        entry = {"type": kind, "id": uuid.uuid4().hex[:12], "parent_id": self.leaf, "ts": time.time(), **data}
        self._write(entry)
        return entry["id"]

    def branch(self, entry_id: str):
        """Continue from an earlier entry. The old path stays in the file as a sibling branch."""
        assert entry_id in self.entries
        self._write({"type": "leaf", "to": entry_id})

    def path_to_leaf(self):
        out, cur = [], self.leaf
        while cur:
            e = self.entries[cur]
            out.append(e)
            cur = e["parent_id"]
        return out[::-1]

    def messages(self):
        """Messages the model sees: start at the last checkpoint on the path, then everything after it."""
        path = self.path_to_leaf()
        last_cp = max((i for i, e in enumerate(path) if e["type"] == "checkpoint"), default=None)
        start = 0 if last_cp is None else last_cp
        out = []
        for e in path[start:]:
            if e["type"] == "checkpoint":
                out.append({"role": "user", "content": f"<checkpoint>\n{e['summary']}\n</checkpoint>"})
            elif e["type"] == "message":
                out.append(e["message"])
        return out

    def tree(self):
        """Text view of all branches, for a /tree command."""
        children = {}
        for e in self.entries.values():
            children.setdefault(e["parent_id"], []).append(e)
        lines = []
        def walk(pid, depth):
            for e in children.get(pid, []):
                text = e.get("message", {}).get("content") or e["type"]
                mark = " <- leaf" if e["id"] == self.leaf else ""
                lines.append(f"{'  ' * depth}{e['id']} {str(text)[:50]!r}{mark}")
                walk(e["id"], depth + 1)
        walk(None, 0)
        return "\n".join(lines)

class FileMemory:
    """A memory slot outside history: recalled into each turn as a labeled user message, saved by a tool.
    Compaction never sees it, so it cannot be summarized away (eve)."""
    def __init__(self, path=Path.home() / ".harness" / "memory.md"):
        self.path = path
    def recall(self):
        text = self.path.read_text() if self.path.exists() else ""
        return {"role": "user", "content": f"<memory slot='profile'>\n{text}\n</memory>"} if text.strip() else None
    def save(self, fact: str):
        self.path.parent.mkdir(parents=True, exist_ok=True)
        with self.path.open("a") as f:
            f.write(f"- {fact.strip()}\n")
        return "saved"

Wiring:

  • At start: Session.latest(cwd) if the user passed -c, otherwise Session.new(cwd). Rebuild state.messages from session.messages().
  • After every message: session.append("message", message=...). After compaction: session.append("checkpoint", summary=...). History before it stays in the file.
  • Add /tree and /fork <id> commands that call tree() and branch().
  • Each turn, prepend memory.recall() to the request (not to the stored history), and give the model a memory_save(fact) tool.

Stage 2 gate

  1. Start a long task, quit mid-way, resume with -c, and finish. Nothing should be repeated.
  2. Let the agent try a wrong approach, branch back, and solve it another way. Show the tree in a post.
  3. Tell the agent a preference in one session ("use pytest -q"). Start a new session and check it follows it without being told.

8. Exercises

  1. Replay test. Rebuild the exact request of step 30 of a saved session from the log alone. Diff it against what was actually sent. Any difference is a missing entry type.
  2. Branch and summarise. Add a command that moves the leaf to an earlier entry and appends a short summary of the branch you left. Does the model avoid repeating the failed approach?
  3. File checkpoints. Snapshot every file the edit tools touch before each turn. Implement "restore code only" and "restore conversation only".
  4. Exact state. Move the plan and remaining budget out of messages into typed state rendered at the tail. Compact twice and check they survive unchanged.
  5. Memory with a pipeline. After each session, extract at most three memories, redact anything that looks like a secret, and commit them to a git-tracked folder. Recall by header, at most five.
