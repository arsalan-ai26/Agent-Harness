Extensibility: skills, MCP and hooks

No harness ships with everything a team needs: their deploy procedure, their issue tracker, their rule that every edit is formatted. So every harness has ways to add things. This chapter derives the four extension points from two questions (does the model need to know about it, and must it happen every time?), then takes seven design decisions: how skills load, how many MCP tools the model sees, what hooks may decide and what happens when they fail, how whole features are packaged, whether the agent may extend itself, and whether extensions move between harnesses. It shows each harness's extension surface and keeps the skills, hooks and MCP client you build.

Level: intermediate Time: about 14 hours with the build Needs: Chapters 1 to 7 Harnesses read: Pi, eve, fx, nanocode, Codex, Claude Code, Kimi Code, Qwen Code, Trae Agent
Before you start: skip check
  1. Why is "always run the formatter after an edit" a hook and not a line in AGENTS.md?
  2. A harness has 200 skills installed. How much context do they cost before any is used?
  3. A pre-tool hook crashes. Should the tool call go ahead?
  4. Why do Qwen Code's hook events use the same names as Claude Code's?
Answers
  1. The model's choices are samples (fact 5); a line in AGENTS.md is a suggestion it will sometimes forget. A hook is code the harness runs at a fixed point, every time.
  2. One short listing entry each (name and description). Claude Code caps each entry at 1,536 characters; the body loads only when the skill is used.
  3. It depends on what the hook guards, so the hook should say. Claude Code treats most errors as non-blocking unless the hook sets a block-on-failure option; Kimi Code makes each hook declare its failure policy. A safety hook should fail closed.
  4. So users can move hooks between harnesses. Shared names, like the Agent Skills format and AGENTS.md, make extensions portable.

1. Four extension points from two questions

Ask two questions of anything you want to add. First: does the model need to know about it to use it? If yes, it costs context, and the only way to make it cheap is to show a short name first and the full text only when the model asks. If no, it can run outside the model and cost nothing. Second: must it happen every time, or only when the model decides? Anything that must always happen cannot be left to the model (fact 5); it must be code the harness runs at fixed points.

The Claude Code paper adds a second map: extension mechanisms act at three points in the loop. Some change what the model sees (assembling the request), some change which tools it may call, and some decide whether an action runs.

2. The decisions, one at a time

Decision 1. How does a skill load?

A skill is a folder: a SKILL.md with a short frontmatter and instructions, plus optional reference files and scripts. The design problem is cost: a team may have hundreds. The answer every harness converged on is progressive disclosure in three levels.

The harnesses differ in who may trigger a skill and where it runs.

  • Who invokes. Claude Code lets a skill be model-invoked (the default), user-only (left out of the listing, so it costs nothing and the model cannot trigger, say, a deploy) or model-only (hidden from the slash menu).
  • Where it runs. A Claude Code skill can declare that it runs in a forked subagent: the body becomes the subagent's task and the main context sees only the result (Chapter 9). The documentation advises this only for skills with an explicit task, not for reference guidelines.
  • How it is found. eve and fx load skills through catalog tools; fx's agent can search for and install skills itself. Codex ships a skill for creating skills, and migrated its older custom commands into skills of at most 4,000 bytes. Claude Code merged commands into skills: both create a slash command, and the skill wins on a name clash.
  • How it is maintained. Qwen Code ships bundled skills and a curator that can roll back a change.

Decision 2. How many MCP tools does the model see?

MCP lets any service expose tools to any harness. Every tool's schema costs context on every request (Chapter 3), and a few servers can bring hundreds of tools. Three answers exist.

Two harnesses wrote their own MCP client rather than use the official SDK: Pi (a small standalone client with standard-input and streamable HTTP transports, added in its 1.0) and nanocode (its own client plus a BM25 search index over tool descriptions). The reason in both cases is control over a component every tool call passes through. Qwen Code pools transports so several servers share connections. Chapter 7's rule applies to all of them: a server configured by a repository must not start until the user trusts that repository.

Decision 3. Which lifecycle points get hooks?

A hook is code the harness runs at a named point. The set of points is the harness's real extension contract: whatever has no hook point cannot be customised without changing the harness.

fx's four are a minimal useful set worth studying: one to gate actions (pre tool use), one to keep the agent working when it should not stop yet (stop), one to react after a turn, and one to tell a person the agent is waiting. Claude Code's set covers the same ground and much more: model switches, file and directory changes, worktrees, task events, configuration changes, instruction loading. Codex is the one that hooks the model request itself, which is where a team would add logging or redaction of every prompt.

Decision 4. What may a hook decide, and what if it fails?

A hook that can only observe is an audit log. A hook that can decide is part of the permission system (Chapter 7), and must have clear semantics.

Two lessons generalise. First, the asymmetry: a hook may tighten freely but loosening needs care, which is why an allow does not override another hook's block. Second, failure policy is per hook, not global: a formatter that crashes should not stop the agent, a secret scanner that crashes should. Claude Code's stop hook shows the other use of blocking: on the stop event, blocking keeps the agent working, which is how teams enforce "do not stop until the tests pass" (Chapter 14).

Decision 5. How are whole features added?

Skills, MCP and hooks add behaviour at the edges. Some additions need to live inside the harness: a new provider, a UI panel, a command with state. Here the harnesses split by how much of themselves they open up.

Claude Code's plugins, per the paper, bundle up to ten component types in one manifest: commands, agents, skills, hooks, MCP servers, LSP servers, output styles and more. eve takes the opposite route to the same goal: the agent's directory is the contract (skills, hooks, connections, tools and channels are folders), and an extension is just a package with the same folders. Kimi Code's design is the most uniform: its own planning, goals, scheduling and reminders are features registered the same way an extension would be.

Decision 6. May the agent extend itself?

Pi's extensions are plain files, so the agent can write and hot-reload its own; Armin Ronacher has described daily extensions (answer, todos, review) written entirely by the agent. fx's agent can search for and install skills. eve ships optional self-improvement and self-modification extensions.

Watch out

An agent that can install skills or write extensions can widen its own powers, and a prompt injection can ask it to (Chapter 7). Pair self-extension with a pre-tool hook that blocks writes to the harness's own configuration and extension folders unless the user approves, and load new extensions only after review.

Decision 7. Do extensions move between harnesses?

An extension written for one harness is worth more if it works in others. Three shared formats exist.

  • Agent Skills. Claude Code's and eve's skills follow the open standard; outside Claude Code only six frontmatter fields are allowed (name, description, license, compatibility, metadata, allowed tools), so Claude-Code-only features do not travel. Codex reads a skills folder shared with other CLIs.
  • Hook names. Qwen Code's events follow Claude Code's names closely, so hook scripts move between them.
  • MCP itself, and AGENTS.md (Chapter 4).

5. Choosing extension points

This book's harness: skills with a listing and on-demand bodies, five hook points (session start, pre tool, post tool, stop, session end) with per-hook failure policies, and an MCP client behind the deferred-tool search from Chapter 3.

6. Research and the Chinese view

  • Progressive disclosure is LangChain's name for loading only skill metadata up front, to protect against context rot.
  • Natural-language harness modules. The NLAH paper treats modules such as a verifier, self-evolution and file-backed state as named natural-language sections, very close to skills.
  • Skills marketplaces in China. In early 2026 Alibaba, ByteDance and Tencent all launched skill marketplaces alongside their desktop agents; 36Kr summarised the stack as: coding builds tools, skills store experience, the harness governs the whole.
  • Chinese practice. Kimi Code's feature registry is the most uniform extension design read for this book; Qwen Code's choice to match Claude Code's hook names is a deliberate bet on portability.

7. Build: skills, hooks and an MCP client

"""Extensibility: skills with progressive disclosure, lifecycle hooks, and a minimal MCP stdio client."""
import json, re, subprocess, threading
from pathlib import Path

# ---- skills: only names and descriptions in the prompt; the body loads on demand ---------------
def parse_skill(path: Path):
    text = path.read_text()
    meta, body = {}, text
    m = re.match(r"^---\n(.*?)\n---\n(.*)$", text, re.S)
    if m:
        body = m.group(2)
        for line in m.group(1).splitlines():
            if ":" in line:
                k, v = line.split(":", 1)
                meta[k.strip()] = v.strip()
    name = meta.get("name") or (path.parent.name if path.name == "SKILL.md" else path.stem)
    return {"name": name, "description": meta.get("description", body.strip().splitlines()[0][:150]),
            "path": path, "body": body}

def load_skills(*roots):
    skills = {}
    for root in roots:
        for p in sorted(Path(root).glob("*/SKILL.md")) + sorted(Path(root).glob("*.md")):
            s = parse_skill(p)
            skills.setdefault(s["name"], s)        # first root wins, so project skills override global ones
    return skills

def skill_catalog(skills):
    """A few lines for the system prompt. The full procedures cost nothing until used."""
    lines = [f"- {s['name']}: {s['description']}" for s in skills.values()]
    return "Skills (load one with the skill tool before following it):\n" + "\n".join(lines)

def skill_tool(skills, name: str):
    s = skills.get(name)
    if not s:
        return f"error: no skill '{name}'. Available: {', '.join(skills)}"
    files = [str(p.relative_to(s["path"].parent)) for p in s["path"].parent.rglob("*")
             if p.is_file() and p != s["path"]] if s["path"].name == "SKILL.md" else []
    extra = "\nSupporting files (read them if the procedure says so): " + ", ".join(files) if files else ""
    return s["body"] + extra

# ---- hooks: deterministic policy that does not depend on the model's judgement ----------------
HOOKS = {"pre_tool_use": [], "post_tool_use": [], "stop": []}

def hook(event):
    def wrap(fn):
        HOOKS[event].append(fn)
        return fn
    return wrap

def run_pre(name, args):
    """Each hook returns None (no opinion), ('block', reason) or ('rewrite', new_args)."""
    for h in HOOKS["pre_tool_use"]:
        r = h(name, args)
        if r and r[0] == "block":
            return None, f"blocked by hook {h.__name__}: {r[1]}"
        if r and r[0] == "rewrite":
            args = r[1]
    return args, None

def run_post(name, args, output):
    for h in HOOKS["post_tool_use"]:
        extra = h(name, args, output)
        if extra:
            output += "\n" + extra
    return output

def run_stop(state):
    """A stop hook may refuse to let the turn end and give the model a reason to continue."""
    for h in HOOKS["stop"]:
        reason = h(state)
        if reason:
            return reason
    return None

# ---- MCP over stdio: JSON-RPC 2.0, one JSON object per line ----------------------------------
class MCPClient:
    def __init__(self, command: list[str]):
        self.proc = subprocess.Popen(command, stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True, bufsize=1)
        self.next_id, self.lock = 1, threading.Lock()
        self.request("initialize", {"protocolVersion": "2025-06-18", "capabilities": {},
                                    "clientInfo": {"name": "harness", "version": "0.1"}})
        self.notify("notifications/initialized")

    def notify(self, method, params=None):
        self.proc.stdin.write(json.dumps({"jsonrpc": "2.0", "method": method, **({"params": params} if params else {})}) + "\n")

    def request(self, method, params=None):
        with self.lock:
            rid, self.next_id = self.next_id, self.next_id + 1
            self.proc.stdin.write(json.dumps({"jsonrpc": "2.0", "id": rid, "method": method, "params": params or {}}) + "\n")
            while True:                                   # skip server notifications until our reply arrives
                msg = json.loads(self.proc.stdout.readline())
                if msg.get("id") == rid:
                    if "error" in msg:
                        raise RuntimeError(msg["error"].get("message"))
                    return msg["result"]

    def tools(self, prefix):
        """MCP tools as our tool specs, namespaced so two servers cannot collide."""
        return [{"name": f"{prefix}__{t['name']}", "description": t.get("description", ""),
                 "parameters": t.get("inputSchema", {"type": "object", "properties": {}})}
                for t in self.request("tools/list")["tools"]]

    def call(self, name, args):
        r = self.request("tools/call", {"name": name, "arguments": args})
        text = "\n".join(c.get("text", "") for c in r.get("content", []) if c.get("type") == "text")
        return ("error: " if r.get("isError") else "") + text

Wiring:

  • Add skill_catalog(skills) to the system prompt (it is stable, so it caches), and a skill(name) tool.
  • Before each tool call run run_pre; after it, run_post. When the model stops, call run_stop; if it returns a reason, append it as a user message and keep looping.
  • For each configured MCP server, add client.tools(prefix) to the tool list and route prefix__name calls to client.call(name, args).

Two hooks to start with: a post_tool_use hook that runs the test suite after any edit or write and appends a one-line result, and a stop hook that refuses to finish while tests fail.

Measure

  1. Count tokens of your skill catalog and of one MCP server's schemas. Put both numbers in a post.
  2. Rerun your 10 tasks with the two hooks on. Did pass rate change? Did steps per task rise?

8. Exercises

  1. Skill budget. Install 100 skills. Measure the listing's token cost, then cap each description and compare. Does the model still pick the right skill?
  2. Formatter hook. Add a post-tool hook that formats edited files and returns a one-line note to the model. Compare with an AGENTS.md line asking for formatting over 20 tasks.
  3. Fail closed. Give your secret-scanning pre-tool hook a "block on failure" policy. Make it crash and confirm the write is blocked with a clear reason.
  4. Stop hook. Block the stop event until the test command passes. Count how many extra steps it adds and how many broken finishes it prevents.
  5. Portability. Take one of your skills and load it unchanged in another harness that supports Agent Skills. Which frontmatter fields did not survive?
