Software factory II: verification gates and self-improvement

In 2026 generating code got cheap and checking it did not. A factory that builds fast without checking its own output only produces problems faster. This chapter derives the two principles behind every useful gate (independence and proportion), then takes eleven design decisions: holdout scenarios, digital twins of outside services, review depth by risk, what an agent reviewer may flag, whether a human reads the code, one attempt or a search over many, gates at the smallest unit, and how a harness may improve itself without overfitting. It compares how leading teams verify, shows the verification pieces in each of the nine harnesses, and keeps the gates and improvement loop you build.

1. The bottleneck moved

A check is useful only if it can disagree with the thing it checks. A test the implementer wrote can share its misunderstanding; a test the implementer can see can be satisfied without solving the task, because the model optimises for whatever signal it is given (fact 5). So the strongest check is one the generator neither wrote nor saw. Checks also cost something, so it is rational to spend them where a mistake costs most. Independence and proportion explain every gate in this chapter.

The data agree. One industry report shown at AI Engineer World's Fair 2026 found that with high AI adoption, pull requests received 25% more review comments and 31.3% more pull requests skipped review entirely. Qodo puts the conclusion plainly: the quality layer that works is one the generator does not control.

2. The decisions, one at a time

Decision 1. Does the generator see the tests?

StrongDM's software factory is built on scenarios: specifications plus scenarios drive agents that write code and run harnesses until they converge, and validation is scenario-based. The scenarios the code is judged on are a holdout, curated by people and kept from the generator, the same principle as a machine-learning test set. The repository's own tests are still run, but they are the generator's tests, and they can be wrong in the same way the code is.

Decision 2. How do you test against outside services?

Real integrations (identity providers, chat, payments) are slow, rate-limited, cost money and cannot be reset between runs. StrongDM built a Digital Twin Universe: behavioural copies of services such as Okta and Slack that agents can run thousands of scenarios against. A Baidu Cloud lead made the same point about agentic training: the biggest obstacle is reproducing real environments, not the model. For a coding factory the twin can be modest: a fake API with recorded responses and a reset button.

Decision 3. How deep is review, and for which changes?

Not every change deserves the same scrutiny. CodeRabbit proposes a review gate whose depth increases with risk and blast radius: a typo fix passes on repository checks, a change to authentication goes to deep review and a person.

Decision 4. What may an agent reviewer flag?

A model reviewer asked to "find problems" will always find some, and a review buried in speculation trains people to ignore it. Codex's review rubric is a short course in useful review: flag only discrete, actionable bugs introduced by the change, that the author would fix if told, without speculating about code you cannot show is affected. Foreman's reviewer (Chapter 13) adds independence (another vendor, diff only) and evidence for each verdict against each criterion. OpenAI's Codex team described a loop where Codex reviews its own pull request, requests more agent reviews locally and in the cloud, and iterates until the reviewers are satisfied, with application logs and metrics exposed to the agent.

Decision 6. One attempt, or a search over many?

Because each attempt is a sample, several attempts give several different patches, and some are better than others. Trae Agent made this its research contribution.

Decision 7. Gates at the smallest unit

The cheapest failures should be stopped before any review sees them.

  • Kimi Code validates every completed tool call against its schema and asks the model to retry an invalid one without executing it (Chapter 2).
  • Qwen Code rejects a change to a file the model has not read, or whose content changed since (Chapter 3), and fails its safety classifier closed (Chapter 7).
  • Claude Code lets a hook be an agent that verifies before deciding, and the paper lists a Verification agent, so the check runs in a context that did not produce the work.
  • Trae Agent refuses to finish with an empty patch.

Decision 8. May the harness improve itself?

An improvement loop is a generator of harness changes, and your eval is its check. Several systems now close that loop.

Decision 9. How do you keep self-improvement honest?

The trap

A loop that optimises against your eval will overfit to your eval. Keep a holdout set the proposer never sees; change one thing per round so you know what helped; require every rule it adds to name the failure it fixes (Chapter 4's zero-tolerance AGENTS.md); and read every accepted change yourself. Block writes to the harness's own configuration from inside a run (Chapter 8).

Decision 10. What kind of feedback goes back to the generator?

Chinese practitioners describe harness feedback as semantic gradient descent: natural-language feedback improves outputs the way gradients improve weights. Two rules follow from the analogy. The feedback must point in a direction (what to change, as Codex's rubric requires, not just "this is wrong"). And it must be constructive rather than hostile, because a model told only that it failed will often change something irrelevant.

Decision 11. How do you know the gates work?

Gates are themselves checks, and checks need checking. Plant known bugs and count how many each gate catches; track how often a human overturns an agent review; measure how many revisions CI-failure classification saved (Chapter 13). A gate that never fires is either unnecessary or broken; find out which.

6. Choosing gates

This book's gates: repository checks in the implementer's container, a holdout of ten scenarios the agent never sees, a reviewer on another vendor limited to concrete bugs, depth by a simple risk rule on touched paths, and an improvement loop that proposes one change per round and must pass the holdout before a person reviews it.

7. The Chinese view

  • Chinese practitioners describe harness feedback as semantic gradient descent, and insist it stays constructive rather than hostile.
  • Woshipm's essay "Harness is the new dataset" argues that harness design is now the main lever for agent capability gains, organised into information, execution and feedback layers.
  • A Baidu Cloud lead told Beijing News that the biggest obstacle to agentic training is reproducing real environments, the insight behind StrongDM's digital twins.
  • ByteDance's Trae Agent made search over attempts plus a selector its research contribution; Kimi Code's per-call schema check is the smallest gate read for this book.

8. Build: gates and an improvement loop

"""Verification gates the generator cannot see, review depth by risk, and a harness that improves from its traces."""
import fnmatch, json, subprocess
from pathlib import Path

# ---- gate 1: holdout scenarios ----------------------------------------------------------------
def holdout_gate(workdir, scenarios_dir):
    """Run scenario checks stored outside the implementer's sandbox (StrongDM keeps holdouts the agent never sees)."""
    results = {}
    for s in sorted(Path(scenarios_dir).resolve().glob("*.sh")):
        p = subprocess.run(["bash", str(s)], cwd=workdir, capture_output=True, text=True, timeout=600)
        results[s.stem] = p.returncode == 0
    return all(results.values()), results

# ---- gate 2: review depth by risk -----------------------------------------------------------------
RISKY_PATHS = ["*auth*", "*payment*", "*migrations/*", ".github/workflows/*", "*secrets*", "Dockerfile"]

def risk(diff_files: list[str], lines_changed: int) -> str:
    """'low' -> agent review is enough; 'high' -> a human must read the code (review depth grows with blast radius)."""
    if any(fnmatch.fnmatch(f, pat) for f in diff_files for pat in RISKY_PATHS):
        return "high"
    return "high" if lines_changed > 400 else "low"

# ---- the improvement loop -----------------------------------------------------------------------
PROPOSER_PROMPT = """You improve an AI agent harness. Below are failing eval runs with their raw traces and the
current harness configuration. Find ONE root cause that appears in several failures and propose ONE change to
the configuration (AGENTS.md rules, tool descriptions, limits or hooks). Every rule you add must name the failure
it prevents. Reply JSON only: {"diagnosis": "...", "evidence": ["trace ids"], "file": "...", "new_content": "..."}"""

def failing_runs(results, traces_dir, limit=5):
    """Raw traces of failed runs, not summaries: Meta-Harness found raw traces are what make diagnosis work."""
    out = []
    for r in results:
        if not r["pass"] and r.get("trace"):
            out.append({"task": r["task"], "trace": Path(traces_dir, r["trace"]).read_text()[-20_000:]})
    return out[:limit]

def improve_once(config_dir, propose, evaluate, min_lift=0.05, max_cost_increase=0.2):
    """propose(prompt, material) -> dict; evaluate(config_dir) -> {'pass_rate', 'mean_usd', 'runs'}.
    Accept a change only if it beats the current harness on the eval without a large cost increase."""
    base = evaluate(config_dir)
    material = json.dumps({"failures": failing_runs(base["runs"], config_dir),
                           "config": {p.name: p.read_text() for p in Path(config_dir).glob("*.md")}})
    change = propose(PROPOSER_PROMPT, material)
    target = Path(config_dir, Path(change["file"]).name)       # stay inside the config folder
    old = target.read_text() if target.exists() else None
    target.write_text(change["new_content"])
    new = evaluate(config_dir)
    lift = new["pass_rate"] - base["pass_rate"]
    cost_ok = new["mean_usd"] <= base["mean_usd"] * (1 + max_cost_increase) or base["mean_usd"] == 0
    if lift >= min_lift and cost_ok:
        return {"accepted": True, "lift": round(lift, 3), "diagnosis": change["diagnosis"]}
    if old is None:                                              # revert: the change did not earn its place
        target.unlink()
    else:
        target.write_text(old)
    return {"accepted": False, "lift": round(lift, 3), "diagnosis": change["diagnosis"]}

Wiring:

  • Keep holdout scenarios in a folder outside the implementer's sandbox. Run holdout_gate after the reviewer approves; a failure sends feedback without the scenario text.
  • Call risk() on the PR's files; for high, label the PR needs-human-review and do not auto-merge anything.
  • Store a trace file per eval run (Chapter 10) and its path in the run record. evaluate runs your paired eval on a training set of tasks; keep 5 tasks back as a holdout and check them only after an accepted change.
  • Run improve_once weekly. Commit each accepted change with its diagnosis in the message.

Measure

Run four improvement rounds. For each, report the diagnosis, train lift, holdout lift and whether you agree with the change. A change with train lift but no holdout lift is overfitting; record it.

9. Exercises

  1. Holdout. Write ten scenarios the agent never sees. Run your factory on five issues and score with both the repo's tests and the holdout. Where do they disagree?
  2. Planted bugs. Plant ten known bugs in diffs and run each gate. Which gate catches which?
  3. Ensemble. Run five attempts per issue, drop those failing regression tests, and let a selector pick. Compare pass rate and cost with one attempt.
  4. Rubric. Review 20 diffs with an open "find problems" prompt and with a rubric limited to concrete bugs. How many findings does each give, and how many are real?
  5. Improvement loop. Let an agent propose one AGENTS.md change per round from failing traces for five rounds. Track visible and holdout scores separately.
