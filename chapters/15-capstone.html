Capstone: benchmark and retrospective

Sixteen weeks ago the loop was 120 lines. Now it has a provider layer, typed tools, cache-stable context, compaction, session trees, a safety gate, skills and hooks, subagents and Code Mode, evals, durability, a server, channels and a factory. This chapter measures it honestly against Pi and fx on the same tasks, writes down what each design choice bought, and tags version 1.0.

Level: advanced Time: about 20 hours Needs: all earlier chapters Facts checked: 22 Nov 2026

1. Why compare against real harnesses

Your weekly eval tells you whether your harness improved. It does not tell you whether it is good. Reason from what a score is: a pass rate is produced jointly by the model, the harness and the tasks, and the model's outputs vary from run to run (fact 5). To learn what the harness contributes, you must hold the other two fixed and repeat enough to see through the noise. Running Pi and fx on the same tasks, with the same model where they allow it, separates three things: the model, the harness and the task. Several 2026 papers make the same point: benchmark scores mix model and harness, so honest comparisons hold one fixed while changing the other (Same model, different harness).

Safety

Pi has no permission gate and fx ask --full-access turns fx's checks off. Run every harness in this chapter inside a container with only the task's copy of the repository mounted.

2. Method

  1. Tasks. Your test tasks from Chapter 1 and 10, plus at least 10 new ones you have never tuned against (a holdout). Optionally add a subset of Terminal-Bench 2.0 or Alibaba's Terminal-Bench Pro through their official runners.
  2. Models. Use the same model for all three where possible (fx talks to one provider at a time through Vercel AI Gateway, a subscription or any OpenAI-compatible endpoint; Pi supports most providers). Then repeat with each harness's preferred model.
  3. Repeats. At least 3 runs per task per harness. Report pass rate, mean time, mean cost and failure categories.
  4. Failure analysis. Read every failed transcript and label it: wrong plan, wrong edit, gave up, stopped early, tool misuse, environment, timeout.

3. Build: the comparison runner

"""Capstone: run three harnesses headless on the same tasks, same model where possible, and compare."""
import json, shutil, subprocess, sys, tempfile, time
from pathlib import Path

# Each harness is a command that takes the prompt as its last argument and works in the current directory.
# Run every one of them inside a container (Chapter 7): fx in full-access mode and Pi have no gate.
HARNESSES = {
    "mine": ["harness", "ask", "--json"],          # your CLI from Chapter 12
    "pi":   ["pi", "--print"],                     # Pi's non-interactive mode
    "fx":   ["fx", "ask", "--json"],               # fx's scripting mode; final answer in .final_output
}

def run(harness, cmd, task, repo, timeout=1800):
    work = Path(tempfile.mkdtemp(prefix=f"cap-{harness}-{task['id']}-"))
    shutil.copytree(repo, work, dirs_exist_ok=True)
    t0 = time.time()
    try:
        p = subprocess.run(cmd + [task["prompt"]], cwd=work, capture_output=True, text=True, timeout=timeout)
        out, err = p.stdout[-4000:], p.returncode
    except subprocess.TimeoutExpired:
        out, err = "timeout", -1
    passed = subprocess.run(["bash", str(task["check"])], cwd=work, capture_output=True).returncode == 0
    shutil.rmtree(work, ignore_errors=True)
    return {"harness": harness, "task": task["id"], "pass": passed, "secs": round(time.time() - t0, 1),
            "exit": err, "output_tail": out[-300:]}

def main(tasks_dir, repo, repeats=3, out="capstone.json"):
    tasks = [{"id": d.name, "prompt": (d / "prompt.md").read_text(), "check": d / "check.sh"}
             for d in sorted(Path(tasks_dir).resolve().iterdir()) if (d / "prompt.md").exists()]
    rows = [run(h, cmd, t, repo) for t in tasks for h, cmd in HARNESSES.items() for _ in range(repeats)]
    Path(out).write_text(json.dumps(rows, indent=1))
    print(f"{'harness':8} {'pass rate':>9} {'mean secs':>9}")
    for h in HARNESSES:
        r = [x for x in rows if x["harness"] == h]
        print(f"{h:8} {sum(x['pass'] for x in r) / len(r):9.0%} {sum(x['secs'] for x in r) / len(r):9.1f}")

if __name__ == "__main__":
    main(*sys.argv[1:3])

6. Lessons the four harnesses teach

  • Pi: a small core you can read in an afternoon beats a large one you cannot. Add a feature when its absence costs you, not before.
  • fx: treat your own outputs as untrusted. fx checks its summaries against the record and makes its safety reviewer prove its claims.
  • eve: shape the loop for durability from day one, and keep secrets out of the place where the model's commands run.
  • nanocode: respect each model's native harness, and state your invariants as numbers you can test.
  • Pi Durable: write the specification before the code when correctness is hard. The effect sandwich fits on a napkin and prevents a class of bugs.
  • Chinese practice: every rule must trace to a failure, and the harness, not the model, is where most teams now compete.

7. Release checklist for v1.0

  • README with a 60-second quick start, the results table and a link to this book.
  • A container image that runs the harness safely by default.
  • The eval suite and holdout in the repo, with instructions to reproduce your numbers.
  • An AGENTS.md where every rule names the failure that created it.
  • A tagged release and a final post: what you built, what it scores, what you would do differently.
