Stage 2 · Context · Chapter 4

Instructions and context assembly

The model keeps nothing between calls (fact 2), so every request must carry everything the model should know: who it is, what tools it has, the project's rules, where it is running, and what has happened so far. Every token of that is paid for on every step unless it is an identical prefix (fact 4), and quality drops as the input grows (fact 3). Context assembly is the job of deciding what goes into the request, in what order, under which role, and how changes get in without breaking the cache. This chapter derives the layout, walks through eight design decisions, shows how nine harnesses assemble their requests, and keeps the cache-stable assembler you build.

Level: intermediate Time: about 12 hours with the build Needs: Chapters 1 to 3 Harnesses read: Pi, eve, fx, nanocode, Codex, Claude Code, Kimi Code, Qwen Code, Trae Agent
Before you start: skip check
  1. The user edits AGENTS.md halfway through a session. Why does Codex append the new text with a notice instead of replacing the old text where it sits?
  2. Claude Code delivers CLAUDE.md as a user message after the system prompt, not inside the system prompt. Name one benefit and one cost.
  3. A model answered "no task received" even though the task was in its input. What had the harness done wrong, and how did Qwen Code fix it?
  4. Why do fx and Kimi Code wait until the agent touches a folder before telling it about that folder's rules?
Answers
  1. Replacing text early in the request changes the prefix, so the provider recomputes everything after it on the next step. Appending keeps the cached prefix valid; the notice ("these instructions replace all previously provided AGENTS.md instructions") tells the model which version wins.
  2. Benefit: it can be appended and reloaded without touching the system prompt, and it cannot pose as the harness's own rules. Cost: user-role text carries less authority than system text, so it guides rather than binds; the documentation points to hooks for anything that must be enforced.
  3. It placed reminders, hook output and memory after the user's own text, so the real task sat in the middle of a long message. Qwen Code moves injected context ahead of the user's text so the instruction is the last thing the model reads.
  4. Loading every folder's rules at the start costs tokens on every step for rules that may never apply. Delivering them when the agent first reaches the folder costs tokens only when they matter, and puts them at the end of the context, where they are noticed.

1. What the model is actually told

Start from what a request is. It is one long sequence of tokens sent to the provider. The provider does not know which part is "the system prompt" and which is "history" except by role markers. The model reads all of it every time. Three forces shape how a harness lays it out:

Sort the content by how often it changes and the layout falls out. What never changes in a session goes first, what changes once per session next, what changes every step last. Changes arrive at the end, which is both the cheapest place (only new tokens are paid in full) and the place the model attends to most.

2. The decisions, one at a time

Decision 1. How long is the base prompt?

The base prompt is the harness's own voice: who the agent is, how it should work, what it must never do. Its length is a bet about the model. A model trained inside this harness already knows how to behave and needs few words; a general model, or a model the harness did not train, needs the rules spelled out.

The other harnesses spread across the same range. Pi's default preamble is one sentence ("You are a coding assistant running inside pi..."), followed by generated lists of the active tools and a few rules (be concise, show file paths), and the user can replace it entirely. fx's is an operating manual of about 1,000 words in sections (identity, workspace behaviour, where to look for answers, how to talk to the user, safety), with per-model overlays. nanocode pins each vendor's own prompt byte for byte, so a model sees exactly the text it was trained with (Chapter 2). Trae Agent has one fixed prompt for every run, which keeps experiments comparable.

Short prompt (Pi)Operating manual (fx, Codex general models)Pinned vendor prompt (nanocode)
ProCheap, transparent, easy to replaceConsistent behaviour across models; encodes lessonsMatches training, so models behave as intended

Decision 2. Which project files, found how?

Project instructions are the user's voice: build commands, conventions, things the agent got wrong before. Every harness but Trae Agent reads them from markdown files in the repository. The questions are which names, which directories, and what happens when several apply.

Three details show the design thinking. First, name compatibility: Pi accepts CLAUDE.md as a fallback, so it reads Claude Code projects unchanged; Claude Code reads only CLAUDE.md, and its documentation suggests a one-line @AGENTS.md import or a symlink to share one file. Second, duplication: nanocode skips a file whose content is identical to one already loaded, and Pi lets a nested git worktree's file shadow the main repository's, so the same rules are not paid for twice. Third, Claude Code's imports: a CLAUDE.md can pull in other files with @path, up to four hops deep, and the first external import triggers an approval dialog. Its documentation is explicit that imports load at launch and save no context; they are for organisation, not for loading less.

Decision 3. Which role do instructions travel in?

Providers give roles different weight: system (or developer) text is treated as the operator's rules, user text as the request. Where project instructions go changes both their authority and how they can be updated.

Claude Code's documentation states the trade plainly: CLAUDE.md is delivered as a user message after the system prompt, it is context rather than enforced configuration, and anything that must always hold belongs in a hook that blocks the action. Codex sends its base instructions and its permission and collaboration-mode instructions as developer items, and AGENTS.md and the environment description as user items, each a separate, typed fragment. That typing is what makes decision 5 possible.

Decision 4. When do rules for a folder arrive?

A large repository may have instruction files in dozens of folders. Loading all of them at the start pays for rules that may never apply. Loading none of them means the agent edits billing/ without knowing its rules. The middle path is to deliver a folder's rules when the agent first reaches it.

The reminder line in fx is worth dwelling on. Its source notes the reason: models tend to apply a rule on the turn it arrives and forget it later, because it is now deep in the middle of a long context (fact 3). A one-line reminder at the end costs a few tokens and restores the rule's position.

Decision 5. How do changes get in mid-session?

The working directory changes, a file of rules is edited, the date rolls over, tools connect, the permission mode changes. The naive design rebuilds the request with the new values in place, which changes the prefix and re-prices the whole history. Every serious harness appends instead.

Codex's design generalises the rule. Each piece of world state the model can see is a typed section with a stable identity and a snapshot of what the model was last told. On every step the harness asks each section for the difference. If nothing changed, nothing is added. The snapshots are saved with the session, so a resumed session knows what the model already saw. Pi takes the same idea from the transcript side: the system prompt is replayed from the transcript, so a replay always reproduces exactly what the model was shown at each point (Chapter 6).

There is one more defence. A tool result is untrusted text (Chapter 7), so a file could contain something that looks like a context update. fx escapes its update tag in tool output so a file cannot forge one.

Decision 6. What does the harness say on its own?

Besides the user's files, a harness injects its own short messages: reminders, warnings, notices. They are how the harness talks to the model between the user's turns, and they are usually wrapped in a recognisable envelope (Kimi Code and Qwen Code use a system-reminder tag) so the model and the harness can tell them from the user's words.

The Qwen Code case is a good lesson in fact 3. The user's message was assembled from independent sources: reminders before the prompt, then hook output and a memory catalog after it. On a long multi-part instruction the real task ended up in the middle, and the model reported that it had received no task. The fix moves the injected run ahead of the user's text in the copy sent to the provider, leaving the stored history unchanged, and every request that shares the cache must apply the same reordering or it re-pays the whole history.

Decision 7. How big may instructions be, and what survives compaction?

Instructions are paid for on every step, and longer instructions are followed less reliably. Harnesses put a number on it.

HarnessBudgetWhat happens at the limit
Codex32 KiB for project instructions by defaultText is cut, and the model is told to trim its project instructions
nanocodeA maximum size per instruction fileFile capped; duplicate files skipped with an "included once" note
Claude CodeTarget under 200 lines per CLAUDE.md; MEMORY.md loads its first 200 lines or 25 KBCLAUDE.md loads in full regardless; longer files reduce adherence

Claude Code adds two thrifty details: block-level HTML comments in CLAUDE.md are stripped before injection, so notes to human maintainers cost no tokens, and its auto-memory index loads at start while topic files are read only on demand. Compaction (Chapter 5) raises a second question: when the history is summarised, do the instructions survive? Claude Code re-reads the project-root CLAUDE.md from disk and re-injects it after compaction; nested files are not re-injected and reload the next time the agent reads a file in their folder. Instructions given only in conversation are lost, which is why the documentation tells users to move them into a file.

Decision 8. Whose instructions are trusted?

A repository you just cloned can contain an AGENTS.md written by anyone. Loading it means a stranger writes part of your agent's prompt.

  • Codex loads no project instructions for a project the user has not trusted.
  • Claude Code asks before following imports that point outside the project, and honours a custom memory location from project settings only after the workspace trust dialog. Managed CLAUDE.md from an organisation cannot be excluded by users.
  • fx escapes its context-update tag in tool output, so file content cannot pose as the harness.
  • All of them treat instructions as guidance. Permissions and sandboxes, not prompt text, are what stop a harmful action (Chapter 7).

5. Choosing a layout

This book's assembler follows the stack in Figure 2: a fixed base prompt and tool list, AGENTS.md from root to working directory with a byte budget, environment facts at session start, and every change appended as a tagged update at the tail. The exercises add section snapshots, folder rules on first touch and a reminder envelope.

6. Research and the Chinese view

  • Natural-Language Agent Harnesses (Tsinghua, March 2026) takes the idea furthest: contracts, roles, stages and failure handling are written as editable natural language and executed by a shared runtime. AGENTS.md is the everyday version.
  • Attention recitation. Manus described rewriting a todo list at the end of the context so the goal stays in recent attention. fx's folder-rule reminder and Kimi Code's escalating reminders are the same move.
  • Short files as maps. OpenAI's Codex team described keeping AGENTS.md short and using it as an index into a structured docs folder rather than one long file, matching Claude Code's advice to stay under 200 lines and use path-scoped rules.
  • Chinese practice. Kimi Code built reminders as a feature system with escalation for repeated tool calls; Qwen Code, inheriting Gemini CLI's hierarchical context files, added a tested context order after a production bug. Chinese practitioners popularised a zero-tolerance rule for AGENTS.md: every line must trace to a real failure. This book adopts it.

7. Build: a cache-stable context assembler

"""Context assembly: a stable prefix, project instructions, and changes appended at the end, never in the prefix."""
import os, platform, subprocess
from pathlib import Path

MAX_INSTRUCTION_BYTES = 32 * 1024            # Codex caps each source at 32 KiB
CANDIDATES = ["AGENTS.override.md", "AGENTS.md", "CLAUDE.md"]   # first match per directory wins (Pi, nanocode)

BASE_PROMPT = """You are a coding agent working in the user's repository.
- Inspect before you answer: read files and run commands instead of guessing.
- Read a file before editing it. Keep edits small and inside the requested scope.
- After changing code, run the relevant tests and report the result.
- If a tool fails, read the error before retrying. Do not repeat an action without new evidence.
- Ask the user only for decisions you cannot make from the repository.
Runtime facts may change during the session. When they do, a <context-update> block is appended to the
latest message; its values replace earlier ones."""

def git_root(start: Path) -> Path:
    try:
        out = subprocess.run(["git", "rev-parse", "--show-toplevel"], cwd=start, capture_output=True, text=True)
        return Path(out.stdout.strip()) if out.returncode == 0 else start
    except FileNotFoundError:
        return start

def instruction_file(directory: Path):
    for name in CANDIDATES:
        p = directory / name
        if p.is_file():
            return p
    return None

def discover(cwd: Path, home: Path = Path.home() / ".harness"):
    """Global file first, then every directory from the repo root down to cwd. Identical files load once."""
    root, files, seen = git_root(cwd), [], set()
    dirs = [home] + [root] + [root / Path(*cwd.relative_to(root).parts[:i + 1]) for i in range(len(cwd.relative_to(root).parts))]
    for d in dirs:
        f = instruction_file(d)
        if f is None:
            continue
        text = f.read_text(encoding="utf-8-sig")[:MAX_INSTRUCTION_BYTES]
        if text in seen:                     # nanocode: "identical to X; included once"
            continue
        seen.add(text)
        files.append((f, text))
    return files

def environment(cwd: Path) -> dict:
    def git(*a):
        r = subprocess.run(["git", *a], cwd=cwd, capture_output=True, text=True)
        return r.stdout.strip() if r.returncode == 0 else ""
    return {"cwd": str(cwd), "os": platform.system(), "shell": os.environ.get("SHELL", "sh"),
            "git_branch": git("branch", "--show-current") or "none"}

def system_prompt(cwd: Path) -> str:
    """Built once per session. Nothing in here may change mid-session, or the prompt cache misses."""
    parts = [BASE_PROMPT]
    for path, text in discover(cwd):
        parts.append(f'<instructions source="{path}">\n{text}\n</instructions>')
    env = environment(cwd)
    parts.append("<environment>\n" + "\n".join(f"{k}: {v}" for k, v in env.items()) + "\n</environment>")
    return "\n\n".join(parts)

class ContextTracker:
    """Appends changes to the end of the latest message (fx's <fx-context-update> pattern)."""
    def __init__(self, cwd: Path):
        self.env = environment(cwd)
        self.loaded = {str(p.parent) for p, _ in discover(cwd)}   # folders whose rules are already in context

    def update(self, cwd: Path) -> str:
        """Call after each tool batch; returns text to append to the last tool result, or ''."""
        now, notes = environment(cwd), []
        changed = {k: v for k, v in now.items() if self.env.get(k) != v}
        if changed:
            notes.append("<context-update>\n" + "\n".join(f"{k}: {v}" for k, v in changed.items()) + "\n</context-update>")
            self.env = now
        return "\n".join(notes)

    def folder_rules(self, touched_path: str) -> str:
        """When a tool first touches a folder with its own AGENTS.md, attach those rules to that tool result."""
        d = Path(touched_path).resolve()
        d = d if d.is_dir() else d.parent
        f = instruction_file(d)
        if f is None or str(d) in self.loaded:
            return ""
        self.loaded.add(str(d))
        return f'\n<instructions source="{f}" scope="{d}">\n{f.read_text(encoding="utf-8-sig")[:MAX_INSTRUCTION_BYTES]}\n</instructions>'

How to use it:

  • Call system_prompt(cwd) once at session start and store it in the state.
  • After each tool batch, call tracker.update(cwd) and append any result to the last tool result. If a tool touched a path, also append tracker.folder_rules(path).
  • Log cached_tokens / input_tokens per step (from Chapter 2). After the second step it should stay high.

Measure

  1. Write an AGENTS.md for your test repo with three rules, each tied to a failure you saw in Stage 1. Rerun the 10 tasks.
  2. Add a rule that is not tied to any failure (for example "write clean code"). Does it change anything you can measure? If not, delete it.
  3. Compare cache hit share with and without the tracker: in the "without" version, rebuild the system prompt every step.

8. Exercises

  1. Measure the cache. Run a 20-step task twice: once rebuilding the environment block in place when the working directory changes, once appending an update. Record cached and uncached input tokens per step for both.
  2. Section snapshots. Turn environment, project instructions and permission mode into sections that store the last value sent. Emit only diffs, with a replacement notice. Resume a saved session and check nothing is re-sent.
  3. Folder rules on first touch. Put an AGENTS.md in a subfolder with a rule the agent would otherwise break. Deliver it when a tool first touches that folder; add a reminder line on later visits. Compare compliance with and without the reminder.
  4. The sandwich bug. Append a long reminder after the user's text and test a multi-part instruction. Then move injected context ahead of the user's text. Does the model miss the task less often?
  5. Zero-tolerance AGENTS.md. Write your AGENTS.md so every line has a comment naming the failure that created it. Strip comments before sending, as Claude Code does.
