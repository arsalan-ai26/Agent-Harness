Stage 3 · Control · Chapter 10

Verification, evals and observability

Every output is a sample (fact 5). That has three consequences: an agent cannot confirm its own work by thinking harder, one run of a harness tells you almost nothing about the next, and a harness can get slower and more expensive while its pass rate looks unchanged. This chapter derives three feedback loops from those consequences (inside a turn, across harness versions, in operation), then takes ten design decisions: what must happen before the agent may stop, who judges, what an eval runs against, how to compare versions, what a trace records and who may see it, how cost is counted, whether the harness's own speed is tested, and how real failures become tests. It shows each harness's approach and keeps the trace, cost and paired-eval runner you build.

Level: intermediate to advanced Time: about 14 hours with the build Needs: Chapters 1 to 9 Harnesses read: Pi, eve, fx, nanocode, Codex, Claude Code, Kimi Code, Qwen Code, Trae Agent
Before you start: skip check
  1. Why does asking the model "are you sure the tests pass?" add almost no information?
  2. Version B passes 62% of tasks, version A 58%, each run once over 50 tasks. Is B better? What would you do instead?
  3. Codex's rollout traces can only be replayed by the same binary that recorded them. Why is that a feature?
  4. Why does fx fail a pull request if a command like help takes more than 2 ms?
Answers
  1. The answer is another sample from the same model reading the same context. Only something outside the model (running the tests) adds new information.
  2. You cannot tell: four points on 50 single runs is within noise. Run both versions on the same tasks several times and compare per task (paired), which removes the large differences between tasks.
  3. A replay by different code could quietly disagree with what actually ran; tying it to the recording binary guarantees the replay shows the truth.
  4. Speed and size are properties of the harness like correctness, and they rot silently unless a test fails when they get worse.

1. Three feedback loops

Each loop comes from fact 5. Inside a turn, the model cannot verify its own claim by thinking harder, because the check would be another sample from the same model on the same context; only something outside the model adds information. Across versions, one run of a task is a coin flip with an unknown bias, so you need repeats and you need to compare versions on the same tasks. In operation, cost and time grow with session length (facts 2 and 4), so a harness can get worse in money and latency while its pass rate stays flat; you only see it if every step records what it spent.

2. The decisions, one at a time

Decision 1. What must happen before the agent may stop?

The most common failure of coding agents is declaring success too early. The fix is to make stopping a checked action.

Decision 2. Who judges the work?

Judges differ in how much new information they add and how much they can be fooled.

Decision 3. What does an eval run against?

An eval is only as good as its resemblance to real use. The harnesses choose different points on the spectrum from fast and fake to slow and real.

Decision 4. How do you compare two versions?

Tasks differ from each other far more than two harness versions differ on any one task. If you compare overall averages, that task-to-task spread drowns the effect you are looking for. Compare per task instead.

Pi's documentation-lift evals are the template for any harness change: run every case without and with the change, several times each, in isolated containers, and report the per-case difference. Record tokens and cost alongside pass rate, because a change that adds one point of pass rate and doubles cost is usually a loss (fact 4).

Decision 5. What does a trace record, and who sees it?

A trace is the record of what the harness actually did: every request, response, tool call and result, with timing and tokens. The design questions are completeness, privacy and faithfulness.

Codex's documentation draws the line clearly: tracing is not telemetry. Its rollout traces are written only when a developer turns them on, contain the raw evidence of a run, and can be replayed into a graph for inspection, but only by the same binary that recorded them, so the replay cannot quietly disagree with what ran. Trae Agent solves a different problem, reading long trajectories: its Lakeview step asks a model to label every step twice, a general description in at most 10 words and bug-specific details in at most 30, so a person can scan a 200-step run. eve shows every session's turns, tool calls, reasoning, timing and token use in its platform dashboard with no instrumentation.

Decision 6. How is cost counted?

Cost has to be attributable: which agent, which turn, which task spent it. nanocode computes tokens, dollars and machine time for each step as a pure function over the event log, then rolls them up by agent, turn, board task and commit. Because it is computed from the log, it can be recomputed for any past session when prices change, and it cannot disagree with what happened. Qwen Code keeps a usage dashboard and per-session token accounting; Chapter 2 covered how each provider's usage report is normalised.

Decision 7. Is the harness's own speed tested?

A harness adds latency on every step and every keystroke. fx treats that as a correctness property: its continuous integration fails a pull request if any benchmarked command (such as help or status) takes more than 2 ms on Linux, and release binaries must fit a size budget. It also benchmarks long-turn memory and approval review. nanocode's simulator checks its memory invariants as numbers. Without such tests, a harness gets slower one reasonable change at a time.

Decision 8. Do guards double as measurements?

The guards from earlier chapters (loop detection, duplicate-call detection, the compaction circuit breaker, the repeat breaker) each fire for a reason. Qwen Code records why a turn stopped, so the guards become signals: a rise in loop-detector stops after a model change is a regression found without a single new eval. Codex records turn aborts as typed items; Kimi Code's repeat breaker escalates in stages that can be counted (Chapter 4).

Decision 9. How do real failures become tests?

Mitchell Hashimoto's habit is the simplest form of loop 3 feeding loop 2: every time the agent makes a mistake, change the harness (a line in AGENTS.md, a tool, a hook) so it cannot make that mistake again. Made measurable, it becomes: save the failing session, turn it into an eval case with a check, make the fix pass it, and keep the case forever. Pair it with Chapter 4's zero-tolerance rule for AGENTS.md: every line traces to a recorded failure.

Decision 10. Who reviews what the agent produced?

For coding agents, the final check is often a review of the diff. Codex has a review command with a rubric limited to concrete bugs the change introduced. Claude Code and Qwen Code have review commands and agents. Trae Agent, for benchmarks, generates many candidate patches, runs regression tests, and lets a selector agent choose among the survivors (Chapter 14). The common rule: the reviewer must not be the context that wrote the code, or it will share its blind spots.

5. Choosing what to build first

This book's setup: a stop gate that runs your tests, a JSONL trace per run with per-step tokens and cost, a cost fold over the trace, and a paired eval runner that runs every case with both versions three times in containers.

6. Research and the Chinese view

  • Self-verification is the biggest lever. LangChain's Terminal Bench gains came mostly from making the agent verify its work and from tracing.
  • Harness optimisation from traces. Meta-Harness gives a coding agent the raw traces, code and scores of past harness versions and lets it propose the next; access to raw traces rather than summaries is the key. Later work on test-time harness evolution extends this.
  • Scores mix model and harness. A September 2026 survey proposes evaluating model, harness, environment and evaluator as four separate factors.
  • Chinese view. Chinese write-ups describe harness feedback as semantic gradient descent: natural-language feedback steers outputs the way numeric gradients steer weights. Alibaba published Terminal-Bench Pro as a harder benchmark, and ByteDance's Trae Agent is the most evaluation-shaped harness in this book.

7. Build: traces, cost and a paired eval runner

"""Traces, cost, and a paired A/B eval runner: the harness's feedback loop."""
import json, shutil, statistics, subprocess, tempfile, time, uuid
from contextlib import contextmanager
from pathlib import Path

# ---- tracing: one JSONL line per span ----------------------------------------------------------
class Tracer:
    def __init__(self, path="traces.jsonl"):
        self.path, self.stack = Path(path), []
    @contextmanager
    def span(self, kind, **attrs):            # kind: "turn", "model", "tool", "compaction"
        sid, start = uuid.uuid4().hex[:8], time.time()
        parent = self.stack[-1] if self.stack else None
        self.stack.append(sid)
        rec = {"id": sid, "parent": parent, "kind": kind, **attrs}
        try:
            yield rec                         # callers add fields: tokens, cost, ok, error
        finally:
            self.stack.pop()
            rec["ms"] = round((time.time() - start) * 1000)
            with self.path.open("a") as f:
                f.write(json.dumps(rec, default=str) + "\n")

def report(path="traces.jsonl"):
    """Where did time, tokens and money go? Roll spans up by kind (nanocode's cost fold, simplified)."""
    rows = [json.loads(l) for l in Path(path).read_text().splitlines()]
    by = {}
    for r in rows:
        k = by.setdefault(r["kind"] if r["kind"] != "tool" else f"tool:{r.get('name')}", {"n": 0, "ms": 0, "tokens": 0, "usd": 0.0, "errors": 0})
        k["n"] += 1; k["ms"] += r.get("ms", 0); k["tokens"] += r.get("tokens", 0)
        k["usd"] += r.get("usd", 0.0); k["errors"] += 0 if r.get("ok", True) else 1
    return by

# ---- evals: a task is a folder with prompt.md and check.sh; the scratch repo is copied fresh each run
def load_tasks(root):
    return [{"id": d.name, "prompt": (d / "prompt.md").read_text(), "check": d / "check.sh"}
            for d in sorted(Path(root).resolve().iterdir()) if (d / "prompt.md").exists()]

def run_once(agent, task, repo):
    """agent(prompt, workdir) -> dict with steps, tokens, usd. Pass/fail comes only from check.sh."""
    work = Path(tempfile.mkdtemp(prefix=f"eval-{task['id']}-"))
    shutil.copytree(repo, work, dirs_exist_ok=True)
    t0 = time.time()
    try:
        stats = agent(task["prompt"], str(work)) or {}
    except Exception as e:
        stats = {"error": str(e)}
    ok = subprocess.run(["bash", str(task["check"])], cwd=work, capture_output=True).returncode == 0
    shutil.rmtree(work, ignore_errors=True)
    return {"task": task["id"], "pass": ok, "secs": round(time.time() - t0, 1), **stats}

def compare(agent_a, agent_b, tasks, repo, repeats=3):
    """Paired comparison: the same tasks, repeated, for two harness variants. Reports lift, not anecdotes."""
    results = {"A": [], "B": []}
    for task in tasks:
        for _ in range(repeats):                         # agents are random; one run proves nothing
            results["A"].append(run_once(agent_a, task, repo))
            results["B"].append(run_once(agent_b, task, repo))
    def summary(rs):
        return {"pass_rate": round(sum(r["pass"] for r in rs) / len(rs), 3),
                "mean_tokens": round(statistics.mean(r.get("tokens", 0) for r in rs)),
                "mean_usd": round(statistics.mean(r.get("usd", 0) for r in rs), 4),
                "mean_steps": round(statistics.mean(r.get("steps", 0) for r in rs), 1)}
    a, b = summary(results["A"]), summary(results["B"])
    per_task = {t["id"]: (sum(r["pass"] for r in results["A"] if r["task"] == t["id"]),
                          sum(r["pass"] for r in results["B"] if r["task"] == t["id"])) for t in tasks}
    return {"A": a, "B": b, "lift_pass_rate": round(b["pass_rate"] - a["pass_rate"], 3),
            "per_task_passes_A_vs_B": per_task, "runs": results}

Wiring:

  • Wrap each turn, model call, tool call and compaction in tracer.span(...) and add tokens, dollars and ok to the record.
  • Turn your 10 tasks into folders: tasks/<id>/prompt.md and check.sh. The check, not the agent, decides pass or fail.
  • Write agent(prompt, workdir) as a thin wrapper over your harness that returns steps, tokens and dollars. Make two variants (for example hooks off vs on) and call compare(A, B, tasks, repo, repeats=3).

Stage 3 gate

  1. Publish a table for every feature you added in Stages 2 and 3: compaction, AGENTS.md rules, hooks, subagents, Code Mode. Each row: pass rate, tokens and dollars, with and without the feature.
  2. Keep a feature only if it helps on at least one measure without hurting another badly. Delete the rest (the zero-tolerance rule, applied to code).
  3. Plot pass rate from week 1 to now. This is the most shareable chart of the book.

8. Exercises

  1. Checked stop. Refuse the stop while tests fail and feed the failure back. Count early "done" claims before and after over 20 tasks.
  2. Paired versus unpaired. Run versions A and B three times on 20 tasks. Compute the difference with overall averages and with per-task pairs. How many runs does each method need to see a 5-point gain?
  3. Step labels. Add a Lakeview-style pass that labels each step in at most 10 words. Can you find where a failed run went wrong in under a minute?
  4. Cost fold. Compute cost per turn and per task from your trace alone. Change a price and recompute last week's sessions.
  5. Latency budget. Add a CI test that fails if starting your harness or rendering a step takes longer than a budget you choose.
