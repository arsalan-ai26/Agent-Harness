Extensibility: skills, MCP and hooks

Anything the model should know or be able to do must be in its window (fact 2), but the window is finite and paid for every call (facts 3 and 4). So no harness can ship every feature its users need in the prompt. Extension points let people add knowledge (skills), connections (MCP), policy (hooks) and whole features (extensions) without forking the core. Each one has a context cost and a safety cost. This chapter reads Pi's code extensions and its new MCP client, eve's directory-as-contract and packaged extensions, fx's four hook kinds and nanocode's tool search, then builds skills with progressive disclosure, lifecycle hooks and a small MCP client.

Before you start: skip check
  1. What is progressive disclosure for skills?
  2. Why put "run tests after every edit" in a hook instead of the system prompt?
  3. Why did Pi first refuse MCP, and what changed?
Answers
  1. Only each skill's name and description go into the prompt. The model loads a skill's full procedure, and its supporting files, only when a task needs it.
  2. A hook always runs; a prompt line runs only when the model remembers and agrees. Policy that must hold belongs in code.
  3. MCP tool schemas cost context on every request (Playwright's server was about 13.7k tokens). Pi 1.0 added a small standalone MCP client, while still favouring CLIs and skills for most work.

1. Four extension points, four jobs

Ask two questions of anything you want to add, and the four extension points fall out. First: does the model need to know about it to use it? If yes, it costs context, and the only way to make it cheap is to show a short name first and the full text only when the model asks (progressive disclosure). If no, it can run outside the model entirely and cost nothing. Second: must it happen every time, or only when the model decides? The model's decisions are samples (fact 5), so anything that must always happen (a formatter, a policy check, an audit log) cannot be left to the model to remember. It has to be code the harness runs at fixed points.

Knowledge the model pulls in when needed: skills. Actions in outside systems the model calls: MCP tools. Rules that must run every time without asking the model: hooks. New harness behaviour that is not about the model at all: extensions.

A practitioner's rule for Claude Code captures the split: tools and MCP give new actions, skills give reusable methods, subagents isolate execution, hooks enforce constraints and collect audit signals, plugins distribute all of it.

2. Code tour

Pi: code extensions the agent can write

packages/coding-agent/src/core/extensions/ loads TypeScript extensions at runtime through jiti (loader.ts, jiti-loader.ts, runner.ts). Extensions can register tools, commands and UI, hook the lifecycle and persist state into the session. Because they are plain files, the agent can write and hot-reload its own; Armin Ronacher's daily extensions (/answer, /todos, /review) were all written by the agent. Pi 1.0 added packages/mcp: a small, standalone MCP client that does not depend on the official SDK, with stdio and Streamable HTTP transports. Its earlier stance remains in the docs: prefer CLI tools with READMEs that the agent reads on demand.

eve: the directory is the contract

Every extension point is a folder: skills/, hooks/, connections/ (MCP and OAuth services), tools/, channels/. Skills follow the Agent Skills standard (docs/skills.mdx): a flat name.md or a directory with SKILL.md plus references/, assets/, scripts/; the model loads one with eve__skill; names are checked at build time. An eve extension (docs/extensions/index.md) is an npm package with the same layout that an agent mounts from agent/extensions/; the repo ships several, including eve-git, eve-code, eve-recall, eve-self-improvement and eve-self-modification.

fx: four hook kinds, skills and MCP

src/core/hooks/definitions.zig defines exactly four HookKinds: pre_tool_use (can allow, block or change a call), stop (can refuse to let the turn end), post_turn_end and attention_required (the agent is waiting for you). Skills live in src/core/skills/, and the agent can search and install skills itself (src/tools/skills/). MCP tools are found through capability search instead of being listed up front.

nanocode: its own MCP client and BM25 search

nanocode replaces the common Rust MCP libraries with its own client (crates/core/mcp, mcp-http), and searches MCP tools with its own BM25 index (crates/integrations/mcp-tools/src/SEARCH.md), so many servers can be connected without filling the context.

Risk

An agent that can install skills or write extensions can widen its own powers. Pair self-extension with a pre_tool_use hook that blocks writes to the harness's own config and extension folders unless the user approves.

4. Research and the Chinese view

  • Progressive disclosure is LangChain's name for loading only skill metadata up front, to protect against context rot (LangChain).
  • Skills marketplaces in China. In early 2026 Alibaba, ByteDance and Tencent all launched skills squares alongside their desktop agents; 36Kr summarizes the stack as coding builds tools, skills store experience, the harness governs the whole (36Kr).
  • Cross-runtime skills. Codex reads ~/.agents/skills/, a path shared with Copilot CLI and Gemini CLI, and eve's skills follow the Agent Skills standard, so one skill works in several harnesses.
  • Natural-language harness modules. NLAH treats modules such as verifier, self-evolution and file-backed state as named natural-language sections, very close to skills (NLAH).

5. Build: skills, hooks and an MCP client

"""Extensibility: skills with progressive disclosure, lifecycle hooks, and a minimal MCP stdio client."""
import json, re, subprocess, threading
from pathlib import Path

# ---- skills: only names and descriptions in the prompt; the body loads on demand ---------------
def parse_skill(path: Path):
    text = path.read_text()
    meta, body = {}, text
    m = re.match(r"^---\n(.*?)\n---\n(.*)$", text, re.S)
    if m:
        body = m.group(2)
        for line in m.group(1).splitlines():
            if ":" in line:
                k, v = line.split(":", 1)
                meta[k.strip()] = v.strip()
    name = meta.get("name") or (path.parent.name if path.name == "SKILL.md" else path.stem)
    return {"name": name, "description": meta.get("description", body.strip().splitlines()[0][:150]),
            "path": path, "body": body}

def load_skills(*roots):
    skills = {}
    for root in roots:
        for p in sorted(Path(root).glob("*/SKILL.md")) + sorted(Path(root).glob("*.md")):
            s = parse_skill(p)
            skills.setdefault(s["name"], s)        # first root wins, so project skills override global ones
    return skills

def skill_catalog(skills):
    """A few lines for the system prompt. The full procedures cost nothing until used."""
    lines = [f"- {s['name']}: {s['description']}" for s in skills.values()]
    return "Skills (load one with the skill tool before following it):\n" + "\n".join(lines)

def skill_tool(skills, name: str):
    s = skills.get(name)
    if not s:
        return f"error: no skill '{name}'. Available: {', '.join(skills)}"
    files = [str(p.relative_to(s["path"].parent)) for p in s["path"].parent.rglob("*")
             if p.is_file() and p != s["path"]] if s["path"].name == "SKILL.md" else []
    extra = "\nSupporting files (read them if the procedure says so): " + ", ".join(files) if files else ""
    return s["body"] + extra

# ---- hooks: deterministic policy that does not depend on the model's judgement ----------------
HOOKS = {"pre_tool_use": [], "post_tool_use": [], "stop": []}

def hook(event):
    def wrap(fn):
        HOOKS[event].append(fn)
        return fn
    return wrap

def run_pre(name, args):
    """Each hook returns None (no opinion), ('block', reason) or ('rewrite', new_args)."""
    for h in HOOKS["pre_tool_use"]:
        r = h(name, args)
        if r and r[0] == "block":
            return None, f"blocked by hook {h.__name__}: {r[1]}"
        if r and r[0] == "rewrite":
            args = r[1]
    return args, None

def run_post(name, args, output):
    for h in HOOKS["post_tool_use"]:
        extra = h(name, args, output)
        if extra:
            output += "\n" + extra
    return output

def run_stop(state):
    """A stop hook may refuse to let the turn end and give the model a reason to continue."""
    for h in HOOKS["stop"]:
        reason = h(state)
        if reason:
            return reason
    return None

# ---- MCP over stdio: JSON-RPC 2.0, one JSON object per line ----------------------------------
class MCPClient:
    def __init__(self, command: list[str]):
        self.proc = subprocess.Popen(command, stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True, bufsize=1)
        self.next_id, self.lock = 1, threading.Lock()
        self.request("initialize", {"protocolVersion": "2025-06-18", "capabilities": {},
                                    "clientInfo": {"name": "harness", "version": "0.1"}})
        self.notify("notifications/initialized")

    def notify(self, method, params=None):
        self.proc.stdin.write(json.dumps({"jsonrpc": "2.0", "method": method, **({"params": params} if params else {})}) + "\n")

    def request(self, method, params=None):
        with self.lock:
            rid, self.next_id = self.next_id, self.next_id + 1
            self.proc.stdin.write(json.dumps({"jsonrpc": "2.0", "id": rid, "method": method, "params": params or {}}) + "\n")
            while True:                                   # skip server notifications until our reply arrives
                msg = json.loads(self.proc.stdout.readline())
                if msg.get("id") == rid:
                    if "error" in msg:
                        raise RuntimeError(msg["error"].get("message"))
                    return msg["result"]

    def tools(self, prefix):
        """MCP tools as our tool specs, namespaced so two servers cannot collide."""
        return [{"name": f"{prefix}__{t['name']}", "description": t.get("description", ""),
                 "parameters": t.get("inputSchema", {"type": "object", "properties": {}})}
                for t in self.request("tools/list")["tools"]]

    def call(self, name, args):
        r = self.request("tools/call", {"name": name, "arguments": args})
        text = "\n".join(c.get("text", "") for c in r.get("content", []) if c.get("type") == "text")
        return ("error: " if r.get("isError") else "") + text

Wiring:

  • Add skill_catalog(skills) to the system prompt (it is stable, so it caches), and a skill(name) tool.
  • Before each tool call run run_pre; after it, run_post. When the model stops, call run_stop; if it returns a reason, append it as a user message and keep looping.
  • For each configured MCP server, add client.tools(prefix) to the tool list and route prefix__name calls to client.call(name, args).

Two hooks to start with: a post_tool_use hook that runs the test suite after any edit or write and appends a one-line result, and a stop hook that refuses to finish while tests fail.

Measure

  1. Count tokens of your skill catalog and of one MCP server's schemas. Put both numbers in a post.
  2. Rerun your 10 tasks with the two hooks on. Did pass rate change? Did steps per task rise?

6. Exercises

  1. Add tool search: instead of listing MCP tools, give the model a find_tool(query) tool that ranks tools by keyword match and returns the best schemas, as fx and nanocode do.
  2. Let the agent write a skill from a session it just finished. Review it before you keep it.
  3. Add the attention_required hook from fx: notify yourself (a desktop notification or a Telegram message) when the agent waits for input.
