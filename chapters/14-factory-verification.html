Software factory II: verification gates and self-improvement

When agents write code faster than people can read it, verification becomes the bottleneck. This chapter covers the gates that let a factory ship safely: holdout scenarios the generator never sees, digital twins of outside services, review depth that grows with risk, and the light-versus-dark factory debate. Then it closes the loop: a harness that reads its own failed traces, proposes one change, and keeps it only if the eval says it helped.

Answers
  1. An agent that can see the tests can satisfy them without solving the problem (special-casing, weakening asserts). Holdouts measure the real behaviour.
  2. A behavioural clone of a third-party service (Okta, Slack, Jira) that tests can hit at high volume without rate limits or cost.
  3. It must improve the paired eval by a meaningful margin without a large cost increase, and it must name the failure it prevents.

1. The bottleneck moved

In 2026 generation got cheap and review did not. One industry report found that with high AI adoption, PRs received 25% more review comments and 31.3% of PRs skipped review entirely (cited at AI Engineer World's Fair 2026). Qodo puts the conclusion plainly: a factory that builds fast without checking its own output only produces problems faster, and the quality layer that works is one the generator does not control (Qodo).

The light versus dark factory question is open. Dan Shapiro's five levels place the dark factory (no human reads the code) at the top. Critics answer that the hard part of software is judgement, so the better metaphor is a software company, not a factory (Every). StrongDM is a security company, which made its choice to drop human review the most debated decision of the year.

3. Harnesses that improve themselves

  • Meta-Harness (Stanford, MIT, KRAFTON, 2026): a coding agent reads a folder of every earlier harness's code, scores and raw traces, proposes a new harness, and the result is evaluated and added to the folder. The model weights never change. Discovered harnesses beat hand-built ones; the key design choice is raw traces, not compressed summaries (arXiv 2603.28052).
  • OpenAI's improvement loop: traces become feedback, feedback becomes evals, eval results rank harness changes, and Codex implements them, in one repeatable workflow (OpenAI cookbook, May 2026).
  • eve ships eve-self-improvement and eve-self-modification extensions; Pi's agents write their own extensions.
  • Test-time harness evolution and JIT-Agent adapt the harness during a task (arXiv 2608.25593).
The trap

A loop that optimizes against your eval will overfit to your eval. Keep a holdout set the proposer never sees, cap changes to one per round, require every rule to name the failure it fixes, and read every accepted change yourself.

4. The Chinese view

  • Chinese practitioners describe harness feedback as "semantic gradient descent": natural-language feedback improves outputs the way gradients improve weights, and insist it stays constructive rather than hostile (CSDN).
  • Woshipm's essay "Harness is the new dataset" argues that harness design is now the main lever for agent intelligence gains, organized into information, execution and feedback layers (Woshipm).
  • A Baidu Cloud lead told Beijing News that the biggest obstacle to agentic training is reproducing real environments, not the model (Beijing News): the same insight behind StrongDM's digital twins.

5. Build: gates and an improvement loop

"""Verification gates the generator cannot see, review depth by risk, and a harness that improves from its traces."""
import fnmatch, json, subprocess
from pathlib import Path

# ---- gate 1: holdout scenarios ----------------------------------------------------------------
def holdout_gate(workdir, scenarios_dir):
    """Run scenario checks stored outside the implementer's sandbox (StrongDM keeps holdouts the agent never sees)."""
    results = {}
    for s in sorted(Path(scenarios_dir).resolve().glob("*.sh")):
        p = subprocess.run(["bash", str(s)], cwd=workdir, capture_output=True, text=True, timeout=600)
        results[s.stem] = p.returncode == 0
    return all(results.values()), results

# ---- gate 2: review depth by risk -----------------------------------------------------------------
RISKY_PATHS = ["*auth*", "*payment*", "*migrations/*", ".github/workflows/*", "*secrets*", "Dockerfile"]

def risk(diff_files: list[str], lines_changed: int) -> str:
    """'low' -> agent review is enough; 'high' -> a human must read the code (review depth grows with blast radius)."""
    if any(fnmatch.fnmatch(f, pat) for f in diff_files for pat in RISKY_PATHS):
        return "high"
    return "high" if lines_changed > 400 else "low"

# ---- the improvement loop -----------------------------------------------------------------------
PROPOSER_PROMPT = """You improve an AI agent harness. Below are failing eval runs with their raw traces and the
current harness configuration. Find ONE root cause that appears in several failures and propose ONE change to
the configuration (AGENTS.md rules, tool descriptions, limits or hooks). Every rule you add must name the failure
it prevents. Reply JSON only: {"diagnosis": "...", "evidence": ["trace ids"], "file": "...", "new_content": "..."}"""

def failing_runs(results, traces_dir, limit=5):
    """Raw traces of failed runs, not summaries: Meta-Harness found raw traces are what make diagnosis work."""
    out = []
    for r in results:
        if not r["pass"] and r.get("trace"):
            out.append({"task": r["task"], "trace": Path(traces_dir, r["trace"]).read_text()[-20_000:]})
    return out[:limit]

def improve_once(config_dir, propose, evaluate, min_lift=0.05, max_cost_increase=0.2):
    """propose(prompt, material) -> dict; evaluate(config_dir) -> {'pass_rate', 'mean_usd', 'runs'}.
    Accept a change only if it beats the current harness on the eval without a large cost increase."""
    base = evaluate(config_dir)
    material = json.dumps({"failures": failing_runs(base["runs"], config_dir),
                           "config": {p.name: p.read_text() for p in Path(config_dir).glob("*.md")}})
    change = propose(PROPOSER_PROMPT, material)
    target = Path(config_dir, Path(change["file"]).name)       # stay inside the config folder
    old = target.read_text() if target.exists() else None
    target.write_text(change["new_content"])
    new = evaluate(config_dir)
    lift = new["pass_rate"] - base["pass_rate"]
    cost_ok = new["mean_usd"] <= base["mean_usd"] * (1 + max_cost_increase) or base["mean_usd"] == 0
    if lift >= min_lift and cost_ok:
        return {"accepted": True, "lift": round(lift, 3), "diagnosis": change["diagnosis"]}
    if old is None:                                              # revert: the change did not earn its place
        target.unlink()
    else:
        target.write_text(old)
    return {"accepted": False, "lift": round(lift, 3), "diagnosis": change["diagnosis"]}

Wiring:

  • Keep holdout scenarios in a folder outside the implementer's sandbox. Run holdout_gate after the reviewer approves; a failure sends feedback without the scenario text.
  • Call risk() on the PR's files; for high, label the PR needs-human-review and do not auto-merge anything.
  • Store a trace file per eval run (Chapter 10) and its path in the run record. evaluate runs your paired eval on a training set of tasks; keep 5 tasks back as a holdout and check them only after an accepted change.
  • Run improve_once weekly. Commit each accepted change with its diagnosis in the message.

Measure

Run four improvement rounds. For each, report the diagnosis, train lift, holdout lift and whether you agree with the change. A change with train lift but no holdout lift is overfitting; record it.
