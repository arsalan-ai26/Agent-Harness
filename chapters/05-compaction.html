Stage 2 · Context · Chapter 5

Context management and compaction

Every step resends the whole history (fact 2), the window has a hard limit and quality drops well before it (fact 3), and every resent token costs money unless it is a cached prefix (fact 4). A long task therefore runs into a wall. This chapter derives the ladder of ways to stay under it, from cheapest and safest to most lossy, then takes the design decisions one at a time: when to compact, what to keep word for word, who writes the summary and what it must say, how to check it, whether raw history stays reachable, and whether compaction blocks the user. It shows the compaction flow of nine harnesses and keeps the compactor you build.

Level: intermediate Time: about 14 hours with the build Needs: Chapters 1 to 4 Harnesses read: Pi, eve, fx, nanocode, Codex, Claude Code, Kimi Code, Qwen Code, Trae Agent
Before you start: skip check
  1. Why does the total number of tokens sent over a session grow with the square of the number of steps?
  2. Claude Code runs five reductions before a model call. Why is a model-written summary the last of them?
  3. Codex introduces its summary to the next call as the work of another model. Why?
  4. What turns lossy compaction into lossless compaction in Kimi Code and fx?
Answers
  1. Step k resends everything from steps 1 to k-1. Summing 1 + 2 + ... + n gives about n²/2.
  2. Each stage loses more than the one before. A summary is a sample (fact 5) that can drop or invent details, so the cheaper, deterministic reductions (capping results, trimming, clearing old tool output) go first.
  3. So the model treats it as a handoff to build on, not as its own words to repeat or second-guess.
  4. The raw history stays on disk and the model is told how to reach it: Kimi Code tells it the log file and how to grep it; fx gives every turn and tool call a handle that a tool can read back.

1. The wall, from first principles

Each step appends a model reply and a tool result, and the next step sends everything again. If steps are roughly equal in size, step k sends k units, and a session of n steps sends about n²/2 units in total. Manus reported about 50 tool calls per task and about 100 input tokens for every output token, which is what this arithmetic predicts. Caching makes the repeated part cheaper but not free, and does nothing for the window limit.

There are only two ways to stay inside a budget: spend less, or throw some away. Throwing away is dangerous because of fact 2: what leaves the window, the model has truly forgotten, and it does not know it has forgotten. That gives an order of preference, from least to most lost.

2. The decisions, one at a time

Decision 1. One compactor, or a pipeline of reductions?

The simplest design has one step: when the window is nearly full, summarise. The Claude Code paper describes a different shape: five stages applied in order before each model call, each with its own condition, each losing more than the one before.

The reasoning is the ladder in Figure 2. A deterministic stage (cut a result, drop an old tool output) never invents anything; a summary might. Running the cheap stages first means many sessions never need the expensive one. Context collapse is the subtle stage: it changes what the model is shown without changing what is stored, so it can be undone. The other harnesses mostly have one summarising compactor plus Chapter 3's output bounds, which together cover rungs 1 and 5.

Decision 2. When does compaction start?

Early (80%)Late (90% or a fixed reserve)
ProEach compaction loses less; headroom for one big tool result; attention stays sharperUses the window fully; fewer lossy summaries
ConCompacts more oftenOne large result can overflow before the check

A fixed reserve (Pi's 16,384 tokens, Kimi Code's 50,000) is a better rule than a percentage when windows vary widely: the summary call itself needs room, and that room does not shrink with a small window. Kimi Code uses both, whichever comes first.

Decision 3. What stays word for word?

The most recent turns are the most relevant and the hardest to summarise well (they are still in motion). So every compactor keeps a tail verbatim. What counts as "the tail" differs.

Decision 4. What must the summary say?

A summary is a prompt written by the model for a future model that knows nothing (fact 2). The best summary prompts ask for the same parts.

Kimi Code's instruction is worth reading as a model of the genre. It asks for the summary in the conversation's language; exact commands, paths and results rather than descriptions of them; decisions kept separate from open questions; an explicit list of what is still unknown; and a careful forward plan, because, in its words, right now you hold more context on this task than you ever will again. Qwen Code, inheriting Gemini CLI's format, asks for an analysis block followed by an XML state snapshot. eve's prompt separates completed progress and decisions from remaining work, and on a second compaction passes the previous summary in full and replaces it, so summaries do not nest.

Codex adds a framing trick: the summary is introduced to the next call with text presenting it as another model's work, so the model builds on it rather than repeating it.

Decision 5. Is the summary checked?

A summary can invent a file name or a test result that never happened, and the next model will trust it. fx is the only harness here that checks.

Decision 6. Can the model get back what was dropped?

If raw history stays on disk and the model knows how to reach it, compaction is a cache in front of a complete record rather than a loss.

Manus calls this restorable compression: drop a page's content but keep its URL, drop a file's content but keep its path. Trae Agent does not compact at all; it keeps the trajectory on disk for analysis, clips tool output at 16,000 characters and relies on its step cap.

Decision 7. Does compaction make the user wait?

A summary call takes seconds to a minute. Done at the moment the limit arrives, it stalls the conversation.

Decision 8. What if compaction fails?

  • eve requires the result to land under 50% of the window. If it does not, it falls back to a text-only tail, then to the summary alone; if instructions, tools and memory alone do not fit, it does not call the provider and the turn fails with a compaction error.
  • Qwen Code stops trying after 3 consecutive failures, a circuit breaker so a broken summariser does not burn money on every step.
  • Kimi Code tries at most 3 times on an overflow.
  • fx uses the same path for provider-overflow recovery as for planned compaction, so the rare case is exercised by the common one.

Decision 9. How does the harness know how full the window is?

The only exact count is the provider's, and it arrives after the call. Harnesses estimate before.

  • eve starts from the provider's last reported input tokens, estimates only the new messages, and scales its character-based estimate by the observed ratio between the two (1.6 until calibrated).
  • Qwen Code counts CJK characters as 1.5 tokens each, because Chinese text tokenises differently and a characters-per-token rule tuned on English would underestimate it badly.

Decision 10. Who decides what to forget?

Every harness above lets the harness decide. Kimi's earlier Python CLI tried the opposite: a tool (named after the D-Mail in Steins;Gate) let the model revert its own context to an earlier checkpoint and leave itself a note with only the useful result, for example after a long dead-end exploration. The model knows better than the harness which turns were wasted; the cost is one more tool the model must learn to use well. Subagents (Chapter 9) are the mainstream version of the same idea: exploration happens in a context that is thrown away.

5. Choosing a compaction design

This book's compactor: trigger at 85% or a fixed reserve, keep user messages and the recent tail verbatim, ask for a handoff summary with the six parts in Figure 7, give every turn a handle, lint the notes against the saved turns, and append a footer telling the model where the raw log is.

6. Research and the Chinese view

  • Externalise memory. Anthropic's harness for long-running agents has each new session read a progress file and the git log instead of relying on a summary. Chinese readings of that post put it bluntly: the context window is not reliable memory, so reliable memory must be written down outside it.
  • Restorable compression. Manus keeps a URL or a path when it drops content, so nothing is truly lost.
  • Long-horizon harness studies. Alibaba's LongHorizon-Harness work asks how much long-task performance changes when only the harness changes; compaction policy is one of the largest levers.
  • Chinese practice. Kimi Code's compaction prompt and recovery footer are the most complete design read for this chapter, and its earlier model-driven context revert is the boldest. Qwen Code's CJK token weighting is a reminder that a harness built and tested in English can quietly miscount for other languages.

7. Build: a compactor with handles, lint and recall

"""Compaction: summarize old turns into a checkpoint, keep a verbatim tail, keep raw history recallable."""
import json, re

THRESHOLD = 0.85          # compact at 85% of the window (fx: 80%, eve: 90%)
TARGET = 0.5              # after compaction, the request must fit in half the window (eve)
KEEP_TAIL_TOKENS = 20_000 # recent messages kept word for word (eve, Pi)
TAIL_TOOL_CHARS = 2_000   # tool results inside the kept tail are shortened (eve)

class TokenEstimator:
    """chars / 4, corrected by the provider's reported input tokens (eve's ratio trick)."""
    def __init__(self):
        self.ratio = 1.0
    def raw(self, messages):
        return sum(len(json.dumps(m, default=str)) for m in messages) / 4
    def calibrate(self, messages, reported_input_tokens):
        est = self.raw(messages)
        if est > 0 and reported_input_tokens:
            self.ratio = reported_input_tokens / est
    def __call__(self, messages):
        return int(self.raw(messages) * self.ratio)

SUMMARY_PROMPT = """You are writing a checkpoint so another engineer can continue this task with no other context.
Every message has a handle M<n>; every tool call has a handle T<n>. Write these sections:
## Goal - the user's request, in their words where possible.
## Done - completed steps and decisions, each citing the handles it rests on, e.g. (M3, T7).
## Remaining - what is left, in order.
## Facts - file paths, commands, constraints and preferences needed to continue, each with a handle.
Cite only handles that appear in the transcript. Do not invent results."""

def with_handles(messages):
    """Give every message and tool call a stable handle, as fx does (M1, T1, ...)."""
    lines, t = [], 0
    for i, m in enumerate(messages, 1):
        body = m.get("content") or ""
        for c in m.get("tool_calls", []) or []:
            t += 1
            body += f"\n[T{t}] {c.name}({json.dumps(c.args)[:300]})"
        lines.append(f"[M{i}] {m['role']}: {str(body)[:4000]}")
    return "\n".join(lines), len(messages), t

def lint(summary, n_messages, n_tools):
    """Flag summary lines that cite handles which do not exist (fx's lint pass)."""
    bad = [h for h in re.findall(r"\b([MT])(\d+)\b", summary)
           if int(h[1]) < 1 or int(h[1]) > (n_messages if h[0] == "M" else n_tools)]
    cited = len(re.findall(r"\b[MT]\d+\b", summary))
    return {"bad_handles": [f"{a}{b}" for a, b in bad], "cited": cited}

def split_tail(messages, estimate):
    """Keep the newest messages up to KEEP_TAIL_TOKENS. Never split a tool call from its results."""
    kept, total = [], 0
    for m in reversed(messages):
        total += estimate([m])
        if total > KEEP_TAIL_TOKENS and kept:
            break
        kept.insert(0, m)
    while kept and kept[0]["role"] == "tool":          # a tail may not start with orphaned tool results
        kept.pop(0)
    old = messages[: len(messages) - len(kept)]
    tail = [dict(m, content=m["content"][:TAIL_TOOL_CHARS] + "\n[shortened]")
            if m["role"] == "tool" and len(m.get("content", "")) > TAIL_TOOL_CHARS else m for m in kept]
    return old, tail

def maybe_compact(state, window, estimate, summarize, archive):
    """summarize(prompt, transcript) -> str uses a cheap model. archive(messages) stores raw history.
    Returns True if the history was compacted."""
    if estimate(state.messages) < THRESHOLD * window:
        return False
    old, tail = split_tail(state.messages, estimate)
    if not old:
        return False
    archive(old)                                       # raw history stays recoverable (Pi Durable, fx)
    transcript, n_m, n_t = with_handles(old)
    previous = state.checkpoint or ""
    summary = summarize(SUMMARY_PROMPT, (f"Previous checkpoint:\n{previous}\n\n" if previous else "") + transcript)
    report = lint(summary, n_m, n_t)
    if report["bad_handles"]:
        summary += f"\n\n[warning: these cited handles do not exist and may be wrong: {', '.join(report['bad_handles'])}]"
    state.checkpoint = summary
    state.messages = [{"role": "user", "content": f"<checkpoint>\n{summary}\n</checkpoint>\n"
                       "Older turns were summarized above; the raw history is available with the recall tool."}] + tail
    if estimate(state.messages) > TARGET * window:     # tail too big: keep only its text
        state.messages = state.messages[:1] + [m for m in tail if m["role"] != "tool"][-4:]
    return True

Wiring:

  • After every model call, call estimator.calibrate(messages, reply.input_tokens).
  • Before every model call, call maybe_compact(state, window, estimator, summarize, archive). summarize calls a cheap model with the prompt and transcript. archive appends the raw messages to session-archive.jsonl.
  • Add a recall(handle_or_query) tool that searches the archive, so the agent can read what the checkpoint left out.

Measure

  1. Create one long task (for example a 3-hour refactor across 15 files) that needs at least two compactions. Record whether it finishes, how many lint warnings appear, and whether the agent used recall.
  2. Run it with the threshold at 0.8 and at 0.9. Compare completion and total tokens.
  3. Read one checkpoint and mark every claim as true or false against the transcript. That number is your summary accuracy.

8. Exercises

  1. Plot the wall. Log input tokens per step for a 40-step task. Plot per-step and cumulative tokens, and mark where your compactor fires.
  2. Cheap rungs first. Before summarising, clear tool results older than 10 turns (keep the calls). How many sessions never reach the summary?
  3. Lint the summary. Make the summariser cite turn handles. Check every cited file path and command against the saved turns; count unsupported claims over 20 compactions.
  4. The footer. Run the same long task with and without a footer that says where the raw log is and how to grep it. Does the agent re-run commands it already ran?
  5. Background start. Start a summary at 65% in the background and apply it at the next turn boundary. Measure the wait saved and check the summary for staleness.
