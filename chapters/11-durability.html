Durable execution

A terminal agent dies with its process. A durable agent survives crashes, redeploys and a laptop lid, and can wait days for a human. This is where eve, Pi Durable and nanocode converged independently in 2026, each in its own way. This chapter reads Pi Durable's 7,300-line specification, eve's workflow-backed sessions and nanocode's journaled runtime, then builds a SQLite journal with the "effect sandwich" and tests it by crashing the agent mid-task.

Before you start: skip check
  1. The agent sends an email, then the process dies before saving that it did. On restart, what should happen?
  2. What is the difference between replaying a model call and repeating it?
  3. Why can only some tool calls be safely re-run?
Answers
  1. Not send it again blindly. The harness knows it started (intent recorded) but not whether it finished, so it tells the agent the outcome is unknown and lets it check, or polls an external handle.
  2. Replaying returns the recorded result from the journal; repeating calls the model again, costs money and may return something different.
  3. Only idempotent ones (reads, pure computations, "set X to 5") give the same result when run twice. "Append a line", "charge a card" or "send an email" do not.

2. Code tour

Pi Durable: a specification first

packages/durable/docs/spec.md is normative and long; read sections 1, 4, 5.2 and 8. Its core rule: a Session atomically commits immutable entries, full task records and documents, and only committed state is observable. Selected invariants: one commit is atomic across all writes; all visible progress is durable (except explicitly deferred commits, which may be lost within a bounded window); external effects do not run inside the mutation transaction; entries and IDs are never reused. Work is modelled as tasks, durable state machines with phases; a terminal task record is the result receipt. Section 5.2 is the effect sandwich: commit the intent phase, perform the external effect, commit the outcome or next phase; reopening in an intent phase means the effect may have happened, so the handler retries safely, polls an external handle, or records interruption. Storage backends: memory, SQLite, JSONL, IndexedDB (src/storage/), each passing a conformance suite. Section 13 lists non-goals, including no automatic checkpoint heuristic and no forced termination of non-cooperative extension code.

Field note: a team killed a Pi Durable agent right after a Gmail write and found two drafts; the sandwich detects the risk, but only you can make the effect idempotent (withone.ai).

eve: the workflow engine is the journal

Every eve session is one workflow on the open-source Workflow SDK (docs/concepts/execution-model-and-durability.mdx). The kernel from Chapter 1 returns { session, next }; each step is saved; a crash replays from the last step. Locally, runs persist under .eve/.workflow-data; self-hosted worlds include Postgres. Durability brings new problems eve solves explicitly: an idle session moves to a new deployment on its next message; a session built by an older eve version is "stranded" and retired safely; after compaction the session moves to a fresh workflow run so its run history stays bounded. On Vercel, the same mechanism runs other harnesses durably too: Vercel documents running Pi, fx, OpenCode, Claude Code and Codex this way.

nanocode: journaled calls everywhere

The README promise: every model call and tool call is journaled, so a turn finishes after its process dies. crates/core/durability-core holds the StateStore, content-addressed payloads and a deterministic state machine; each backend defines its own checkpoint format; stores run on JSONL, SQLite, Postgres, Durable Objects or D1. Subagents are durable sessions too (with only 2 resident by default when durable).

4. Research and the Chinese view

  • Durable execution is an old idea. Workflow engines (Temporal, Step Functions) have used journals and replay for years; 2026 harnesses apply them to agents, where every model call is a slow, expensive, non-deterministic effect worth recording.
  • Long-horizon work needs it. Anthropic's long-running harness and the Dive into Claude Code paper both name horizon scaling (from single sessions to multi-day programs) as an open direction.
  • Chinese coverage. Taiwanese and Chinese tech press covered Pi Durable's release as an agent framework that reads saved progress after a restart and handles unfinished work, with several conversations at once and several people joining one task (iThome). Cloudflare's Agents SDK already runs Pi Durable as a harness (Cloudflare).

5. Build: a journal with the effect sandwich

"""Durable execution: journal every model and tool call; commit intent, do the effect, commit the outcome."""
import json, sqlite3, time

class Journal:
    def __init__(self, path="harness.db"):
        self.db = sqlite3.connect(path, isolation_level=None)       # autocommit; every write is durable
        self.db.execute("PRAGMA journal_mode=WAL")
        self.db.execute("""CREATE TABLE IF NOT EXISTS effects (
            session TEXT, key TEXT, phase TEXT, payload TEXT, ts REAL, PRIMARY KEY (session, key))""")
        self.db.execute("""CREATE TABLE IF NOT EXISTS checkpoints (
            session TEXT PRIMARY KEY, step INTEGER, state TEXT, ts REAL)""")

    # -- the effect sandwich (Pi Durable spec, section 5.2) ---------------------------------------
    def effect(self, session, key, fn, idempotent=False):
        """Run fn() at most once per (session, key), unless it is idempotent.
        key must be deterministic, e.g. f"step{n}:tool:{call_id}" or f"step{n}:model"."""
        row = self.db.execute("SELECT phase, payload FROM effects WHERE session=? AND key=?", (session, key)).fetchone()
        if row and row[0] == "done":
            return json.loads(row[1])                       # replay: the effect already happened, reuse its result
        if row and row[0] == "intent" and not idempotent:
            # We crashed between starting and recording. The effect may or may not have happened.
            outcome = {"interrupted": True, "note": f"'{key}' was started before a crash and its outcome is unknown. "
                       "Check the current state before repeating it."}
            self._done(session, key, outcome)
            return outcome
        self.db.execute("INSERT OR REPLACE INTO effects VALUES (?,?,?,?,?)", (session, key, "intent", None, time.time()))
        result = fn()                                          # the external effect, outside any transaction
        self._done(session, key, result)
        return result

    def _done(self, session, key, result):
        self.db.execute("UPDATE effects SET phase='done', payload=? WHERE session=? AND key=?",
                        (json.dumps(result, default=str), session, key))

    # -- state checkpoints at step boundaries (eve's step function) ------------------------------
    def save(self, session, step, state: dict):
        self.db.execute("INSERT OR REPLACE INTO checkpoints VALUES (?,?,?,?)",
                        (session, step, json.dumps(state, default=str), time.time()))

    def load(self, session):
        row = self.db.execute("SELECT step, state FROM checkpoints WHERE session=?", (session,)).fetchone()
        return (row[0], json.loads(row[1])) if row else (0, None)

def run_durable(journal, session, initial_state, step_fn, done):
    """Resume from the last checkpoint, then step until done. step_fn(state, n, effect) -> state.
    Inside step_fn, every model call and tool call goes through effect(key, fn, idempotent)."""
    n, state = journal.load(session)
    state = state or initial_state
    while not done(state):
        effect = lambda key, fn, idempotent=False, n=n: journal.effect(session, f"step{n}:{key}", fn, idempotent)
        state = step_fn(state, n, effect)
        n += 1
        journal.save(session, n, state)                      # the step boundary is the checkpoint
    return state

Wiring:

  • Your step() from Chapter 1 becomes step_fn(state, n, effect). Wrap the model call as effect("model", lambda: llm.complete(...)) and each tool call as effect(f"tool:{call.id}", lambda: call_tool(...), idempotent=tool.idempotent).
  • Mark read, grep, recall idempotent. Leave bash, write, edit non-idempotent unless you can prove otherwise.
  • State must be JSON: messages, checkpoint text, counters. Anything else (open files, live processes) is not state; recreate it on start.

Stage 4 gate: kill it ten times

  1. Run a long eval task. At 10 random moments, kill -9 the process and restart it with the same session ID.
  2. Check: the task finishes; no model call is paid twice for a completed step; no non-idempotent tool ran twice; every interrupted effect produced the "outcome unknown" note.
  3. Post the result, and the one bug you found. There is always one.
