Stage 4 · Durability and surfaces · Chapter 11

Durable execution

Processes die: a laptop sleeps, a deploy replaces a server, a container is killed. Because the model keeps nothing (fact 2), restoring the agent's mind is easy: replay what the harness wrote down. Restoring the world is not (fact 6): a crash between "push the branch" and "the push succeeded" leaves a question the message list cannot answer. This chapter derives the effect sandwich that answers it, then takes ten design decisions: what to journal and how often, what to do with an effect of unknown outcome, torn writes, who hosts the journal, deploys and version upgrades, single writers, authority after a resume, reconnecting clients and what durability deliberately does not promise. It shows each harness's recovery path and keeps the journal you build.

  3. Claude Code deliberately does not save a session's permission bypass flag to the transcript. Why?
  4. Kimi Code reports a corrupted last line in its log instead of failing the session. Why is that the right default?
Answers
  1. The model's whole state is the history the harness wrote (fact 2); any process can replay it. The world changed outside the process, and a crash in the gap between doing and recording leaves the outcome unknown (fact 6).
  2. Re-run it if it is safe to repeat; check an external handle (look for the sent message); or tell the agent the outcome is unknown and let it or the user decide.
  3. Durable state and durable authority are different. A temporary grant should not outlive the process the user granted it to.
  4. A crash mid-write produces exactly that: a torn last line. Everything before it is intact, so losing one partial record is better than losing the session.

1. The problem in one picture

Ask the smallest question: after a crash, what does a new process need to continue exactly where the old one stopped? The model contributes nothing; any model can read the saved history and carry on. So the answer is only what the harness wrote down. If it wrote every step, the agent's mind is back. The hard part is the world.

A real case from the field: a team killed a Pi Durable agent right after a Gmail write and found two drafts on restart. The sandwich detected the risk correctly; only the effect's owner can make it safe to repeat (for example by searching for an existing draft before creating one). Durability tells you an outcome is unknown; idempotency is what lets you act on that safely.

Decision 2. What happens to work that was in flight?

On restart, the last record tells the harness what was happening. The harnesses that replay logs classify the session and repair it before the model sees it, because a provider rejects a history with a tool call that has no result (Chapter 2).

A synthesised result must be honest. "The tool was interrupted; its outcome is unknown" lets the model check (look at the file, query the branch) before acting again. A synthesised "success" would be a lie the model then builds on.

Decision 3. What if the crash tears a write?

A process killed in the middle of writing a line leaves half a line. Three properties make that harmless:

  • Append-only files (every harness here): a torn write can only damage the last record, never history before it.
  • Tolerant readers: Kimi Code's log reader reports a corrupted or truncated last line instead of failing the whole session.
  • Atomic commits: Pi Durable's rule is that one commit is atomic across all its writes, and only committed state is observable, so a reader never sees half a step.

Decision 4. Who hosts the journal?

Pi Durable's specification is worth reading as an example of how to write down durability semantics. Selected invariants: one commit is atomic across all writes; all visible progress is durable, except explicitly deferred commits, which may be lost within a bounded window; external effects never run inside the mutation transaction; entries and IDs are never reused. Work is modelled as tasks, durable state machines with phases, and a finished task record is the receipt for its result. The workflow-engine route trades that control for infrastructure: Vercel documents running several harnesses (including Pi, fx, Claude Code and Codex) durably on the same workflow mechanism eve uses, and Cloudflare's Agents SDK runs Pi Durable.

Decision 6. Who may write a session?

Two processes appending to one session (two terminals, a retry and the original) interleave records and corrupt the history. Qwen Code takes a writer lease so only one process writes a session at a time. Pi Durable's atomic commits serialise writers through the store. nanocode limits how many durable subagents are resident at once. A workflow engine like eve's guarantees one run per session.

Decision 7. What authority survives a resume?

The Claude Code paper points out a deliberate asymmetry: the session's permission-bypass flag and its computer-use app allowlist are not written to the transcript, so a session resumed in a new process starts without them. The reasoning generalises: a user grants a temporary permission to a process they are watching; a resumed session may run somewhere else, later, unwatched. Durable state and durable authority are different things. Codex and Qwen Code keep approvals per session; eve's approvals are durable on purpose, because its sessions are built to wait days for a human (Chapter 7), and the approval is for one specific pending action.

Decision 8. Can a client reconnect to work that kept running?

If the harness runs as a server (Chapter 12), the client is not the process: closing a laptop should not stop the agent. Codex's app server has its own recovery so clients can reconnect to work that kept running. eve sessions live on the platform and are reached through its API and channels. Pi Durable is built for several conversations at once and several people joining one task.

Decision 9. What does durability not promise?

Pi Durable's specification ends with non-goals, a good habit: no automatic checkpoint heuristic (the code says when to commit) and no forced termination of extension code that does not cooperate. Two others apply to every design: durability cannot make an effect idempotent (the Gmail drafts), and it cannot recover what the world itself lost (a deleted branch).

Decision 10. When is durability not worth it?

Trae Agent runs one benchmark task per process and keeps only the trajectory; if a run dies, it runs again. The Pi CLI and fx save the session file and lose only the turn in progress, which a person at the terminal simply repeats. Durability pays off when nobody is watching, when runs are long or expensive, or when effects reach other people (emails, pull requests, payments).

5. Choosing a durability design

This book's journal: an append-only JSONL file with intent and outcome records around every model call and tool call, a tolerant reader, a recovery pass that classifies the session and synthesises honest "outcome unknown" results, a writer lock, and no saved temporary permissions.

6. Research and the Chinese view

  • Durable execution is an old idea. Workflow engines such as Temporal and AWS Step Functions have used journals and replay for years; 2026 harnesses apply them to agents, where every model call is a slow, expensive, non-deterministic effect worth recording.
  • Long-horizon work needs it. Anthropic's long-running harness and the Dive into Claude Code paper both name horizon scaling, from single sessions to multi-day programs, as an open direction.
  • Chinese practice. Kimi Code shows that event sourcing gives most of durability for free; Qwen Code's recovery classification is the most explicit repair design read for this book. Taiwanese and Chinese tech press covered Pi Durable's release as an agent framework that reads saved progress after a restart, handles unfinished work, and lets several people join one task.

7. Build: a journal with the effect sandwich

"""Durable execution: journal every model and tool call; commit intent, do the effect, commit the outcome."""
import json, sqlite3, time

class Journal:
    def __init__(self, path="harness.db"):
        self.db = sqlite3.connect(path, isolation_level=None)       # autocommit; every write is durable
        self.db.execute("PRAGMA journal_mode=WAL")
        self.db.execute("""CREATE TABLE IF NOT EXISTS effects (
            session TEXT, key TEXT, phase TEXT, payload TEXT, ts REAL, PRIMARY KEY (session, key))""")
        self.db.execute("""CREATE TABLE IF NOT EXISTS checkpoints (
            session TEXT PRIMARY KEY, step INTEGER, state TEXT, ts REAL)""")

    # -- the effect sandwich (Pi Durable spec, section 5.2) ---------------------------------------
    def effect(self, session, key, fn, idempotent=False):
        """Run fn() at most once per (session, key), unless it is idempotent.
        key must be deterministic, e.g. f"step{n}:tool:{call_id}" or f"step{n}:model"."""
        row = self.db.execute("SELECT phase, payload FROM effects WHERE session=? AND key=?", (session, key)).fetchone()
        if row and row[0] == "done":
            return json.loads(row[1])                       # replay: the effect already happened, reuse its result
        if row and row[0] == "intent" and not idempotent:
            # We crashed between starting and recording. The effect may or may not have happened.
            outcome = {"interrupted": True, "note": f"'{key}' was started before a crash and its outcome is unknown. "
                       "Check the current state before repeating it."}
            self._done(session, key, outcome)
            return outcome
        self.db.execute("INSERT OR REPLACE INTO effects VALUES (?,?,?,?,?)", (session, key, "intent", None, time.time()))
        result = fn()                                          # the external effect, outside any transaction
        self._done(session, key, result)
        return result

    def _done(self, session, key, result):
        self.db.execute("UPDATE effects SET phase='done', payload=? WHERE session=? AND key=?",
                        (json.dumps(result, default=str), session, key))

    # -- state checkpoints at step boundaries (eve's step function) ------------------------------
    def save(self, session, step, state: dict):
        self.db.execute("INSERT OR REPLACE INTO checkpoints VALUES (?,?,?,?)",
                        (session, step, json.dumps(state, default=str), time.time()))

    def load(self, session):
        row = self.db.execute("SELECT step, state FROM checkpoints WHERE session=?", (session,)).fetchone()
        return (row[0], json.loads(row[1])) if row else (0, None)

def run_durable(journal, session, initial_state, step_fn, done):
    """Resume from the last checkpoint, then step until done. step_fn(state, n, effect) -> state.
    Inside step_fn, every model call and tool call goes through effect(key, fn, idempotent)."""
    n, state = journal.load(session)
    state = state or initial_state
    while not done(state):
        effect = lambda key, fn, idempotent=False, n=n: journal.effect(session, f"step{n}:{key}", fn, idempotent)
        state = step_fn(state, n, effect)
        n += 1
        journal.save(session, n, state)                      # the step boundary is the checkpoint
    return state

Wiring:

  • Your step() from Chapter 1 becomes step_fn(state, n, effect). Wrap the model call as effect("model", lambda: llm.complete(...)) and each tool call as effect(f"tool:{call.id}", lambda: call_tool(...), idempotent=tool.idempotent).
  • Mark read, grep, recall idempotent. Leave bash, write, edit non-idempotent unless you can prove otherwise.
  • State must be JSON: messages, checkpoint text, counters. Anything else (open files, live processes) is not state; recreate it on start.

Stage 4 gate: kill it ten times

  1. Run a long eval task. At 10 random moments, kill -9 the process and restart it with the same session ID.
  2. Check: the task finishes; no model call is paid twice for a completed step; no non-idempotent tool ran twice; every interrupted effect produced the "outcome unknown" note.
  3. Post the result, and the one bug you found. There is always one.

8. Exercises

  1. Kill test. Run a 20-step task and kill the process at a random step, ten times. Every restart must finish the task without repeating a completed effect.
  2. Unknown outcome. Kill the process between intent and outcome for a file write. On restart, synthesise an honest "unknown" result and check the model looks before it writes again.
  3. Torn line. Truncate the last line of your journal by a few bytes. Your reader must report it and load everything before it.
  4. Two writers. Start two processes on the same session. Your lock must make the second wait or fail clearly.
  5. Idempotent effect. Make a "create pull request" tool check for an existing one with the same branch before creating. Repeat the kill test.
