Stage 4 · Durability and surfaces · Chapter 12

Surfaces: embedding, protocols and channels

The model needs the same thing from every front door: text in, text out (fact 1). The front doors need very different things from the harness: a terminal wants a live stream, an editor wants diffs and approvals, a script wants one JSON answer, GitHub sends a webhook and waits hours. This chapter derives where to put the boundary between the harness and its surfaces, then takes ten design decisions: one core or many, headless mode, the client protocol, long turns and reconnection, embedding as a library, chat and work channels, trust at the door, remote control, live views, and testing every surface. It shows each harness's surfaces and keeps the session server and GitHub channel you build.

Level: intermediate to advanced Time: about 12 hours with the build Needs: Chapters 1 to 11 Harnesses read: Pi, eve, fx, nanocode, Codex, Claude Code, Kimi Code, Qwen Code, Trae Agent
Before you start: skip check
  1. Why should a terminal UI, an editor plugin and a Slack bot not each have their own agent loop?
  2. A turn takes 40 minutes and the laptop sleeps halfway. What does the client protocol need so the user sees everything when it wakes?
  3. Codex rejects a command that needs a human approval if no capable client is connected. Why not wait?
  4. What does Qwen Code's channel list tell you about who it is built for?
Answers
  1. You would build the harness again for each surface and their behaviour would drift. One core behind thin adapters keeps one behaviour and one set of tests.
  2. An event stream with sequence numbers the client can resume from, and pending approvals that replay on reconnect.
  3. A headless run with nobody able to approve would hang forever; failing clearly lets the model or the operator choose another path.
  4. DingTalk, Feishu, WeCom, WeChat and QQ: teams in Chinese workplaces, where the channel a request arrives on is part of the harness.

1. Split the harness from its front doors

Put the boundary where the needs diverge. Behind it, one harness that only knows sessions, messages and events. In front of it, thin adapters that translate one surface's input into a message and the harness's events into that surface's output. Two facts shape the API: a turn can take minutes or days (fact 6), so a front door subscribes to events instead of holding a request open; and input from a public channel is untrusted text (fact 5), so deciding who may start or steer a session belongs at the door.

2. The decisions, one at a time

Decision 1. One core, or a loop per surface?

Every harness in this book that has several surfaces converged on one core. The Claude Code paper reports that the same loop serves the command line, the SDK and the IDE integrations. Codex's IDE extension and desktop app are clients of its app server. Kimi Code puts the boundary exactly where this chapter derives it: a server exposes its own agent protocol over REST and WebSocket, and the terminal UI, web UI, desktop app and VS Code extension are all its clients.

Decision 2. What does headless mode return?

Scripts and CI jobs need one request in and one machine-readable answer out. Every harness has a one-shot mode; they differ in what comes back.

Decision 4. How do long turns survive the client?

Once the person is remote, the protocol must handle what a terminal never had to: the client disconnects, sleeps, reconnects from another device. Codex's app-server documentation lists the cases.

Decision 5. Can the harness run inside someone else's app?

Embedding turns the harness into a component: a product team adds an agent to their app with their own tools and UI.

  • fx ships its agent core as a library built both as a native Node.js addon and as WebAssembly: one call runs an agent with your own tools, MCP clients and skills, another embeds the fx terminal. Vercel's AI SDK added an fx adapter, so an app can run fx as one option behind a common harness API.
  • nanocode builds every reusable crate for native and WebAssembly. Bindings exist for TypeScript (one WebAssembly module), Swift for macOS and iOS, and C for a game engine or any host. An embedder supplies one host object for scheduling, sleeps, clocks and secure random bytes.
  • Pi runs as an SDK and over RPC; OpenClaw embeds it as its engine, and a composition runtime underlies Pi Durable.
  • Claude Code exposes the harness as the Claude Agent SDK. Codex has Python and TypeScript SDKs over its app server. Qwen Code ships SDKs for TypeScript, Python and Java.

Decision 6. How do chat and work channels connect?

A channel is a surface where the agent is a participant: a Slack thread, a GitHub issue, a Feishu group. Each has its own addresses, delivery rules and identity.

eve's README states the split precisely: the channel normalises inbound transport, applies authentication and delivery policy and owns channel-local addresses; the harness does one unit of work. Qwen Code's list shows the other half of the lesson: for a team in China, the channel a request arrives on (DingTalk, Feishu, WeCom) is part of the product, not an add-on.

Decision 7. Who may talk to the agent?

A public channel lets anyone type into the agent's context. Chapter 7's rule applies at the door: decide who may start or steer a session before the text reaches the model. In eve, authentication and delivery policy are the channel's job. Only messages from authorised people count as the user's intent (Codex's reviewer rule); an issue comment from a stranger is untrusted content, like a web page. A GitHub channel that runs on any comment is a remote-control interface for anyone who can comment.

Decision 8. Can the user drive a local agent remotely?

Sometimes the work must run on the user's machine (their files, their credentials) but the user is elsewhere. Codex offers remote control of a session from another device. Kimi Code tunnels a local server through a relay so a phone can drive it. Both keep the harness local and move only the client, which keeps the machine's data where it is.

Decision 9. How do several viewers see one session?

A session watched in a terminal, a browser and a phone at once needs every viewer to see the same state. nanocode folds the event log into live views and sends diffs to every subscribed socket, the same "log is the truth, views are projections" pattern as Chapters 6 and 10. Pi Durable is built for several people joining one task.

Decision 10. How are surfaces tested?

Every new surface is a new way to get behaviour wrong. Kimi Code runs one end-to-end scenario on its terminal, web, desktop and agent-protocol surfaces. eve ships a conformance kit every channel must pass. Both work only because the surfaces are thin: the behaviour being tested lives in one core.

5. Choosing surfaces

This book's harness: a small HTTP session server (create, send, answer, cancel) with a sequence-numbered event stream, a one-shot JSON mode, and a GitHub channel that maps an issue to a session and only accepts commands from repository collaborators.

6. Research and the Chinese view

  • The harness boundary moves. The Dive into Claude Code paper lists where, when, what and with whom the agent acts as an open design direction; surfaces are how that boundary moves.
  • Enterprise convergence. Stripe, Ramp and Coinbase independently built internal agents triggered from Slack and GitHub; an Aliyun article lists many entry points as one of the problems that forced the same architecture.
  • Chinese practice. Qwen Code's workplace channels and Kimi Code's server-first design are the two clearest surface architectures read for this book. Alibaba's desktop agent QoderWork, launched in January 2026, reached several hundred thousand users, with close to 80% starting three or more tasks a day: the same harness idea delivered as a desktop surface.

7. Build: a session server and a GitHub channel

"""One harness, many front doors: a session server with an event stream, plus a GitHub channel."""
import asyncio, hashlib, hmac, json, os, uuid
from fastapi import BackgroundTasks, FastAPI, Header, HTTPException, Request
from fastapi.responses import StreamingResponse

app = FastAPI()
SESSIONS: dict[str, dict] = {}        # in production: the Chapter 11 journal, not a dict

def run_turn(session_id: str, text: str, emit):
    """Replace with your harness. emit(event) is called for text deltas, tool calls and the final reply."""
    emit({"type": "turn.started"})
    emit({"type": "text", "delta": f"(working on: {text})"})
    emit({"type": "turn.completed", "reply": f"done: {text}"})

def emitter(session_id):
    s = SESSIONS[session_id]
    def emit(event):
        event = {"seq": len(s["events"]), **event}
        s["events"].append(event)                  # the log is the source of truth; clients replay from any seq
    return emit

@app.post("/sessions")
def create_session(body: dict | None = None):
    sid = uuid.uuid4().hex[:12]
    SESSIONS[sid] = {"events": [], "busy": False, "address": (body or {}).get("address")}
    return {"session_id": sid}

@app.post("/sessions/{sid}/messages")
def send(sid: str, body: dict, tasks: BackgroundTasks):
    s = SESSIONS.get(sid)
    if s is None:
        raise HTTPException(404)
    if s["busy"]:                                  # queue as steering instead of starting a second turn
        s["events"].append({"seq": len(s["events"]), "type": "steering.queued", "text": body["text"]})
        return {"queued": True}
    s["busy"] = True
    def work():
        try: run_turn(sid, body["text"], emitter(sid))
        finally: s["busy"] = False
    tasks.add_task(work)
    return {"accepted": True}

@app.get("/sessions/{sid}/events")
async def events(sid: str, after: int = -1, follow: bool = True):
    """Server-sent events. A client that reconnects passes the last seq it saw and misses nothing."""
    if sid not in SESSIONS: raise HTTPException(404)
    async def stream():
        seq = after
        while True:
            for e in SESSIONS[sid]["events"][seq + 1:]:
                seq = e["seq"]
                yield f"id: {seq}\ndata: {json.dumps(e)}\n\n"
            if not follow or (SESSIONS[sid]["events"] and SESSIONS[sid]["events"][-1]["type"] == "turn.completed"
                              and not SESSIONS[sid]["busy"]):
                return
            await asyncio.sleep(0.2)
    return StreamingResponse(stream(), media_type="text/event-stream")

# ---- a channel: GitHub issue comments start or continue a session -------------------------------
def verify(secret: str, body: bytes, signature: str | None) -> bool:
    expected = "sha256=" + hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()
    return bool(signature) and hmac.compare_digest(expected, signature)

@app.post("/channels/github")
async def github(request: Request, tasks: BackgroundTasks, x_hub_signature_256: str | None = Header(None)):
    raw = await request.body()
    if not verify(os.environ.get("GITHUB_WEBHOOK_SECRET", ""), raw, x_hub_signature_256):
        raise HTTPException(401, "bad signature")
    ev = json.loads(raw)
    comment = ev.get("comment", {}).get("body", "")
    if "@harness" not in comment or ev.get("comment", {}).get("author_association") not in ("OWNER", "MEMBER", "COLLABORATOR"):
        return {"ignored": True}                   # only trusted users may start privileged work
    address = f"{ev['repository']['full_name']}#{ev['issue']['number']}"   # one session per issue
    sid = next((k for k, v in SESSIONS.items() if v["address"] == address), None) or create_session({"address": address})["session_id"]
    return send(sid, {"text": comment.replace("@harness", "").strip()}, tasks)

Wiring:

  • Replace run_turn with your durable harness from Chapter 11, calling emit for text deltas, tool calls and the reply. Store events in the journal, not in memory.
  • Make your CLI a client: create a session, post messages, read /events. Now the terminal is just one surface.
  • Expose the server (a small VM, or a tunnel), add the webhook to your repo with a secret, and comment @harness on an issue. Post replies back with the GitHub API from the trusted process only.

Stage 4 gate

  1. Start a task from a GitHub comment, kill the server mid-task, restart it, and watch the task finish and reply on the issue.
  2. Reconnect a client with ?after=<seq> mid-stream and confirm no event is missed or repeated.

8. Exercises

  1. Reconnect. Start a long task over your session server, disconnect the client for two minutes, reconnect with the last sequence number and check that no event is missing or duplicated.
  2. Schema output. Add a one-shot mode that validates the final answer against a JSON Schema and retries once on failure.
  3. ACP. Expose your harness over the Agent Client Protocol and drive it from an editor that speaks it.
  4. Door policy. In your GitHub channel, reply to a stranger's command with a polite refusal and log it; accept the same command from a collaborator.
  5. Cross-surface test. Run one scenario through the terminal, the HTTP API and the GitHub channel, and assert identical tool calls.
