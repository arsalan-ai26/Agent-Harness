Subagents and Code Mode

Two ideas attack the same cost from different sides. Subagents move work into a separate context and bring back only a report. Code Mode lets the model write one program that calls many tools and returns only the result. Both keep intermediate noise out of the main context. Pi rejects subagents, nanocode makes each one a durable session, and both Pi and nanocode ship Code Mode. You build a subagent tool and a Python Code Mode cell runner, and measure what each saves.

  1. What does a parent agent see of a subagent's work?
  2. Reading 30 files to find one function: how many model round trips with normal tools, and with Code Mode?
  3. What is Pi's main objection to subagents?
Answers
  1. Usually only its final report. The parent chose the subagent's context and cannot see its full conversation unless the harness keeps a transcript.
  2. Normal tools: up to 30 tool results in context, often many steps. Code Mode: one program reads all 30 in a loop and returns one line, one round trip.
  3. They are a black box: the orchestrator decides what context the child gets and the user cannot see what it did. Zechner prefers gathering context in a separate session and saving it as a file.

1. Two ways to keep the context clean

2. Code tour

nanocode: a durable task tree

crates/runtime/subagents owns spawning, waiting, messages, residency, completions, budgets and a journal. Constants in lib.rs: DEFAULT_MAX_RESIDENT_SUBAGENTS = 16, and only 2 resident when durable; a completion request has its own prefix so the parent can tell a child's report from a user message. There is a spawn policy and router (SpawnPolicy, SpawnRouter) and a roster. The README's design point: a Code Mode cell can spawn children, and each child is a durable session of its own, so nothing is a black box.

nanocode and Pi: Code Mode

nanocode's Claude Code Mode prompt (crates/backends/claude/prompts/code_mode.md) is a short course in when to use it: orchestrate related calls whose next step needs no model judgement; keep the whole lifecycle in one cell; use Promise.all for independent calls and Promise.allSettled when one may fail; await long commands instead of polling; return only what the next reasoning step needs; use separate calls when a result needs judgement, user input or a progress update. The QuickJS worker gives each cell a fresh context. Pi ships the same idea as packages/codemode and in Pi Durable (src/codemode/).

eve: subagents are agents

A subagent is a folder under agent/subagents/ that reuses defineAgent, with its own instructions, tools, model and sandbox. The main agent delegates and combines results. The Foreman software factory (Chapter 13) is four subagents with separate sandboxes; its Reviewer never sees the Implementer's reasoning, on purpose.

fx: subagents with a smaller step limit

src/core/subagent/ (tool_host.zig, execution.zig, agent_adapter.zig) runs subagents with their own step limit, which the adapter sets lower than the parent's.

Pi: no subagents in core

Pi's README lists no subagents as a deliberate choice. For code review, a slash command runs pi --print as a separate process; for research, gather context in a separate session and save it as a file the next session reads.

3. Design decisions compared

ChoiceProConWho
No subagents; files carry contextFully visible; nothing hiddenManual; no parallelismPi
Subagents as durable sessionsInspectable, resumable, budgetedComplex runtimenanocode
Subagents as agents in foldersEach has its own tools and sandboxMore configurationeve
Code ModeFewer round trips and tokens; parallel callsNeeds a sandboxed interpreter; model must write correct codenanocode, Pi
When to use which

Use a subagent when the work needs judgement at each step but its details are not needed afterwards (explore a codebase, review a diff). Use Code Mode when the steps are mechanical (read many files, filter, aggregate, run a command per item). Use neither when the user needs to watch and steer the work.

4. Research and the Chinese view

  • Planner, generator, evaluator. Anthropic's 2026 long-running harness splits work across three agents and keeps the evaluator separate so the generator does not grade itself.
  • Manus moved planning out. Updating a todo.md in the main agent used about a third of all actions, so Manus moved to a planner agent that calls executor sub-agents (Lance Martin's notes).
  • Programmatic tool calling. Anthropic's API feature and open-source versions run model-written code that calls tools, keeping data-heavy intermediate results out of context.
  • Chinese practice. Kimi's K2.x releases emphasize long agent runs and agent swarms; Chinese analyses of Claude Code's leaked source describe its subagents, task graph and team mailboxes as the parallel layer of the harness.

5. Build: a subagent tool and Code Mode cells

"""Subagents (child sessions with their own context and budget) and Code Mode (one program calls many tools)."""
import json, subprocess, sys

# ---- subagents --------------------------------------------------------------------------------
def make_task_tool(run_agent, max_depth=1):
    """run_agent(system, task, tools, max_steps, transcript_path) -> final text. The parent sees only that text."""
    def task(description: str, prompt: str, tools: list[str] | None = None, depth: int = 0, max_steps: int = 30):
        if depth >= max_depth:
            return "error: subagents may not spawn subagents"
        path = f"subagent-{abs(hash((description, prompt))) % 10**8}.jsonl"   # a real, inspectable transcript
        system = ("You are a subagent. Do only this task, then reply with a short report: what you found or "
                  "changed, with file paths and line numbers. Your report is all the parent will see.")
        result = run_agent(system, prompt, tools or ["read", "bash"], max_steps, path)
        return f"{result}\n[subagent transcript: {path}]"
    return task

# ---- Code Mode ----------------------------------------------------------------------------------
PRELUDE = r'''
import json, sys
class _Tools:
    def __getattr__(self, name):
        def call(**args):
            sys.__stdout__.write("\x00CALL" + json.dumps({"name": name, "args": args}) + "\n"); sys.__stdout__.flush()
            reply = json.loads(sys.stdin.readline())
            if reply.get("error"): raise RuntimeError(reply["error"])
            return reply["result"]
        return call
tools = _Tools()
_out = []
def result(value): _out.append(value if isinstance(value, str) else json.dumps(value, default=str))
'''
EPILOGUE = '\nsys.__stdout__.write("\\x00DONE" + json.dumps("\\n".join(_out)) + "\\n")\n'

CODE_MODE_DESCRIPTION = """Run a Python program that calls tools as functions: tools.read(path=...), tools.bash(command=...),
tools.edit(path=..., edits=[...]). Each returns the tool's text. Use loops and conditionals for steps that need no
judgement, and call result(value) with only what you need for your next decision; nothing else returns to you.
Use separate calls when an intermediate result needs your judgement."""

def exec_cell(code: str, call_tool, timeout=300, python=(sys.executable, "-I")):
    """Run one cell in a fresh interpreter. Tool calls come back over stdout and are answered on stdin.
    In production, run `python` inside the Chapter 7 sandbox container."""
    proc = subprocess.Popen([*python, "-c", PRELUDE + code + EPILOGUE], stdin=subprocess.PIPE,
                            stdout=subprocess.PIPE, stderr=subprocess.PIPE, text=True)
    calls, printed = 0, []
    try:
        for line in proc.stdout:
            if line.startswith("\x00CALL"):
                req = json.loads(line[5:])
                calls += 1
                out = call_tool(req["name"], req["args"])
                reply = {"error": out[7:]} if out.startswith("error: ") else {"result": out}
                proc.stdin.write(json.dumps(reply) + "\n"); proc.stdin.flush()
            elif line.startswith("\x00DONE"):
                proc.wait(timeout=5)
                return f"{json.loads(line[5:])}\n[cell made {calls} tool calls]"
            else:
                printed.append(line)          # stray prints are kept short; result() is the real channel
        proc.wait(timeout=timeout)
        err = proc.stderr.read()[-3000:]
        return f"error: cell failed after {calls} tool calls\n{err}\n{''.join(printed)[-1000:]}"
    finally:
        if proc.poll() is None:
            proc.kill()

Wiring:

  • run_agent is your Chapter 1 to 8 loop with a different system prompt, tool subset, step limit and its own session file. Register task as a tool.
  • Register exec_cell as a tool named python with CODE_MODE_DESCRIPTION. Its call_tool is your registry's call from Chapter 3, so every nested call still passes the Chapter 7 gate.
  • Run the cell interpreter inside the Docker sandbox in production: replace python= with a docker run -i ... command.

Measure

Pick 5 of your tasks that read many files. Run each three ways: plain tools, with the task tool, with Code Mode. Record main-context tokens, total tokens, wall time and pass rate. Expect Code Mode to win on tokens and time for mechanical searches, and subagents to win when judgement is needed.
