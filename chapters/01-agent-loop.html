The agent loop

The model can neither act nor remember (facts 1 and 2 from Chapter 0), so something has to alternate between asking it and acting for it. That alternation is the agent loop. It looks like ten lines of code, and every harness agrees on those ten lines. They disagree on everything around them: who owns the loop, when a turn is allowed to end, when tools start, what happens to a message typed mid-turn, where retries live and what a crash costs. This chapter takes those decisions one at a time, shows how nine harnesses answered each one and why, and ends with a working agent you build yourself.

Level: intermediate Time: about 20 hours with the build Needs: Python 3.11+, an API key for any OpenAI-compatible endpoint Harnesses read: Pi, Pi Durable, eve, fx, nanocode, Codex, Claude Code, Kimi Code, Qwen Code, Trae Agent
Before you start: skip check
  1. What is the difference between a turn and a step, and why does Pi use the word "turn" for what eve calls a "step"?
  2. A user types a correction while the agent is running tools. Name three different moments a harness could deliver it, and one harness that uses each.
  3. Codex and Claude Code start a tool before the model has finished its reply. What does that buy, and what does it make harder?
  4. Why can't "the model replied without a tool call" be the only way a turn ends?
Answers
  1. A step is one model call plus the tool calls it asked for; a turn is one user input and every step until the agent answers. Pi's loop calls one model reply plus its tool calls a "turn" and the whole run an "agent run". The concepts are the same; the names are not, so always check a harness's glossary.
  2. At the next step boundary (Pi's steering queue, Codex, fx, Kimi Code), by cancelling a model call that has not produced output yet (eve's default steering, nanocode's optional preemption), or only after the turn ends (Pi's follow-up queue, eve's queue policy).
  3. Latency: a slow read can run while the model is still writing the rest of its reply. It makes ordering, cancellation and permission checks harder, because a tool can be running while the reply that asked for it is still incomplete.
  4. That signal is a sample (fact 5). A model can stop before the work is done, or never stop. Every serious harness adds checks it does not leave to the model: limits, loop detectors, budgets, stop hooks and completion checks.

1. The one thing every loop does

Start from what the model is: a function from text to text that keeps nothing between calls. It cannot run a command (fact 1) and it cannot see what happened last time unless you show it (fact 2). Put those two facts together and the loop is forced on you. Something must send the model the whole story so far, read what it asks for, do it, write down the result, and send the longer story back. That something repeats until the model stops asking for actions.

Two consequences follow before you write any code. First, the history only grows, and each step resends all of it, so total tokens grow roughly with the square of the number of steps. OpenAI's write-up of the Codex loop says exactly this: the loop is quadratic in the JSON it sends, which is why caching shapes the design (Unrolling the Codex agent loop). Second, the only moment the history is complete and consistent is between steps: after the model replied and every tool it asked for has a result. That moment, the step boundary, is where every harness does its housekeeping, and most of the decisions below are about what happens there.

2. Turn, step, run, session, and why the names do not match

Because the step boundary is the only consistent moment, the step is the natural unit of an agent, and every other unit is a group of steps. The concepts are the same in every harness. The words are not, and reading source without knowing that is the fastest way to get confused.

Two more words you need: a steering message arrives while a turn is running and should change its course; a follow-up message arrives while a turn is running but should wait until it ends.

3. Anatomy of one step

Stretch one step out and the same stages appear in every harness that does real work. They differ in which stages exist, how much each does, and what may interrupt them. The Claude Code study lists nine stages for one iteration of its loop: settings resolution, state initialization, context assembly, the pre-model context shapers, the model call, tool dispatch, the permission gate, tool execution and the stop check (Dive into Claude Code). Generalised across the nine harnesses, it looks like this.

Two stages deserve a first-principles note now, because they are easy to forget. Stage 5, checking calls, exists because a tool call is sampled text (fact 5): it can name a tool that does not exist, carry arguments that do not match the schema, or be cut off because the reply hit its output-token limit. Pi refuses to run any call from a reply that stopped for length, because a salvage parser can produce arguments that parse but are silently incomplete. Kimi Code validates every finished call against its schema and asks again without running a bad one. Stage 8, ordering, exists because providers expect results in the order the calls were made. Even harnesses that run tools in parallel buffer the results and append them in request order.

4. The decisions, one at a time

Each subsection below states the question, derives the reasonable answers from the facts, says what each answer costs, and shows who chose what. Section 5 then walks each harness as a whole, and section 6 puts everything in one table.

Decision 1. Who owns the loop?

The loop has to live somewhere, and where it lives decides what a crash costs. There are four answers in the code we read.

  • A. An ordinary loop in the process. The program runs while there are tool calls, call the model and run them. Easiest to read, easiest to debug, fastest. A crash loses the step in flight and anything not yet written down. Pi, fx, Codex, Claude Code, Qwen Code and Trae Agent all start here; most of them then write finished messages to disk so a session can be resumed, which recovers the conversation but not the half-done step.
  • B. An event-sourced actor. Kimi Code's loop is an actor: commands arrive in an inbox, the actor handles one at a time, and every change is recorded as an event (turn started, step started, message appended, tool started, tool ended, model retried). The loop's state is never stored directly; it is computed by replaying the events. Since the model holds nothing (fact 2), treating the log as the agent's real memory is the literal reading of the facts. After a crash the log is replayed and the harness can tell whether the last step ended with tool calls that never got results, and continue from there.
  • C. A step function. eve has no loop of its own. Its kernel does one step and returns the new session plus what should run next. A workflow engine (Vercel's Workflow SDK) calls it, saves the result, and calls it again, possibly in another process, possibly days later. By default one step is one model call plus the inline tool calls that follow it; an experimental setting groups several model calls into one saved step to reduce checkpoint overhead, at the cost of a larger replay unit.
  • D. A durable state machine. Pi Durable models a model response as a task with named phases: prepare, request, poll (for providers that answer later), retry, tools, and a few finishing phases. Each phase change is one atomic commit. nanocode does the same idea differently: every model call and every tool call is a journaled effect, so its README promises that a turn finishes after its process dies.
OwnerBuys youCosts you
A. In-process loopSimple code; any state you like; lowest latencyNo durability; hidden state accumulates in variables and is hard to save later
B. Event-sourced actorOne source of truth; replay for debugging and resume; every change has a recordEvery state change must be an event; reducers must stay compatible with old logs
C. Step functionDurability and long waits come from the engine; sessions can move between deploymentsAll state must be saveable and replay-safe; you depend on the engine and its version rules (eve documents "stranded" sessions after upgrades)
D. Durable state machineExact resume of an interrupted phase; external effects get intent and outcome recordsThe most design work: every phase, every effect, every migration of old records
Why this decision comes first

Moving from A to B, C or D later is hard, because an in-process loop quietly accumulates state that is not in the history: a retry counter, a half-streamed reply, a flag that says a reminder was already sent. Every one of those has to be found and made saveable. If you might ever need durability, keep the loop's state in one object you could write to disk, even while the loop is still shape A. That is what our build does.

Decision 2. When is a turn allowed to end?

The model can only say "I am done" one way: by replying without a tool call. Every harness uses that as the main signal. None trusts it alone, because the signal is a sample (fact 5): a model stops early with work undone, stops with an empty reply, or never stops at all. So the real question is what the harness checks before it accepts a stop, and what limits it imposes when the model will not stop.

Four mechanisms appear, each answering a different way the stop signal goes wrong.

  • Limits for a model that will not stop. A step count, a token budget, or both. The surprising finding is how many harnesses ship without a step limit by default. fx's default is zero, meaning unlimited; Kimi Code's per-turn step limit is off unless configured; Pi's loop has none; Codex has none by default and an optional token budget behind a feature flag. eve uses money instead of steps: before every model call it checks a usage budget (by default 40 million new input tokens per window) and, when it is crossed, pauses the turn and asks the person whether to continue. Qwen Code caps a turn at 100 rounds; Trae Agent at 200 steps; Claude Code has a configurable maximum. The reasoning behind "no default limit" is that a step count is a bad proxy for cost or progress, and a coding task can legitimately need hundreds of tool calls; the reasoning behind a limit is that an unattended run with no ceiling is a blank cheque.
  • Detectors for a model that is stuck. A model that repeats an identical tool call gets an identical result, so repeating it cannot help. Qwen Code ends a turn after 5 identical tool calls in a row, a content chunk repeated 10 times, or the same file read 8 times. fx ends a turn when the same shell command fails in three consecutive steps with no file changed in between, and resets the count after any edit, because rerunning a command after an edit is a new attempt, not a repeat.
  • Recovery for a reply that is not really a stop. Some replies have no tool call but are not answers either. fx asks the model once to continue when a reply has no text and no tool call (some providers return that when a tool call fails to form), and ends the turn as failed if it happens twice in a row. Trae Agent never accepts a text-only reply: it answers "It seems that you have not completed the task" and continues.
  • Checks for a stop that is premature. The model says it is done; the harness checks the world. Trae Agent's turn can only end through its task_done tool, and in benchmark mode the harness rejects it if the change, minus test files, is empty. Codex and Claude Code run Stop hooks: user code that can block the stop and hand the model a reason to keep going. Codex treats a block as a new message in the same turn; the Claude Code study lists hook intervention as one of its five stop conditions.
The design tension

Every check you add is a place where the harness overrides the model. Too few and an unattended agent stops early or loops forever. Too many and the harness fights a model that was right, or burns tokens on a forced continuation. The pattern the stronger harnesses share: limits and detectors that end the turn with a clear reason, and a small number of completion checks that look at the world (tests, a diff), never at the model's own claim.

Decision 3. When do tools start, and how many at once?

A model can ask for several tool calls in one reply. Two independent questions follow: do you wait for the whole reply before starting any tool, and once you start, which calls may run at the same time?

Derive the grouping rule from fact 6. A read does not change the world, so two reads in any order give the same results: running them together only saves time. A write changes the world, so a write and anything that touches the same thing must keep their order. Every harness that runs tools in parallel encodes some version of "reads together, writes alone". They differ in how they know which is which.

Starting tools during the stream is a latency trade. It overlaps tool time with model time, which matters most when the model writes a long explanation after its tool calls. It also means a tool can be running while the rest of the reply is still arriving, so cancellation, permission prompts and ordering all have to handle a reply that is not finished yet. The Claude Code study places this design between serial dispatch and fully speculative execution.

Decision 4. What happens to a message typed mid-turn?

People do not wait. They see the agent heading the wrong way and type a correction, or think of the next task and type it early. The model reads its input once, at the start of a call (fact 2), so a message that arrives mid-call cannot reach it until some later call. The design space is which later call, and whether to throw away work to get there sooner.

The details matter more here than anywhere else in the loop, because they decide whether the person feels in control.

  • Pi has two queues. Steering messages are checked after each step's tools finish and join before the next model call; the tool calls already made are not skipped. Follow-up messages are checked only when the agent would otherwise stop. Each queue drains either one message at a time (the default) or all at once. Pi's outer loop exists to serve the follow-up queue, and to honour a finish-turn hook that asks for one more request.
  • eve lets the sender choose per message. The default, steer, is the most aggressive of all nine harnesses: if the model has not started producing visible output, eve stops the pending model call and restarts it with the new message in the same turn; once output has started, the message waits for the next step boundary so streamed text is not thrown away. Running tools always finish and keep their results. The other policy, queue, holds the message until the turn ends. Only the turn's own caller can steer it; anyone else's message waits.
  • Codex drains its input queue at the top of every iteration, so typed input joins before the next sampling request. Messages from other agents arrive through a mailbox and can cut a sampling request short.
  • fx frames each boundary message by who wrote it: the user's as a live update, a parent agent's as that agent's feedback, and a subagent's as an untrusted report, never as the user's words. A message can also be a handoff, which ends the current turn so the queued prompt runs as its own turn.
  • Kimi Code has three inbox lanes: normal prompts (the next turn), notify (messages that join the current turn at the next step, which is what steering moves a prompt into) and remind (system reminders attached to the next request).
  • nanocode stores steering messages durably, each with the model-call index after which it was accepted, so a resumed turn knows exactly where each one belongs. It can optionally let a steer preempt a model call in progress.

The trade-off is responsiveness against waste and confusion. Cancelling a model call responds fastest but throws away tokens already paid for, and if output was already visible it rewrites what the person saw. Waiting for the boundary never wastes work but can feel slow when a step runs a long command. Waiting for the end of the turn is right for "do this next" and wrong for "stop, that is the wrong file". Offering both a steer and a queue, as Pi, eve and Kimi Code do, lets the person say which they mean.

Decision 5. Where do failures and retries live?

Two kinds of failure reach the loop, and the first-principles answer for each is different.

Tool failures are information. A failing test or a missing file is exactly what the model needs to see to change course, so every harness returns a tool error to the model as the tool's result instead of stopping. Trae Agent goes one step further: after a step with failed tools it adds a message saying the tool failed and suggesting a different approach or different parameters. Permission denials work the same way; the Claude Code study notes that a denial is returned with its reason so the model can try a safer action.

Model-call failures are not information the model can use: a rate limit, an overloaded server, a dropped stream. The model never sees them; the harness retries. The question is at which layer, and the nine harnesses spread across three.

Why spread them out? Each layer can only fix what it can see. The transport layer can resend the same bytes, which fixes a dropped connection and nothing else. The loop layer can change the request: if the reply was cut off, ask for more output tokens; if the prompt is too long, compact and try again. Only the session layer can decide that a whole step should be redone, and it has to be careful about history: Pi keeps the failed attempt in its raw record but leaves it out of what the model sees, so the retry is clean without lying about what happened.

One rule is shared by the careful harnesses: a retry must not leak half a reply. Qwen Code's design notes record a bug class from before its loop was unified: two of its surfaces dropped the tool calls collected before a retry or a model fallback and a third did not, so the same failure produced different behaviour depending on where you ran it.

Decision 6. Where can other code change the loop?

Everything a harness does beyond the bare cycle (compaction, permissions, reminders, stop checks, telemetry) needs a place to attach. Hard-coding it into the loop makes the loop unreadable; exposing named points keeps the loop small and puts the policies outside it. Pi and Kimi Code are the clearest examples, and they place their hooks almost identically.

Two properties make a hook system safe to build on. First, a defined failure policy: Pi's contract says its queue and context hooks must never throw and must return a safe fallback; Kimi Code's hooks declare what happens if they fail, and a hook that blocks records why. Second, one path for every call: Pi exposes a function that runs a tool call through the same validation and before and after hooks as a model-issued call, so a tool that calls other tools cannot bypass a permission check. Chapter 8 covers hooks in depth; for the loop, the decision is only where the points are.

Decision 7. One loop, or one per surface?

A harness grows front doors: a terminal UI, a headless mode, an editor protocol, an SDK, a server, subagents. The tempting shortcut is to give each its own loop. Qwen Code's design notes are the best case study in this book of what that costs. Before its unification work it had seven implementations of the loop, one or more per surface. The copies drifted: the session turn cap was computed three different ways and one surface had none, the duplicate-tool-call suppression was written four times, one surface ran a cut-off edit that the others refused, and several bugs were found only by comparing copies. The fix was one shared loop in the core with surfaces as thin hosts, rolled out surface by surface behind a setting, each move gated on a parity suite. The next step, in progress, re-expresses that loop as an event-driven state machine with ten named events, one owner per piece of state, round identifiers so late events from an abandoned round are dropped, and a cap on how long cancellation may take.

The others reached the same conclusion from the start. The Claude Code study reports one loop for the interactive CLI, headless mode, the SDK and the IDE. Kimi Code's terminal, web, desktop and editor surfaces are all clients of one server and one core loop, and its end-to-end tests run the same scenario on all four. The lesson is cheap to state and expensive to learn: the loop is policy, and policy must have exactly one copy.

Decision 8. How do you know the loop is right?

Loops fail at the edges: a second empty reply, a steer that arrives during compaction, a crash between a tool's effect and its record. Ordinary tests rarely reach those orders of events. fx takes the most rigorous approach in this book: it writes formal models of its loop's rules in TLA+ and checks them with a model checker. Its agent-runtime model covers the empty-reply nudge (asked once, a second empty reply in a row ends the turn as failed, the step limit always holds) and the malformed-tool-call feedback (a third malformed reply ends the turn). Each model comes with deliberately planted bugs that the checker must catch, and a driver that runs the real binary against a local fake model and has the checker validate every recorded run. Its saved-turn model checks that the next request always starts with the previous request's exact messages, which is what keeps the provider's prompt cache valid.

You do not need TLA+ for your first harness. You need the habit behind it: write down the loop's rules as statements ("a turn never ends with an unanswered tool call", "a steering message is delivered exactly once"), then test those statements, including in odd orders. Kimi Code's fake model and Pi's separate loop package make exactly that kind of test cheap.

5. The nine loops, harness by harness

Each subsection describes one loop as a design: what flows where, what is decided at each point, and the reasoning the harness gives or that its design implies. Section 4 already compared the decisions; here you see how they fit together inside one system.

Pi: two nested loops and two queues

Pi keeps its loop in a small package of its own, separate from the coding agent built on it, and works with its own message type until the very last moment, when it converts to the provider's format. The inner loop runs while there are tool calls to answer or steering messages waiting. The outer loop exists for one reason: when the inner loop would end, it checks the follow-up queue, and if anything is there it goes around again.

Decisions worth copying. The hooks are the policy: prepare next turn can swap the context, the model or the thinking level between steps (compaction runs here), and finish turn can end the run or force one more request. A reply cut off by its output limit has all its tool calls failed rather than run, with a message telling the model to reissue them complete. Changes to the available tools are declared to the model as a system message in the transcript, so replaying the transcript always reproduces exactly which tools were offered. Errors end the loop; retries live in the session around it.

What it leaves out on purpose: no step limit, no loop detection, no durability. Pi's position is a small core you can read in an afternoon, with everything else added by extensions.

Pi Durable: the same loop as a state machine

Pi Durable is a specification and implementation of the same agent as durable records. A model response is a task, and its progress is a named phase stored with it: prepare, request, poll (for providers that answer later through a handle), retry (with the time to wait until), tools (waiting on one task per tool call), and finishing phases for hooks that run after tools, after the answer, or when the run yields. Each phase change is one atomic commit, and only committed state is ever visible.

Two design choices carry the weight. The effect sandwich: commit the intent, perform the external effect, commit the outcome. If the process dies in the middle, reopening finds a stored intent and must retry safely, poll, or record that the effect was interrupted (Chapter 11 builds this). And turn limits as failed runs: when a run reaches its agent's maximum number of turns, its inputs are settled as unanswered with a turn_limit reason rather than silently stopping, so the caller always learns how the run ended. Its inbox has the same steer and follow-up lanes as Pi, plus display-only writes that never reach the model.

eve: no loop, a kernel and an engine

eve's harness does one step per call and returns the new session plus what should run next; the Workflow SDK drives it and saves a checkpoint at every step boundary. Before it ever calls the model, the step settles anything that happened outside the turn: results from background work, answers to questions and approvals, newly delivered messages. If the turn is waiting for a person to approve something, the step parks: it returns with nothing scheduled and no compute held, and a later delivery wakes it. If the turn would end while background tasks are still working, it returns held on those tasks instead of ending.

Why build it this way: eve sessions are meant to live for days in Slack threads and on servers that redeploy. A step function lets the engine move an idle session to a new deployment and recover after crashes without any loop code knowing. The costs are documented with unusual honesty: every piece of state must be saveable; only the eve version that started a workflow run can replay it, so an upgrade can strand sessions; and grouping several model calls into one step trades checkpoint overhead for a larger replay unit. Limits are money, not steps: a usage budget checked before every model call, which pauses the turn and asks the person to continue or stop. A tool can also end the turn by itself when its success is the whole answer, such as posting a reaction.

fx: a careful in-process loop with formal rules

fx is a native binary with one loop over steps. What makes it distinctive is how much happens at the step boundary and how carefully the order is fixed: notes queued by the previous step's gate, then a changed runtime context (a branch switch, for example), then any steering, each framed by who wrote it. The order is not cosmetic. A provider's prompt cache only reuses a request up to the first message that differs, so fx guarantees that each request starts with the previous request's exact messages, and it checks that guarantee with a formal model.

Its guards are each a response to a failure seen in practice: one nudge for an empty reply, at most two rounds of feedback for malformed tool calls, an end to the turn after three steps of the same failing shell command with nothing edited in between, and an optional review prompt after any step that wrote files. Recovery for model calls lives in its own module with capped waits, content-filter resends and a guard against crash loops that asks before resuming after two crashes. Every one of these rules has a TLA+ model with planted bugs (section 4, decision 8).

nanocode: a journaled runtime that hosts other harnesses

nanocode is an SDK that runs the Codex and Claude harnesses with their own prompts and tools, so its loop lives in each vendor driver while the runtime around it provides durability, steering, subagents and Code Mode. In the Claude driver, a turn is a sequence of numbered model calls resumed from a stored cursor. At each index it consumes any durable steering due at that boundary, compacts inside the turn if the context passed its threshold, and makes the model call as a journaled effect; tool calls are journaled too.

When a model call fails, the driver retries with a changed request and records which change it tried: dropping unsigned thinking, using a plainer summary, refreshing tools, or shrinking a request that was too large. A steer can optionally preempt a model call in progress. The design bet is that the vendor harnesses are already tuned for their models, so the most valuable thing a runtime can add is making them durable and embeddable, not replacing their loop.

Codex: a stateless loop built around the cache

OpenAI's own description is the simplest statement of the loop in this book: send the prompt, stream the reply, run any requested tool, append its output, query again, and end the turn when the model emits an assistant message instead of a tool call. Codex deliberately does not ask the server to remember earlier responses; every request carries the full history, to keep requests stateless and to support zero-data-retention customers. That makes the cache central: changing tools, the model, the sandbox, the approval mode or the working directory mid-conversation breaks the cached prefix, so Codex appends a new message describing the change instead of editing earlier content (OpenAI).

Three details show the care. The step context (settings, the tools offered, the tools that will run) is captured once per step, so what the model was offered and what can execute never drift apart inside a step. Tools start as soon as each call is complete in the stream and their results are kept in request order. An experimental option starts compaction in the background at a lower threshold so it is ready when needed, and it is tagged as mid-turn or post-turn depending on whether the model still has work to do. Retries for the stream and the request live inside the sampling call, invisible to the loop.

Claude Code: a simple loop and heavy infrastructure

The Claude Code study describes its core as a simple while-loop that calls the model, runs tools and repeats, and argues that the system invests in deterministic infrastructure rather than decision scaffolding such as explicit planners or state graphs. Its reactive ReAct design trades search completeness for simplicity and latency: each turn commits to one action sequence without backtracking (Dive into Claude Code).

The loop yields a stream of events, so the CLI, the SDK and the IDE all consume the same loop. Its state between iterations lives in one object, and the study counts seven places where the loop continues, each replacing that object in one whole assignment rather than mutating fields, which keeps every iteration's state consistent. It stops on five conditions: no tool use, the maximum number of turns, a prompt that is too long after recovery failed, a hook that stops continuation, or an abort. Recovery is a ladder: raise the output limit up to three times per turn, compact reactively at most once, then end with a prompt-too-long reason; a streaming fallback and a fallback model sit beside it.

Kimi Code: the loop as a log

Kimi Code's loop is an actor that owns three inbox lanes (normal prompts, notify messages that join the current turn, and system reminders) and records every change as an event. Six hook points (turn starting, message appending, step starting, tool batch starting, step stopping, step continuing) can each block with a recorded cause; even the step limit is just one blocking hook. A step's tool calls all start together, and the user can move a long-running tool to the background, at which point the model receives an acknowledgement and the turn continues.

The reasoning is the same as section 4's decision 1: if all state is a projection of a log, then debugging is replaying the log, resuming is replaying the log, and a crash halfway through a write shows up as a truncated last line that the reader can report instead of failing the whole session. The cost is discipline: nothing may change state except by recording an event.

Qwen Code: from seven loops to one

Qwen Code's loop today has three layers. A chat layer owns the provider request, retries, model fallback, output-limit escalation, auto-compaction and history. A client layer owns one interaction step: prompt-submit hooks, reminders, loop detection, the turn cap, and the continuations that run after the model stops (the Stop hook and steering). The shared loop on top sends a request, streams the reply, runs the requested tools as one batch with read, search and fetch calls in parallel, sends results back, and repeats.

Two choices stand out. Every exit has a named reason (completed, cancelled, loop detected, duplicate provider call, a tool ended the turn, the session turn cap, the token limit, a blocked prompt), which makes the loop's behaviour testable and visible. And the next-speaker check inherited from Gemini CLI, a second model call that reads the last reply and decides whether the model or the user should speak next, is now off by default: an extra model call on every stop is expensive, and the decision it makes is one the stop signal and the completion checks already cover. The unification story in decision 7 is the most useful part of Qwen Code for anyone designing a harness.

Trae Agent: the minimum that works for research

Trae Agent's loop counts steps up to a maximum (200 in its example configuration). Each step makes one blocking model call. If the reply calls task_done, the harness checks completion (in benchmark mode, that the change minus tests is not empty) and either ends or tells the model its patch is empty. If the reply has no tool calls, the harness says the task does not look complete. Otherwise it runs the calls, in parallel or in order by one setting, adds a reflection message for any failed tool, and records the whole step to a trajectory file.

The simplicity is a feature for its purpose. A small, stable loop means a change to one tool or one prompt is the only thing that changed between two experiments, and a full trajectory per step makes failures analysable. Its weaknesses for interactive use follow from the same choices: one exception ends the run, there is no way to steer, and a long task eventually fills the window.

7. Choosing a loop for what you want to build

You do not have to pick a harness; you have to pick answers. The questions below are ordered by how hard each is to change later.

For the harness you build in this book: shape A first, with all loop state in one object and the loop body written as a function that takes the state and returns the next state. That keeps Chapter 11's move to durability a matter of saving the object at each boundary, not a rewrite. Steering and a follow-up queue come in the exercises; limits and a loop detector before you ever run unattended.

8. Research and how Chinese teams see the loop

  • ReAct (2022) introduced interleaving reasoning, action and observation. Every loop here is ReAct plus engineering; the Claude Code study names it explicitly and contrasts it with graph-based orchestration, where control flow is a state machine with typed edges, and with tree search, which explores several trajectories before committing.
  • The Ralph loop: when the model tries to stop, a hook re-injects the original goal into a fresh context window, and files carry state between iterations. LangChain describes it as a harness pattern for long goals. It is an outer loop around the loop in this chapter, and the Stop hooks in Codex and Claude Code are the mechanism it needs.
  • Chinese practice. Chinese analyses stress that the innermost loop can be about 200 lines and that the hard part is everything around it (36Kr); practitioner write-ups describe the loop's job as mediating observation, action, feedback and completion (Jimmy Song). The two Chinese production harnesses in this chapter bear that out from opposite directions: Kimi Code rebuilt its loop around an event log, and Qwen Code spent a release cycle consolidating seven loop copies into one and is now turning it into an event-driven state machine. Both arrived at "one loop, explicit events" from different starting points.

9. Build: a 120-line agent with a step function

We use the openai Python SDK because almost every provider (OpenAI, OpenRouter, Ollama, vLLM, most Chinese labs) offers an OpenAI-compatible endpoint. Chapter 2 replaces it with our own provider layer.

pip install openai
export BASE_URL=...   # any OpenAI-compatible endpoint; leave unset for OpenAI
export API_KEY=...
export MODEL=...
import json, os, subprocess
from dataclasses import dataclass, field
from openai import OpenAI

client = OpenAI(base_url=os.getenv("BASE_URL"), api_key=os.getenv("API_KEY"))
MODEL = os.getenv("MODEL", "gpt-5-mini")
SYSTEM = "You are a coding agent. Use the tools to inspect and change files. Be brief."

def tool(name, desc, props, required):
    return {"type": "function", "function": {"name": name, "description": desc,
            "parameters": {"type": "object", "properties": props, "required": required}}}

TOOLS = [
    tool("read", "Read a text file.", {"path": {"type": "string"}}, ["path"]),
    tool("write", "Create or overwrite a file.", {"path": {"type": "string"}, "content": {"type": "string"}}, ["path", "content"]),
    tool("edit", "Replace exact text in a file. old must appear exactly once.",
         {"path": {"type": "string"}, "old": {"type": "string"}, "new": {"type": "string"}}, ["path", "old", "new"]),
    tool("bash", "Run a shell command and return its output.", {"command": {"type": "string"}}, ["command"]),
]

def run_tool(name, args):
    try:
        if name == "read":
            return open(args["path"]).read()[:20_000]
        if name == "write":
            os.makedirs(os.path.dirname(args["path"]) or ".", exist_ok=True)
            open(args["path"], "w").write(args["content"])
            return f"wrote {len(args['content'])} chars"
        if name == "edit":
            text = open(args["path"]).read()
            if text.count(args["old"]) != 1:
                return f"error: old text found {text.count(args['old'])} times, need exactly 1"
            open(args["path"], "w").write(text.replace(args["old"], args["new"]))
            return "edited"
        if name == "bash":
            p = subprocess.run(args["command"], shell=True, capture_output=True, text=True, timeout=120)
            out = (p.stdout + p.stderr)[-20_000:]
            return f"{out}\n[exit code: {p.returncode}]"
        return f"error: unknown tool {name}"
    except Exception as e:
        return f"error: {e}"

@dataclass
class State:
    messages: list
    steps: int = 0
    done: bool = False
    steering: list = field(default_factory=list)  # messages typed while the agent works

def step(state: State, max_steps: int = 50) -> State:
    """One unit of work: one model call plus the tool calls it asks for."""
    if state.steering:                       # deliver queued user messages first
        state.messages += [{"role": "user", "content": m} for m in state.steering]
        state.steering.clear()
    reply = client.chat.completions.create(model=MODEL, messages=state.messages, tools=TOOLS).choices[0].message
    state.messages.append(reply.model_dump(exclude_none=True))
    state.steps += 1
    if not reply.tool_calls:                 # no tool call: the turn is over
        state.done = True
        return state
    for call in reply.tool_calls:
        output = run_tool(call.function.name, json.loads(call.function.arguments or "{}"))
        state.messages.append({"role": "tool", "tool_call_id": call.id, "content": output})
    if state.steps >= max_steps:             # the harness, not the model, enforces limits
        state.messages.append({"role": "user", "content": "Step limit reached. Summarize and stop."})
    return state

def run(task: str) -> str:
    state = State(messages=[{"role": "system", "content": SYSTEM}, {"role": "user", "content": task}])
    while not state.done:
        state = step(state)
    return state.messages[-1].get("content", "")

if __name__ == "__main__":
    import sys
    print(run(" ".join(sys.argv[1:])))

Four design choices in this code, each taken from the code tour:

  • step() is the unit. It does one model call and its tools, and returns the state. run() is a thin driver, the role eve gives its workflow engine.
  • Steering waits for a step boundary, as in Pi. Never inject input in the middle of a tool batch.
  • Errors are results, not exceptions. A failed tool returns text that starts with error:, so the model can recover. Manus keeps failed actions in context for the same reason.
  • The harness enforces the step limit and tells the model, as fx does. The model never decides its own budget.
Safety for this week

This agent runs any shell command with your permissions. Run it inside a container or a throwaway VM (docker run -it -v $PWD:/work python:3.12 bash). Chapter 7 adds real permissions and a sandbox.

Your first test tasks

Make a small scratch repository and write 10 tasks the agent must do in it. Each task needs an automatic check, usually a test that passes only when the task is done. Examples:

  1. A function has an off-by-one bug; a failing test shows it. Fix it.
  2. Rename get_user to fetch_user everywhere.
  3. Add a --verbose flag to the CLI.
  4. Add type hints to one module without changing behaviour.
  5. Write a test for an untested function.
  6. Fix an import error after a file was moved.
  7. Make a slow function 10x faster (a timing test checks it).
  8. Update a README section to match the code.
  9. Add input validation that raises ValueError.
  10. Find and remove dead code that a test proves is unused.

Run all 10, reset the repo with git checkout . between tasks, and record: tasks passed, total steps, total tokens. That is your baseline. Every later chapter reports against it.

10. Exercises

  1. Parallel reads, ordered writes. Run tool calls in a thread pool, but make write and edit take an exclusive lock, Codex-style. Then try Pi's rule (any sequential tool makes the batch sequential) and fx's rule (group up to the first writer). Measure the time on a task that reads ten files and edits two.
  2. Steering and follow-ups. Add two queues. Steering messages join at the next step boundary; follow-up messages are checked only when the model stops. Type a correction while a long command runs and confirm the model sees it before its next call, not mid-command.
  3. A stop the model cannot fake. Before accepting a stop, run the task's check script. If it fails, add a message with the failure and continue, at most twice. Compare pass rates with and without it on your ten tasks.
  4. A loop detector. End the turn when the same tool call with the same arguments fails three steps in a row with no file changed in between. Write a task that triggers it.
  5. Crash and resume. Save state to a JSON file at every step boundary. Kill the process mid-task and restart from the file. Then kill it during a tool call that writes a file. What is wrong after the restart? (Chapter 11 fixes it.)
  6. Write the rules down. List five statements your loop must always satisfy (for example, "every tool call in the history has exactly one result"). Write a test for each that feeds the loop a scripted fake model.
